# SETTINGS_MODE_UX_PLAN.md — 설정모드 조작감·가독성 정비

> 착수: 2026-08-26 · 선행: [SETTINGS_MODE_UI_PLAN.md](SETTINGS_MODE_UI_PLAN.md) S-0~S-6 완료
> **이 계획은 기능을 바꾸지 않는다.** 같은 일을 더 쉽게·더 읽기 쉽게 하는 것만 다룬다.

---

## 0. 왜 지금인가

S-0~S-6은 **화면을 만드는 일**이었다. 화면 여덟 개를 각각 다시 그렸고, 그 결과 화면끼리 조작 방식이 갈라졌다. 한 화면 안에서는 말이 되는데 화면을 옮기면 손이 다시 배워야 한다.

측정으로 확인한 갈라짐이 넷이다.

| 축 | 실측 |
|---|---|
| 버튼 높이 | **14 ~ 33px** — 화면마다 다르다 |
| 삭제 조작 | **세 가지** — raw `✕` 6패널 · `SetIconButton`+✕ 1 · 휴지통 1 |
| 되돌리기 | **1개 패널에만** 있다. 나머지 6개는 확인도 없이 즉시 삭제 |
| 추가 위치 | 목록 **위** 2 : **아래** 4 |

그리고 글자 크기가 여섯 종인데 스케일은 다섯 단계다 — `13.33px`이 밖에 있다(스와치 100개 · 이미지 셀 11개).

---

## 1. 원칙

**하나. 같은 뜻은 같은 모양으로.** 삭제는 어디서나 같은 컨트롤·같은 자리·같은 되돌리기.

**둘. 파괴적 조작에는 되돌릴 길을 준다.** 확인 대화상자보다 **삭제 후 되돌리기 토스트**를 쓴다 — 흐름을 끊지 않으면서 실수를 되돌린다(Gmail · Linear · Notion의 방식). `SetToast` + `pendingDeletes` 구현이 이미 `SettingsLibraryPanel`에 있다.

**셋. 문서 정체성은 좌측 상단에.** 지금 무엇을 편집 중인지가 항상 보이고, 그 이름이 곧 전환 지점이다(Figma · Notion · Google Docs · VS Code 공통).

**넷. 목록에서는 행 전체가 대상이다.** 이름을 읽고 오른쪽 끝의 작은 버튼으로 이동하게 만들지 않는다(Finder · 탐색기 · Figma 최근 파일).

## 2. U-1 — 시나리오 전환 ✅ 완료 (2026-08-26)

### 지금 상태 (1280px 실측)

```
사이드바 240 │ 본문 1040 ──────────────────────────┤
                    저장·목록 툴바 x562 (우측 정렬)
                              저장목록 팝업 x740 w520
                                        └ 오른쪽 여백 20px
```

세 가지가 겹친다.

1. **정체성이 오른쪽에 있다.** 시선은 왼쪽 위에서 시작하는데 "무엇을 편집 중인가"가 반대편이다
2. **팝업이 메뉴도 대화상자도 아니다.** 520×260 패널이 오른쪽 끝에 붙고, 여는 버튼(x766)과 팝업(x740)의 모서리도 안 맞는다
3. **행마다 두 번 조준한다.** `불러오기`(77×26)와 삭제(26×26)가 오른쪽 끝에 나란히 있다

### 가는 곳

```
┌──────────────────────────────────────────────┐
│ ▾ 강릉 3층 상가 화재        ● 저장 안 됨      │  이름이 곧 전환 버튼
├──────────────────────────────────────────────┤
│  🔍 시나리오 검색…                            │
│  ────────────────────────────────────────    │
│  ● 강릉 3층 상가 화재        2일 전           │  행 전체 = 불러오기
│    속초 지하주차장           1주 전      ⋯    │  삭제는 ⋯ 안으로
│    양양 물류창고             3주 전      ⋯    │
│  ────────────────────────────────────────    │
│  + 새 시나리오   다른 이름으로   ⬆   ⬇       │
└──────────────────────────────────────────────┘
```

- `저장 목록` 버튼이 사라진다 — 이름 자체가 트리거다
- 목록은 이름 **바로 아래**로 열린다(좌측 정렬). 앵커가 분명해진다
- **인라인 이름 편집은 유지한다.** 시나리오를 쓰면서 이름을 자주 고치므로, 이름은 입력칸으로 두고 그 옆에 붙은 `▾`가 목록을 연다. 둘이 시각적으로 한 컨트롤이다
- `다른 이름으로`는 목록 바닥 액션으로 내린다(Figma·Google Docs가 파일 메뉴에 두는 자리). 툴바에는 `저장`만 남는다
- 항목이 많아지면 검색이 필요하다 — 8건 이상일 때만 검색칸을 그린다

### 완료 기준

- 이름·목록·상태칩이 **본문 좌측 정렬** (x = 사이드바 우측 경계)
- 목록 왼쪽 모서리가 이름 입력칸의 왼쪽 모서리와 **일치**
- 행 어디를 눌러도 불러오기. 삭제는 행 메뉴 안
- 현재 시나리오 행에 표시가 있고 다시 불러올 수 없다
- Esc·바깥 클릭으로 닫힌다. 열려 있을 때 `aria-expanded`

## 3. U-2 — 삭제 되돌리기 ✅ 완료 (2026-08-26)

### 범위를 좁혔다 — 체크리스트만

처음에는 여섯 패널 전부에 넣으려 했으나, **사용자 판단으로 체크리스트에만 넣는다.**
기준은 「삭제 부담」이다.

| 대상 | 지우면 | 판정 |
|---|---|---|
| **체크리스트 섹션** | 딸린 **항목이 통째로** 날아간다 | 2단계 + 되돌리기 |
| **체크리스트 항목** | 한 줄 | 1단계 + 되돌리기 |
| 지휘절차 · 프리셋 · 상태 메시지 · 구조대상자 · 건물 · 출동대 | 한 줄, 다시 쓰면 그만 | **그대로 둔다** |

되돌리기를 여섯 곳에 다 붙이면 토스트가 흔한 화면 장식이 되어 정작 위험한
삭제에서 눈에 안 띈다. 부담이 있는 곳에만 두는 편이 신호가 산다.

### 만든 것

- **섹션** — 윤곽선 휴지통 → (클릭) 채워진 휴지통 + 위험색 → (클릭) 삭제.
  툴팁이 `섹션 삭제` → `섹션 "…" 삭제 — 한 번 더 누르면 항목까지 지워집니다`
- **항목** — 휴지통 한 번 클릭으로 삭제. 되돌리기가 뒤를 받으므로 확인을 더 받지 않는다
- 둘 다 **지연 삭제**다. 목록에서 즉시 감추되 실제 삭제는 5초 뒤 —
  「되돌리기」는 타이머만 취소하므로 `checklistConfig` 는 그동안 한 번도 바뀌지 않는다.
  되살릴 자리를 기억할 필요가 없다
- `SetSortableHead` 에 `deleteIcon` · `deleteArmed` 를 **선택 프롭**으로 더했다 —
  지휘절차는 `✕` 그대로다(실측 확인)

### 검증

섹션 — 1단계에서 목록 변화 없음 · 아이콘 채움 · 24×24 유지 · 2단계에서 6 → 5 ·
되돌리기로 6 복구.
항목 — 한 번 클릭에 16 → 15 · 되돌리기로 16 복구 · `aria-label` 「항목 "출동지령" 삭제」.

## 4. U-3 — 컨트롤 크기 3단

| 단 | 높이 | 쓰는 곳 |

## 9. U-1 실측 (2026-08-26, 1280px)

| | 전 | 후 |
|---|---|---|
| 목록 위치 | x740 (오른쪽 끝, 여백 20px) | **x108** — 이름 상자 왼쪽 모서리와 일치 |
| 목록 폭 | 520 (버튼과 모서리 어긋남) | **392** — 이름 상자와 정확히 같음 |
| 행 클릭 영역 | 77×26 버튼 | **386×32** 행 전체 |
| 툴바 버튼 | 저장 · 다른 이름으로 · 저장 목록 · ⋯ | **저장 · ⋯** |

동작 확인 — 행 클릭 전환 ✓ · 전환 후 자동 닫힘 ✓ · 현재 항목 표시·잠금 ✓ ·
Esc 닫힘 ✓ · 바깥 클릭 닫힘 ✓ · 삭제가 행 메뉴 안 ✓ · 「다른 이름으로 저장」이
목록 바닥 ✓

### 걸린 것

목록을 `.slp__switcher` 에 걸었더니 라벨 폭(88px)만큼 왼쪽으로 밀려 모서리가
어긋났다. 기준점은 **이름 상자**여야 하는데, 그 상자는 `overflow: hidden`
(모서리를 한 번만 자르려고)이라 기준점이 될 수 없다 — `.slp__switcher-anchor`
를 한 겹 두어 해결했다.

`border-radius: 0 var(--set-r-sm) …` 의 리터럴 `0` 이 토큰 규칙에 걸렸다.
단축값을 쓰지 않고 부모의 `overflow: hidden` 으로 자르게 바꿨다 — 안쪽 요소가
각자 반경을 갖지 않아 더 낫다.

### U-1 후속 — 발견성 (2026-08-26)

「백업에서 복원했더니 시나리오가 목록에 안 보인다」는 보고를 받았다.

**데이터는 멀쩡했다.** 실제 백업 파일(시나리오 11건)로 복원해 보니
localStorage 에도 화면에도 11건이 전부 들어온다. 문제는 다른 데 있었다 —
U-1 이 「저장 목록」 버튼을 없앴는데, 복원 직후 목록을 찾을 곳이 라벨 없는
`▾` 하나뿐이었다. **내가 만든 발견성 회귀다.**

고친 것:

- 토글에 **시나리오 개수**를 함께 보인다(`11 ▾`). 숫자가 「뒤에 목록이 있다」는
  신호다. 1건 이하면 그리지 않는다
- 복원 직후 **목록을 저절로 연다.** 복원은 새로고침으로 끝나므로
  (여러 store 가 마운트 때만 localStorage 를 읽는다) 일회용 세션 플래그로
  건너뛴다. `importSettings` 가 복원 건수를 돌려주게 바꿔 토스트에 적는다
- 플래그는 **읽기만** 초기값에서 하고 지우는 것은 effect 에서 한다 —
  초기화 함수에서 지우면 StrictMode 의 두 번째 호출이 null 을 본다

교훈: **라벨을 지우면 그 자리에 다른 신호를 놔야 한다.** 「저장 목록」이라는
글자를 없앤 대가를 개수 표시로 치렀다.

### U-1 후속 2 — 목록이 통째로 안 보이던 진짜 원인 (2026-08-26)

앞의 「발견성」 진단은 **틀렸다.** 사용자가 보낸 화면에는 토글이 `6 ▾` 로
열려 있는데 그 안에 행이 하나도 없었다 — 목록을 못 찾은 것이 아니라
**열었는데 비어 있었다.**

실측하니 팝업은 86px 인데 안의 목록은 320px 였다. 목록의 `position` 이
`absolute`, `right: 20px`, `width: 520px` 로 잡혀 팝업 상자 **밖으로** 나가
있었고, 팝업은 `overflow: hidden` 이라 통째로 잘렸다.

원인은 `SettingsPage.css` 에 남아 있던 옛 규칙이다.

```css
.settings-page__topbar .slp__list,          /* (0,2,0) */
.settings-page__topbar .slp__save-as-row { position: absolute; right: 20px; … }
```

U-1 이 새로 쓴 `.slp__list` 는 (0,1,0) 이라 **졌다.** 이 규칙이 바로 원래
불만이던 「오른쪽 끝 팝업」을 만들던 코드인데, 파일이 달라
(`SettingsLibraryPanel.css` 가 아니라 `SettingsPage.css`) 정리에서 빠졌다.

`.slp__list` 를 선택자에서 뺐다. 팝업 모양은 이제 `.slp__list-pop` 한 곳이
그린다.

**교훈은 §9의 「분류 색이 죽어 있었다」와 같다** — 특이도가 높은 옛 규칙이
새 규칙을 조용히 이긴다. 눈으로 보면 「원래 저런가 보다」로 지나가고,
치수를 재야 드러난다. 화면을 옮길 때는 **옛 위치를 잡던 규칙이 어느 파일에
있는지** 먼저 찾아야 한다.

### U-1 후속 3 — 행 삭제를 제자리 2단계로 (2026-08-26)

`⋯` 메뉴가 세 가지를 잘못했다.

1. **무엇을 하는 버튼인지 눌러 봐야 안다.** 점 셋은 「뭔가 더 있다」이지 「지운다」가 아니다
2. **메뉴가 목록을 밀어낸다.** 열린 높이만큼 아래가 밀려 스크롤이 생기고, 지우려던 행이 눈에서 사라진다
3. 삭제 하나뿐인데 메뉴를 여는 것은 클릭이 한 번 더 드는 일이다

바꾼 것 — **제자리 2단계.**

| 상태 | 아이콘 | 툴팁 |
|---|---|---|
| 평소 | 윤곽선 휴지통(본문색) | `삭제` |
| 확인 대기 | **채워진** 휴지통 + 위험색 + 테두리 | `한 번 더 누르면 삭제됩니다` |

같은 자리에서 윤곽선 → 채움으로 바뀌는 것이 「한 번 더 누르면 지워진다」를
말한다. 다른 그림으로 바꾸면 무엇을 하는 버튼인지 다시 읽어야 한다. 두 상태의
크기·자리가 같아야 두 번째 클릭이 빗나가지 않는다(28×28 고정).

`window.confirm` 은 없앴다. 아이콘이 이미 확인을 받고, 실수는 5초 되돌리기가
받는다. 대화상자는 흐름을 끊고 정작 사람은 읽지 않고 누른다.

검증 — 팝업 높이 406 → 406(**스크롤 안 생김**) · 28×28 유지 · 윤곽 → 채움 ·
툴팁 전환 · 두 번째 클릭에 삭제(11 → 10) · 되돌리기로 복구(10 → 11).

#### 걸린 것 — 측정 환경의 함정

확인 대기 색이 안 바뀌는 것처럼 보였다. 실제로는 **개발용 브라우저 패널이
프레임을 합성하지 않아 CSS 트랜지션이 진행되지 않은 것**이다. 컴퓨티드 값이
시작색에 멈춰 있었다. `getAnimations().forEach(a => a.finish())` 로 강제 종료한
뒤 재니 danger 색이 정확히 나왔다.

**트랜지션이 걸린 속성을 이 패널에서 잴 때는 애니메이션을 먼저 끝내야 한다.**

## 10. U-6 — 이름을 고친 순간에만 갈림길을 보인다 (2026-08-26)

### 제안과 그 결함

「이름칸을 고치면 `저장` 버튼이 `다른 이름으로`로 바뀌게 하자」는 제안이 있었다.
촉발 조건(이름을 고쳤다 = 의도가 갈린다)은 정확한데, **그대로 하면 이름 변경이
불가능해진다.**

`saveSettings` 는 `activeSettingsId` 를 그대로 써서 upsert 한다. 즉 **이름칸을
고치고 `저장`을 누르는 것이 지금 유일한 이름 변경 경로**이고, 저장소에 별도
rename 함수가 없다. 이름을 고칠 때마다 복제된다면 `무림빌딩-중급`을
`무림빌딩-고급`으로 바꾸려던 사람이 파일 두 개를 얻는다.

이 코드베이스는 같은 종류로 이미 데였다 — 옛 「내보내기/가져오기」가 실제로는
백업이었는데 이름이 그렇게 읽히지 않아, 시나리오 하나를 주고받으려던 사람이
남의 설정을 통째로 덮었다.

### 한 것 — 버튼이 둘로 갈라진다

| 상태 | 버튼 |
|---|---|
| 평소 | `저장` |
| 이름이 저장된 것과 다름 | `이름 바꿔 저장` · `사본으로 저장` |

레이블이 결과를 그대로 적는다. `다른 이름으로 저장`은 「이름만 바꾸는 건가,
새로 만드는 건가」가 안 읽혔다. 툴팁은 더 구체적이다 —
`"DS타워-중급" 을 "DS타워-고급" 로 바꿔 저장합니다` /
`"DS타워-중급" 은 그대로 두고 … 를 새로 만듭니다`.

저장된 적 없는 시나리오는 비교 대상이 없으므로 늘 `저장` 하나다.

### 곁들여 지운 것

`다른 이름으로 저장` 전용 입력 줄(`.slp__save-as-row`)과 목록 바닥 액션
(`.slp__list-foot`)이 필요 없어졌다 — 이름칸 자체가 그 입력이다.

그래서 `SettingsPage.css` 의 옛 우측 팝업 규칙도 **마지막 사용자를 잃고 사라졌다.**
§9 후속 2에서 목록을 팝업 밖으로 끌어내던 바로 그 규칙이다.

### 검증

버튼 전환 — 평소 `저장` → 이름 고침 `이름 바꿔 저장`·`사본으로 저장` →
원래 이름 복구 시 다시 `저장` 하나.

동작 — `이름 바꿔 저장`: 11건 유지, `DS타워-중급` → `DS타워-고급`.
`사본으로 저장`: 11 → 12건, 원본과 사본이 함께 남는다.
