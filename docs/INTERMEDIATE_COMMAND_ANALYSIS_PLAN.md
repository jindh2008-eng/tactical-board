# 중급 지휘관평가 분석창 구현 계획

> 작성일: 2026-09-04  
> 작업 브랜치: `codex/intermediate-analysis-plan`  
> 범위: 코드 수정 전 설계. 초급·고급 확장을 전제로 중급 분석창을 먼저 구체화한다.

## 1. 목표와 기본 원칙

훈련 종료 후 전술상황판의 진행 기록을 근거로 지휘관의 판단과 자원 운용을 디브리핑할 수 있는 전문 분석보고서를 만든다. 첫 구현 대상은 중급이며, 이후 초급·고급은 동일한 분석 엔진에 등급별 평가 규칙을 주입하는 방식으로 확장한다.

분석 결과는 네 영역으로 나눈다.

1. 화재현장 출동 중 지휘절차 이행
2. 각 절차 진행의 적절성
3. 이벤트 발생 시 상황대처의 적절성
4. 수원 관리의 적절성

핵심 원칙은 다음과 같다.

- **사실과 평가를 분리한다.** 시간·이동·체크·연결·수량은 프로그램이 계산하고, 해석 문장은 규칙 엔진 또는 AI가 만든다.
- **모든 판정에는 근거가 있어야 한다.** 점수·경고·AI 문장마다 관련 로그 시각과 출동대/이벤트 ID를 연결한다.
- **AI가 없어도 보고서가 완성되어야 한다.** 기본 점수, 차트, 표, 경고는 브라우저에서 결정적으로 계산한다.
- **등급을 하드코딩하지 않는다.** 중급용 기준을 `AnalysisProfile`로 분리하고 초급·고급이 같은 화면과 계산기를 재사용한다.
- **훈련 중 설정 변화에 영향받지 않는다.** 분석은 훈련 세팅 시점에 동결한 시나리오·등급·평가 기준 버전을 사용한다.
- **현재 수리 모델과 평가 정책을 구분한다.** 실제 수량 계산 상수와 교육상 적정/부적정 판정 임계값은 별도 설정으로 둔다.

## 2. 현재 코드 기준 현황과 격차

### 이미 활용 가능한 기반

| 기반 | 현재 위치 | 분석 활용 |
|---|---|---|
| 훈련 등급 | `activeCommandProcedureLevel` | `intermediate`일 때 중급 프로필 선택 |
| 지휘절차 정의 | `commandProcedureConfigs[level]` | 분모, 카테고리, 항목명 |
| 지휘절차 체크 상태 | `ChecklistProgressContext.checked` | 훈련 종료 시 최종 이행 여부 |
| 통합 로그 | `LogContext`, `LogEntry` | 경과시간·절대시각·사건 유형 |
| 출동대 이동 | `payload.kind === 'move'` | 이벤트 전후 배치 재구성 |
| 이벤트 변화 | `event-status`, `event-fire-pct` | 발생·진행·해소 시각 |
| 방수 상태 | `payload.kind === 'spray'` | 방수 개시·중단과 대상 |
| 수원 연결 | `WaterConnectionContext` | 현재 연결 토폴로지 |
| 수량·유량 계산 | `WaterLevelContext` | 펌프 2,800L, 물탱크 6,000L 및 유량 계산 |
| 훈련 시작·종료 | `payload.kind === 'training'` | 분석 구간 경계 |

### 구현 전에 보강해야 할 데이터

| 부족한 정보 | 현재 한계 | 필요한 보강 |
|---|---|---|
| 절차 체크 이력 | 체크할 때 평문 로그만 남고 해제는 기록되지 않음 | 등급·카테고리·항목 ID·체크 여부를 담는 구조화 로그 |
| 절차 기준 시간 | 항목에 기대 시점·제한 시간이 없음 | 중급 평가 프로필에 시작점, 권장시간, 필수 선행조건 정의 |
| 이벤트 순간 배치 | 이동 로그를 전부 재생해야 하며 초기 상태 누락 가능 | 이벤트 발생 시 출동대·임무·상태·방수·수원 연결 스냅샷 저장 |
| 대응 행위의 의미 | 이동/상태 로그는 있으나 어떤 이벤트에 대한 대응인지 불명확 | 시간창+대상 위치로 자동 연계하고 분석 화면에서 수동 보정 가능하게 설계 |
| 수원 시간 이력 | 현재 잔량만 저장하고 50%/0%만 로그에 남음 | 구조화된 송수 연결/해제 기록의 구간별 유량을 적분해 재구성 |
| 송수 구조화 로그 | 연결/해제가 주로 `note` 문자열 | 공급원·수신처·연결/해제·유량을 payload로 저장 |
| 펌프 과부하 기준 | 물 소모는 계산하지만 펌프 토출 한계 판정 없음 | 동시 방수 6개대 이상, 집중운용 시간, 예비 수원 여부를 평가 규칙으로 추가 |
| 분석 당시 설정 | 분석을 열 때 현재 설정을 읽으면 훈련 후 변경에 취약 | 훈련 시작 스냅샷과 평가 프로필 버전을 결과 번들에 포함 |

## 3. 화면 정보구조

현재 `AnalysisModal`은 `/play` 안에서 열리는 스텁이다. 1차 구현은 라우트를 늘리기보다 이 모달을 **전체 화면 분석 워크스페이스**로 확장한다. 훈련 화면 Context와 세션 데이터를 그대로 읽을 수 있고 기존 메뉴 동작도 유지된다. 추후 결과 보관·직접 링크가 필요해질 때 `/analysis/:sessionId` 독립 라우트로 분리한다.

### 공통 상단부

- 보고서 제목: 대상명 + `중급 지휘관평가 분석`
- 훈련 메타: 훈련일시, 총 시간, 대상 건물, 화점, 출동 편성, 평가 기준 버전
- 상태 배지: `훈련 중`, `훈련 종료`, `데이터 불완전`
- 전체 요약 카드: 종합점수, 절차 이행률, 이벤트 평균 대응시간, 수원 위험 노출시간
- 페이지 탭: `종합` / `지휘절차 이행` / `절차 적절성` / `이벤트 대응` / `수원 관리`
- 공통 필터: 전체 시간 또는 구간, 출동대, 층·방면, 중요도
- 공통 작업: 근거 로그 보기, JSON 내보내기, Markdown 요약 내보내기, 인쇄/PDF

점수는 초기에 100점 만점으로 표시하되 가중치는 확정 전 `잠정` 표식을 붙인다. 예시 기본값은 지휘절차 이행 25, 절차 적절성 25, 이벤트 대응 30, 수원 관리 20이다. 교육 담당자가 기준을 승인하기 전에는 점수를 공식 성적으로 사용하지 않는다.

## 4. 종합 페이지

전문가가 디브리핑을 시작하는 첫 장이다.

### 구성

1. **핵심 결과 카드**
   - 종합점수와 등급
   - 필수절차 누락 수
   - 중요 이벤트 미대응/지연 수
   - 수량 소진·토출 부족·단일펌프 집중운용 시간

2. **훈련 전체 타임라인**
   - 가로축은 훈련 경과시간
   - 레인: 지휘절차, 화재/이벤트, 출동대 재배치, 방수, 수원 위험
   - 마커를 선택하면 네 상세 페이지의 해당 근거로 이동

3. **영역별 점수 레이더 또는 가로 막대차트**
   - 네 평가영역의 균형을 비교
   - 표본 부족 영역은 회색 `평가 불가`로 처리하며 0점으로 만들지 않음

4. **잘한 점 / 개선 우선순위**
   - 각각 최대 3건
   - 문장 아래에 `[03:25 이벤트 발생]`, `[04:10 진압2 이동]`처럼 근거 링크 표시

5. **AI 종합평가 영역**
   - 기본 상태는 프로그램이 만든 근거 요약
   - 사용자가 ChatGPT 분석 결과를 붙여 넣거나 향후 API 결과를 불러오면 전문가 서술로 교체
   - AI 문장에도 `근거 있음`, `추론`, `확인 필요` 태그를 표시

## 5. 페이지 1 — 화재현장 출동 중 지휘절차 이행

### 핵심 질문

- 중급 지휘절차 중 무엇을 수행·누락했는가?
- 수행 순서와 시점은 적절했는가?
- 필수 절차가 현장도착 전 또는 지정 기준시점 안에 완료됐는가?

### 화면 구성

- **이행률 도넛**: 전체/필수/권고 항목의 완료율
- **카테고리별 막대차트**: 상황파악, 지휘선언, 자원요청 등 설정된 카테고리 단위 완료율
- **절차 타임라인**: 항목별 권장 구간과 실제 체크 시각 비교
- **상세 표**

| 열 | 내용 |
|---|---|
| 분류 | 지휘절차 카테고리 |
| 절차 | 설정된 항목명 |
| 중요도 | 필수/권고 |
| 기준시점 | 훈련 시작, 첫 착대, 현장도착, 특정 이벤트 등 |
| 실제 수행 | 시각 또는 미수행 |
| 지연 | 기준 대비 초/분 |
| 판정 | 적정/지연/누락/평가 불가 |
| 근거 | 체크 로그 및 관련 사건 링크 |

### 프로그램 판정

- `완료율 = 완료 항목 수 / 적용 대상 항목 수`
- 항목별 `actualAt - anchorAt`을 계산해 권장시간과 비교
- 선행 절차가 정의된 경우 순서 위반 탐지
- 훈련 조건상 적용되지 않는 항목은 분모에서 제외
- 체크 후 해제된 항목은 최종 상태와 최초/최종 체크시각을 모두 표시

세부 평가 기준을 나중에 주더라도 화면을 다시 만들지 않도록, 항목 정의에 아래 메타데이터를 붙이는 구조로 설계한다.

```ts
interface ProcedureCriterion {
  itemId: string;
  required: boolean;
  anchor: 'training-start' | 'first-arrival' | 'incident-arrival' | `event:${string}`;
  expectedWithinSec?: number;
  prerequisites?: string[];
  weight: number;
  evidenceKinds: string[];
}
```

## 6. 페이지 2 — 각 절차 진행의 적절성

이 페이지는 단순 체크 여부가 아니라 **절차를 어떤 상황에서 어떤 순서로 수행했는지** 평가한다. 사용자가 추후 제공할 세부지침은 코드 분기가 아니라 버전이 있는 규칙 데이터로 등록한다.

### 화면 구성

- **판정 분포 차트**: 적정/부분 적정/부적정/평가 불가
- **절차별 근거 카드**
  - 기대 행동
  - 실제 관측 행동
  - 시간·순서 차이
  - 긍정 근거와 개선 근거
  - 관련 로그 원문
- **선후관계 흐름도**: 필수 선행 절차와 실제 순서를 겹쳐 표시
- **오류 유형 표**: 누락, 지연, 순서 역전, 자원 부족 상태에서의 결정, 반복 수정

### 규칙 표현

각 기준은 `적용조건 → 기대행동 → 시간창 → 판정 → 근거`로 표현한다.

```ts
interface AnalysisRule {
  id: string;
  level: 'beginner' | 'intermediate' | 'advanced';
  category: 'procedure' | 'event' | 'water';
  version: string;
  when: Condition[];
  expect: ExpectedAction[];
  withinSec?: number;
  severity: 'info' | 'warning' | 'critical';
  score: { pass: number; partial: number; fail: number };
}
```

첫 단계에서는 규칙을 TypeScript/JSON 파일로 관리하고, 기준이 안정된 뒤 설정관리 UI를 추가한다. 자유문장 지침을 바로 실행 규칙으로 쓰지 않고 사람이 검토한 구조화 규칙으로 변환해야 판정이 재현 가능하다.

## 7. 페이지 3 — 이벤트 상황대처의 적절성

### 분석 대상

- 화재확산 및 화재단계 변화
- 구조대상자 발견
- 폭발
- 대원부상
- 그 밖의 설정 이벤트
- 이벤트 전후 출동대 재배치, 임무·상태 변경, 추가출동 요청, 방수 변경

### 이벤트 한 건의 분석 구간

- 기준점 `T0`: 이벤트 최초 발생 시각
- 사전상황: 기본 `T0-2분 ~ T0`
- 초기대응: 기본 `T0 ~ T0+1분`
- 후속대응: 기본 `T0+1분 ~ T0+5분` 또는 이벤트 해소 시각
- 이벤트 종류별로 시간창을 중급 프로필에서 조정

### 화면 구성

- **이벤트 목록/심각도 필터**
- **대응시간 분포 차트**: 최초 인지, 최초 지시, 최초 이동, 최초 유효조치, 해소까지
- **이벤트 전후 배치 비교**: `발생 직전`과 `발생 후 1/3/5분`의 방면·층별 출동대 표
- **이벤트 상세 타임라인**: 사건과 대응 행동을 한 축에 표시
- **대응 매트릭스 표**

| 이벤트 | 발생 | 최초대응 | 유효조치 | 해소 | 재배치 | 추가자원 | 판정 |
|---|---:|---:|---:|---:|---|---|---|

### 판정 방법

- 이벤트 위치와 출동대 이동 목적지, 임무, 방수 대상을 함께 비교한다.
- 단순 이동을 대응으로 오인하지 않도록 이벤트 유형별 `유효행동` 목록을 둔다.
- 발생 전 이미 적절한 자원이 배치돼 있었다면 `선제대응`으로 인정한다.
- 여러 이벤트가 겹치면 한 행동을 자동으로 중복 가점하지 않는다. 가장 직접적인 이벤트에 우선 연결하고 검토 가능한 후보로 남긴다.
- 이벤트 시점의 전체 배치 스냅샷과 이후 변화분을 함께 보관해 “그때 현장에 무엇이 있었는가”를 재현한다.

## 8. 페이지 4 — 수원 관리의 적절성

### 확정된 단순 계산 기준

수원 분석에서는 현재 `WaterLevelContext`의 상세 수리 모델을 재사용하지 않는다. **이벤트 기록의 송수 연결/해제 기록만** 시간순으로 재생하여 펌프차와 물탱크차의 수량을 계산한다.

- 1선펌프의 송수라인에 연결된 **모든 출동대**는 종류와 관계없이 1개대당 **300L/min 소모**
- 소화전에 연결된 펌프 또는 물탱크에는 소화전 1개당 **1,000L/min 유입**
- 같은 시각의 순변화량은 `소화전 유입량 - 연결 출동대 수 × 300`으로 계산
- 연결 또는 해제가 일어난 시각마다 구간을 나누고, 다음 사건까지의 경과시간만큼 순변화량을 적분
- 차량 수량은 0L 미만 또는 정격용량 초과가 되지 않도록 제한
- 소화전 연결이 없는 상태에서 다른 펌프에 송수하는 펌프·물탱크는 저장수만 감소하며, 지속 공급을 위해 순환보수 필요 여부를 분석
- 일반 펌프차의 적재수량은 **2,800L**로 계산한다.
- 물탱크차의 초기 적재수는 훈련설정 또는 별도 분석설정 값을 사용한다. 값이 없을 때는 현재 프로그램 기본값 6,000L를 적용하고 보고서에 기본값 사용을 표시한다.

예를 들어 어떤 중요물탱크에 출동대 4개대가 연결되면 수요는 1,200L/min이다. 소화전 1개가 동시에 연결되어 있으면 순감소는 200L/min이고, 소화전이 없으면 1,200L/min으로 감소한다.

송수 로그에는 계산에 필요한 `연결/해제`, `fromId/fromType`, `toId/toType`, 차량 표시명과 사건 시각이 구조화되어 있어야 한다. 기존 평문 로그만 있는 훈련은 문자열 해석 결과에 `낮은 신뢰도`를 표시한다.

### 순환보수 분석

순환보수는 소화전에 직접 연결되지 않은 중요물탱크를 여러 대의 펌프차가 왕복하며 계속 보수하는 방식으로 정의한다.

1. 중요물탱크에 펌프차 1대가 연결되어 보수한다.
2. 보수를 마친 펌프차는 사용 중이지 않은 인근 소화전으로 이동한다.
3. 대기 중인 다음 펌프차가 중요물탱크 위치로 이동해 보수를 이어간다.
4. 소화전에서 충수한 펌프차는 현장으로 복귀해 현재 보수 차량 뒤에서 대기한다.
5. 이 교대를 반복해 중요물탱크의 방수 공급을 끊지 않는다.

분석기는 훈련대상의 소화전 설정에서 **사용 중이지 않은 소화전**과 거리를 가져오고, 펌프차 이동속도는 **시속 50km**로 계산한다. 편도 이동시간(분)은 다음과 같다.

```text
편도 이동시간 = 소화전 거리(km) ÷ 50(km/h) × 60
```

순환보수 펌프차의 적재량은 2,800L이며, **2,500은 1회 보수량이 아니라 중요물탱크로 보내는 최대 유량 2,500L/min**이다. 소화전 충수 유량은 1,000L/min이므로 빈 펌프차에 2,800L를 채우는 데 2분 48초가 걸린다.

중요물탱크의 수량이 충분할 때는 그 물탱크에 연결된 1선펌프의 총 소모량만큼 공급한다. 예를 들어 연결 출동대가 6개대이면 `6 × 300 = 1,800L/min`, 1개대이면 300L/min으로 보수한다. 이동시간 때문에 중요물탱크의 수량이 줄어 부족한 상태라면 펌프차가 최대 2,500L/min으로 공급해 현재 소비를 감당하면서 부족분을 회복한다.

- 정상 유지 공급유량: `D = 연결 출동대 수 × 300L/min`
- 부족 수량 회복 공급유량: 최대 `2,500L/min`
- 부족 상태의 순회복 유량: `2,500 - D` L/min
- `D > 2,500L/min`이면 펌프차 1대가 보수 중이어도 중요물탱크 수량이 계속 감소하므로 별도 공급라인이 필요하다고 판정

필요 차량 수는 각 펌프차가 2,800L를 최대 2,500L/min으로 보수하고, 1,000L/min으로 다시 충수해 왕복하는 전체 순환주기의 평균 공급량이 수요 `D` 이상이 되도록 계산한다.

```text
D = 중요물탱크에 연결된 모든 출동대 수 × 300L/min
C = 펌프차 적재량 2,800L
Q = 부족 상태 보수유량 2,500L/min
보수시간 = C ÷ Q = 1.12분
왕복 이동시간 = 소화전 거리(km) × 2 ÷ 50(km/h) × 60
충수시간 = C ÷ 1,000L/min = 2.8분
차량 1대의 순환주기 = 보수시간 + 왕복 이동시간 + 충수시간
필요 펌프차 수 = max(3, ceil(D × 순환주기 ÷ C))
```

이 식은 이동·충수 외 연결 전환 준비시간이 0분이라는 현재 가정이다. 준비시간이 정해지면 순환주기에 더한다.

예시처럼 50m 소화전을 첫 번째 중요물탱크가 이미 사용하고 있고, 두 번째 중요물탱크가 사용할 수 있는 미사용 소화전이 3km 거리에 있다면 두 번째 중요물탱크는 3km 소화전을 기준으로 왕복시간·충수시간·보수시간을 계산한다. 여기에 두 번째 중요물탱크에 연결된 출동대 수(`개대 수 × 300L/min`)를 적용해 순환보수 펌프차의 필요 대수를 제시한다.

3km 소화전을 사용하는 경우 왕복 이동시간은 7.2분, 충수시간은 2.8분, 최대유량 보수시간은 1.12분이므로 한 차량의 순환주기는 11.12분이다. 연결 출동대 수에 따른 예시는 다음과 같다. 연결 전환 준비시간과 교통 지연은 포함하지 않는다.

| 연결 출동대 | 수요 | 순환주기 평균 필요량 | 계산 필요 대수 |
|---:|---:|---:|---:|
| 1개대 | 300L/min | 3,336L | 3대(최소 편성 적용) |
| 4개대 | 1,200L/min | 13,344L | 5대 |
| 6개대 | 1,800L/min | 20,016L | 8대 |

실제 시계열에서는 펌프차의 남은 적재수와 중요물탱크의 여유용량을 함께 적용한다. 중요물탱크가 정격용량에 도달하면 보수를 멈추며 남은 물은 해당 펌프차에 유지한다.

### 전술상황판 후속 구현 항목

현재 전술상황판에는 순환보수 행동 자체가 없다. 후속 기능으로 다음을 추가해야 한다.

- 펌프차에 `순환보수 투입`, `중요물탱크 보수`, `소화전으로 이동`, `소화전 충수`, `현장 복귀`, `교대 대기` 상태 추가
- 중요물탱크 지정 기능
- 순환보수 조 편성 및 순번 표시
- 훈련대상 소화전 정보와 사용 중 여부 연동
- 출발·도착·충수 시작/완료·보수 시작/완료를 구조화 이벤트 로그로 기록
- 실제 순환보수가 시행된 경우 계획 필요 대수와 실제 투입 대수·공급 공백을 분석 결과에서 비교

### 화면 구성

1. **전체 수량 시계열**
   - 펌프/물탱크별 잔량(L, %)
   - 50%, 20%, 0% 임계선
   - 송수 연결/해제와 소화전 연결/해제 마커

2. **수요·공급 차트**
   - 연결 출동대 수 × 300L/min의 총 수요
   - 연결 소화전 수 × 1,000L/min의 총 유입
   - 부족 구간을 붉은 면적으로 표시

3. **수원 연결 토폴로지**
   - `소화전/물탱크/펌프 → 펌프/고가/진압대` 연결을 시점별로 표시
   - 단일 고장점은 붉은 테두리, 예비 경로는 녹색 표시

4. **펌프 부하 히트맵**
   - 행: 펌프·물탱크
   - 열: 시간
   - 값: 동시 방수대 수 또는 사용률
   - 6개대 이상 구간 강조

5. **위험 구간 표**

| 시작~종료 | 위험 | 영향 출동대 | 원인 | 지속시간 | 개선 권고 | 근거 |
|---|---|---|---|---:|---|---|

6. **순환보수 산정 카드**
   - 대상 중요물탱크와 연결 출동대 수
   - 필요 보수량(`연결된 모든 출동대 수 × 300L/min`)
   - 이용 가능한 미사용 소화전과 거리
   - 왕복 이동시간(시속 50km 기준)
   - 차량 적재량, 최대 보수유량과 순환주기
   - 최소 필요 펌프차 수와 실제 보유/투입 대수
   - 부족 대수와 예상 공급 공백

### 핵심 지표

- 최초 방수부터 안정 수원 확보까지 걸린 시간
- 총 방수시간 중 공급 부족 시간 비율

- 단일 펌프 집중운용 시간

- 잔량 50%/20%/0% 이하 체류시간
- 소화전 및 예비 물탱크 확보 시점
- 독립 수원 수와 최대 단일고장 영향도
- 중요물탱크별 순환보수 필요 여부와 필요 펌프차 수

수원 분석은 실제 물리 시뮬레이션이 아니라 현재 교육용 모델에 기반한 추정임을 보고서에 명시한다.

## 9. 데이터 모델과 분석 파이프라인

### 권장 흐름

```text
훈련 세팅
  → 시나리오·등급·평가기준 버전 동결
  → 훈련 중 구조화 로그 + 이벤트 상태변화 스냅샷 수집
  → 훈련 종료 시 AnalysisSession 생성
  → 순수 함수 분석 엔진이 네 영역의 지표·판정·근거 생성
  → React 보고서가 동일 결과를 차트·표로 표시
  → JSON/Markdown/PDF 내보내기
  → 필요 시 ChatGPT에서 전문가 종합평가 작성
```

### 권장 핵심 타입

```ts
interface AnalysisSession {
  schemaVersion: number;
  sessionId: string;
  level: 'beginner' | 'intermediate' | 'advanced';
  profileVersion: string;
  startedAt: number;
  endedAt: number;
  scenario: FrozenScenarioSnapshot;
  logs: LogEntry[];
  eventSnapshots: EventSituationSnapshot[];
  hydrants: FrozenHydrantSnapshot[];
}

interface AnalysisFinding {
  id: string;
  domain: 'procedure-compliance' | 'procedure-quality' | 'event-response' | 'water-management';
  ruleId: string;
  verdict: 'good' | 'adequate' | 'needs-improvement' | 'critical' | 'not-assessable';
  score?: number;
  title: string;
  summary: string;
  evidence: EvidenceRef[];
  confidence: 'high' | 'medium' | 'low';
}
```

원본 로그는 수정하지 않고, 분석 결과를 별도 파생 데이터로 만든다. 규칙이 바뀌면 같은 원본으로 재분석할 수 있어야 한다.

### 저장 전략

- 훈련 중: 기존 `sessionStorage`에 현재 세션 유지
- 종료 시: `AnalysisSession` JSON 다운로드를 1차 영구보관 방식으로 제공
- 후속 단계: 여러 훈련 비교가 필요해질 때 IndexedDB에 결과 목록 저장
- 별도 텔레메트리를 저장하지 않고 송수 연결/해제 사건 사이의 수량 변화는 분석 시 계산해 저장량을 줄임
- 개인정보·무전 STT를 포함할 수 있으므로 이름/전화번호 등 불필요한 식별정보를 내보내기 전에 제거

## 10. AI 전문 분석 연계

### 1차 권장안: 파일 내보내기 + ChatGPT 프로젝트

프로그램은 다음 두 파일을 만든다.

1. `analysis-session.json`: 원본에 가까운 구조화 사실, 기준 버전, 프로그램 판정, 근거 참조
2. `analysis-brief.md`: 사람이 읽기 쉬운 훈련 개요, 네 영역 요약, 확인이 필요한 쟁점

ChatGPT 프로젝트에는 다음을 프로젝트 소스로 둔다.

- 중급 지휘전술 지침
- 소방 SOP
- 지휘관 평가표
- 평가 용어와 점수 기준
- 프로그램이 내보낸 해당 훈련의 JSON/Markdown

프로젝트 지침에는 다음 원칙을 고정한다.

- 제공된 파일 밖의 사실을 만들어내지 않는다.
- 모든 평가 문장에 `findingId` 또는 로그 시각을 인용한다.
- `관측 사실`, `전문가 해석`, `추가 확인 필요`를 구분한다.
- 데이터가 없으면 감점하지 말고 `평가 불가`로 표시한다.
- 프로그램의 수치 계산은 재계산하지 말고 모순만 지적한다.
- 최종 출력은 종합평가, 강점, 개선사항, 핵심 디브리핑 질문 순서로 작성한다.

ChatGPT 프로젝트는 파일과 프로젝트별 지침을 함께 유지할 수 있으므로 반복 분석에 적합하다. 다만 ChatGPT 프로젝트에 파일을 올리는 흐름과 프로그램 내부 자동 분석은 별개다. 초기에는 수동 업로드로 검증하고, 자동화를 원할 때 서버 측 OpenAI API 연동을 별도 단계로 구현한다.

### 2차 선택안: OpenAI API 자동화

- 브라우저 코드에 API 키를 넣지 않고 별도 서버에서 호출
- Responses API에 분석 번들과 평가 지침을 전달
- 응답은 자유문장이 아니라 `AiAnalysisResult` 구조로 검증
- 결과에는 사용 모델, 프롬프트 버전, 생성 시각, 입력 파일 해시를 저장
- AI 결과는 프로그램 판정을 덮어쓰지 않고 별도 레이어로 표시
- 민감한 훈련자료의 외부 전송 승인, 보존정책, 접근권한을 먼저 확정

## 12. 단계별 구현 순서

### A. 평가 기준 확정 전에도 가능한 기반 작업

1. `AnalysisSession`, `AnalysisFinding`, `EvidenceRef` 스키마 확정
2. 훈련 세팅 시 등급·시나리오·프로필 버전 동결
3. 지휘절차 체크/해제 구조화 로그 추가
4. 송수 연결/해제 구조화 로그 추가
5. 이벤트 발생 스냅샷과 소화전 사용상태 보존
6. JSON/Markdown 내보내기 및 스키마 검증

### B. 중급 분석 MVP

1. 전체 화면 분석 셸과 공통 필터
2. 페이지 1 지휘절차 이행률·상세표
3. 페이지 3 이벤트별 타임라인·배치 비교
4. 페이지 4 수량/수요·공급 차트와 순환보수 필요 대수 산정
5. 종합 페이지와 인쇄 레이아웃
6. 근거 드로어와 `평가 불가` 처리

페이지 2는 세부지침이 필요하므로 UI 골격과 규칙 인터페이스까지만 먼저 만들고, 지침을 받은 뒤 규칙을 채운다.

### C. 전문가 기준 반영

1. 중급 세부 평가표를 구조화 규칙으로 변환
2. 실제 훈련 3~5건을 전문가가 수기 평가
3. 프로그램 판정과 비교해 임계값·가중치 조정
4. 규칙 버전 `intermediate-v1` 고정
5. 초급 프로필을 같은 엔진에 추가

### D. AI 연계

1. ChatGPT 프로젝트용 파일과 프로젝트 지침 템플릿 제공
2. 전문가가 AI 문장의 근거성·일관성 검수
3. 필요할 때만 서버/API 자동화

## 13. 검증 기준

- 동일한 `AnalysisSession`을 여러 번 분석해도 점수와 finding이 동일하다.
- 모든 점수와 경고에서 원본 로그/스냅샷으로 이동할 수 있다.
- 로그가 부족한 항목은 0점이 아니라 `평가 불가`가 된다.
- 이벤트 발생 시점의 배치와 이후 1/3/5분 배치가 실제 로그 재생 결과와 일치한다.
- 송수 로그만 재생한 수원 시계열의 특정 시점을 수동 계산했을 때 허용 오차 이내다.
- 5개대→6개대 전환, 추가 펌프 확보, 펌프 고장 시 위험 구간이 정확히 열리고 닫힌다.
- 50m와 3km 소화전 사례에서 사용 중인 소화전은 후보에서 제외되고, 시속 50km 기준 이동시간과 최소 3대 규칙이 정확히 적용된다.
- 브라우저 화면과 인쇄/PDF에서 표 잘림, 차트 범례 누락, 색상만으로 판정하는 문제가 없다.
- 구버전 세션은 가능한 범위까지만 분석하고 누락 데이터 경고를 명시한다.
- AI가 생성한 모든 핵심 주장에 유효한 `findingId` 또는 로그 근거가 있다.

## 14. 구현 전 확정이 필요한 교육 정책

아래 값은 기술적으로 임의 결정하면 안 된다.

1. 중급 지휘절차 항목별 필수/권고, 기준시점, 허용시간, 선행조건
2. 이벤트 종류별 기대 대응과 허용시간
3. 절차·이벤트·수원 영역의 배점과 감점 상한
4. 물탱크차의 초기 적재용량을 항상 6,000L로 고정할지, 차량별 설정을 허용할지
5. 거리 계산에 사용할 값이 직선거리인지 실제 도로거리인지
6. 출발·도착 및 연결 전환에 별도의 준비시간을 더할지
7. 교통 지연이나 현장 진입 지연을 반영할지
8. AI 업로드가 허용되는 데이터 범위와 익명화 수준

이 정책들은 `intermediate-v1` 프로필로 버전 관리한다. 정책 변경 후 과거 훈련을 새 기준으로 재분석할지, 당시 기준을 유지할지도 함께 정한다.

## 15. 최종 제안

첫 구현은 “AI가 평가하는 화면”보다 **근거가 남는 결정적 분석 엔진**에 집중한다. 중급 평가 기준을 프로그램 규칙으로 만들고, AI는 그 결과와 SOP를 바탕으로 디브리핑 문장을 작성하게 해야 계산 오류와 환각을 통제할 수 있다.

따라서 가장 먼저 할 일은 화면 CSS가 아니라 다음 세 가지다.

1. 지휘절차·송수 로그의 구조화
2. 이벤트 순간 배치와 송수 연결 이력의 구조화
3. 중급 평가기준을 담을 버전형 프로필 확정

이 기반이 갖춰지면 네 상세 페이지, 종합보고서, ChatGPT 전문 분석이 모두 같은 근거 데이터를 공유하게 된다.
