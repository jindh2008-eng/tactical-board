## 0. 요약 — 결론부터

### 0.1 훈련창이 무너지는 진짜 이유

배율 계산이 틀린 게 아니다. `useUiScale`의 `min(w/2560, h/1364)`는 정확하다. 문제는 **그 배율을 따르는 요소가 전체의 7%뿐**이라는 것이다.

`/play` 계열 CSS 47개 파일 실측:

| 치수 체계 | 개수 | 비율 | 화면 크기에 따라 |
|---|---:|---:|---|
| **원시 px** | **1,157** | **72%** | ❌ **전혀 안 변한다** |
| rem | 221 | 14% | 루트 글꼴(`--font-scale`, 하한 0.78)을 따라감 |
| `--ui-scale` 환산 | 107 | 7% | 기하 배율(하한 0.50)을 따라감 |
| % / clamp | 120 | 7% | 컨테이너를 따라감 (위 둘과 무관) |

**네 개의 서로 다른 자가 한 화면에 있고, 이들이 일치하는 지점은 2560×1364 단 하나다.** 해상도가 그 점에서 멀어질수록 넷이 각자 다른 속도로 벌어진다. 사용자가 본 "각 부분이 개별적으로 축소확대"는 정확히 이 현상이다.

### 0.2 권장 방향

| 화면 | 방식 | 이유 |
|---|---|---|
| **훈련창 `/play`** | **고정 스테이지 + contain 스케일**<br>가로 `2560×1440`(16:9) · 세로 `1440×2560`(9:16) 두 벌 | 상황판은 **공간 구성 자체가 정보**다. 리플로우로 재배치되면 훈련이 성립하지 않는다. 스테이지는 구성을 **수학적으로 보장**한다 |
| **설정모드 `/settings`** | **리플로우(브레이크포인트) 3단** | 폼·표 화면이다. 레터박스로 화면을 버리는 건 손해. 넓으면 넓게 쓴다 |

같은 앱에서 두 화면이 다른 전략을 쓰는 것이 맞다. **한쪽은 구성을 지켜야 하고, 다른 쪽은 공간을 써야 한다.**

## 1. 진단 — 왜 지금 무너지는가

### 1.1 결함 A: 글꼴 하한과 기하 하한이 **의도적으로 어긋나 있다**

`useUiScale.ts`(**삭제됨** — 이 문서 §2.1 이 그 근거다)의 두 하한이었다:

```
UI_SCALE_MIN   = 0.50   ← 기하(패딩·아이콘·px 토큰)
FONT_SCALE_MIN = 0.78   ← 글꼴
```

`raw = min(w/2560, h/1364)`가 **0.78 아래로 내려가는 순간 둘이 갈라진다.**

| 뷰포트 | raw | 기하 | 글꼴 | 글자/상자 비 |
|---|---:|---:|---:|---:|
| 2560×1404 | 1.03 | 1.03 | 1.03 | 1.00 |
| 1920×1044 | 0.75 | 0.75 | **0.78** | **1.04** |
| 1366×732 | 0.53 | 0.53 | **0.78** | **1.47** |
| 1280×764 | 0.50 | 0.50 | **0.78** | **1.56** |

1280×764에서 **글자는 상자보다 1.56배 크다.** 넘치고, 줄바꿈되고, 잘린다.

코드 주석은 이걸 알고 있다 — *"작은 화면일수록 글자가 상대적으로 커지는데, 이게 의도한 절충이다."* 의도는 옳다(작은 화면에서 글자가 5px가 되면 안 된다). **그러나 두 배수를 갈라 놓은 것이 대가였다.** 스테이지에서는 배수가 하나뿐이라 이 분기 자체가 사라진다 — 작은 화면에서 글자가 작아지는 문제는 남지만, 적어도 **레이아웃이 무너지지는 않는다**(§3.1).

### 1.2 결함 B: `TacticalArea`가 최초 1회만 측정하고, 그 px를 저장한다

[`TacticalArea.tsx:65`](../src/components/building/TacticalArea.tsx:65):

```ts
useLayoutEffect(() => {
  const totalH = el.clientHeight;
  ...
  setBuildingHeight(saved > 0 ? clamp(saved) : naturalBuildingH);
}, []);          // ← 의존성 배열이 비어 있다
```

세 가지 결과가 따라온다.

1. **창 크기를 바꿔도 건물 행 높이가 재계산되지 않는다.** 나머지가 배율을 따라 줄어드는 동안 건물만 최초 px에 고정된다. 이것 하나만으로 화면이 무너진다.
2. **`localStorage`에 px를 저장한다**(`tacticalBoardBuildingHeight`). 노트북에서 조정한 높이가 훈련장 2560px PC에 그대로 적용된다. **기기를 넘나드는 px는 오염이다.**
3. `140px`(C면), `A_FACE_MIN_HEIGHT = 200`은 `--ui-scale` 환산 없는 상수다.

CLAUDE.md가 경고하는 *"구역 높이가 0으로 보이면 이걸 먼저 의심한다"*와 같은 뿌리다.

### 1.3 결함 C: 열 너비와 열 내용이 다른 자를 쓴다

```css
.play-layout {
  --op-panel-w:        clamp(300px, 21.5%, 620px);   /* 뷰포트 폭의 % */
  --procedure-panel-w: clamp(200px, 12%,  340px);
}
```

열 **너비**는 뷰포트 폭 비례, 열 **내용**은 `min(w/W, h/H)` 비례다. 화면이 세로로 길어지면(태블릿 세로) 폭은 그대로인데 내용만 작아지고, 가로로 길어지면 반대가 된다. **두 축이 독립적으로 움직인다.**

### 1.4 종합 — 종횡비가 감당해야 하는 범위

| 기기 | CSS 뷰포트 | 종횡비 |
|---|---|---:|
| 갤럭시탭 S9 세로 | 800×1244 | **0.64** |
| iPad 11 세로 | 834×1158 | 0.72 |
| iPad Pro 12.9 세로 | 1024×1330 | 0.77 |
| iPad Pro 12.9 가로 | 1366×988 | 1.38 |
| iPad 11 가로 | 1194×798 | 1.50 |
| 갤럭시탭 S9 가로 | 1280×764 | 1.68 |
| 노트북 FHD | 1920×1044 | 1.84 |
| **훈련장 PC** | **2560×1404** | **1.82** |

**0.64 ~ 1.84 — 2.9배 범위다.** 하나의 구성으로 덮을 수 없다. 사용자가 말한 "가로 기본 / 세로 기본 두 벌"이 정확한 판단이다.

## 2. 방향 선택 — 세 가지 안

| | **A. 지금 방식 보수** | **B. 완전 리플로우** | **C. 고정 스테이지 + contain** |
|---|---|---|---|
| 방법 | px 1,157개를 rem/`--ui-scale`로 환산 | 브레이크포인트마다 배치를 다시 짬 | 논리 캔버스에 그리고 `transform: scale()` 한 번 |
| 구성 보장 | ❌ 환산 누락 하나면 다시 어긋남 | ❌ 배치가 화면마다 달라짐 | ✅ **수학적으로 보장** |
| 작업량 | 1,157곳 수정 + 영구 감시 | 구성 2~4벌 재설계 | 셸 교체 + 좌표계 감사 |
| 종횡비 대응 | 나쁨 | 좋음 | 레터박스로 흡수 |
| 화면 활용 | 100% | 100% | 레터박스만큼 손해 |
| 글자 크기 | 화면따라 제각각 | 화면따라 제각각 | **배율 하나로 예측 가능** |
| 재발 위험 | **높음** — 새 px 하나면 원상복귀 | 중간 | **낮음** — 스테이지 밖에 치수가 없음 |

**C를 권장한다.** 근거는 세 가지다.

1. **상황판은 지도다.** B면·건물·D면·A면의 상대 위치와 크기가 훈련 정보 그 자체다. 리플로우로 D면이 아래로 내려가면 다른 화면이 된다.
2. **A는 이미 시도했고 3년째 안 끝났다.** `--ui-scale` 도입 후에도 원시 px가 1,157개다. 재발을 막는 구조가 아니라 규율에 의존하는 방식이기 때문이다.
3. **C는 규율이 필요 없다.** 캔버스가 고정이므로 px로 그려도 된다 — 오히려 px가 정답이 된다. 지금 있는 1,157개의 px가 **부채에서 자산으로 바뀐다.**

### 2.1 "치수를 CSS 파일 한 곳에 모으면 되지 않나" — 맞다, 그리고 부족하다 ★

사용자가 제기한 방향이다. **진단이 정확하다.** 다만 실행에는 두 겹이 있고, 한 겹만 하면 안 된다.

문제는 사실 **두 개**다.

| | 문제 | 한 파일로 모으면 |
|---|---|---|
| **(a) 흩어짐** | 같은 성격의 값이 47개 파일에 1,157개로 흩어져 있다 | ✅ **해결된다** |
| **(b) 갈라짐** | 값들이 **서로 다른 배수**를 따른다 (px 0배 / rem 0.78하한 / ui-scale 0.50하한 / % 컨테이너) | ❌ **해결 안 된다** |

**(b)가 화면을 무너뜨리는 쪽이다.** 파일 하나에 모아도 그 안에서 어떤 건 `px`, 어떤 건 `rem`, 어떤 건 `%`면 배율을 바꿀 때 여전히 따로 논다. 위치만 한 곳으로 옮긴 것이다.

**따라서 조건은 "한 파일"이 아니라 "하나의 배수"다.**

```css
/* 안 D — 단일 토큰 파일 + 단일 배율 변수 */
:root { --s: 0.8; }                                  /* JS가 min(w/W,h/H) 로 계산 */
.token      { width: calc(120px * var(--s)); }
.token__name{ font-size: calc(13px * var(--s)); }    /* 글꼴도 같은 --s. 하한 예외 없음 */
```

이 방식(**안 D**)은 실제로 성립한다. 스테이지와 비교하면:

| | **안 D — 단일 배율 변수** | **안 C — 스테이지** |
|---|---|---|
| 배수 개수 | 1 (`--s`) | 1 (transform scale) |
| 배수를 적용하는 곳 | CSS 선언 **1,157곳** | **루트 1곳** (브라우저 합성 단계) |
| 기존 px 처리 | **전부 `calc()`로 변환해야 함** | **그대로 두면 됨** |
| 새 px 유입 시 | 재발한다 (`calc` 안 쓰면 끝) | 재발 불가 (캔버스가 고정) |
| 서브픽셀 | 요소마다 독립 반올림 → 1px 어긋남 누적 | 합성 단계 일괄 → **누적 없음** |
| 포털·`offsetWidth` | 영향 없음 ✅ | **감사 필요** (§4) |
| 종횡비 남는 공간 | 처리 규칙을 또 만들어야 함 | 레터박스로 자동 흡수 |
| 글자 렌더링 | 선명 | 비정수 배율에서 재래스터화 |

**결론 — 스테이지는 사용자 아이디어의 극한값이다.**

"한 곳에서 조정한다"를 끝까지 밀면, 조정 지점이 CSS 파일 하나도 아니고 **숫자 하나**(`scale`)로 줄어든다. 그리고 그 지점에서 **1,157개의 px를 고칠 필요가 사라진다** — 캔버스가 안 변하므로 px가 이미 정답이기 때문이다. 안 D가 요구하는 가장 큰 작업량이 통째로 없어진다.

**다만 토큰 파일은 그래도 만든다. 역할이 달라질 뿐이다.**

```
토큰 파일  →  일관성(디자인 시스템) 담당.  "칩 높이는 24px, 본문은 13px"
스테이지   →  배율 담당.                    "이 화면에서는 전부 ×0.83"
```

지금은 이 둘이 뒤엉켜 있다. **분리하는 것이 핵심이다.** 토큰 파일이 배율까지 책임지려 하면(=`calc(var(--s))`) 다시 규율에 의존하게 되고, 규율은 3년간 지켜지지 않았다.

> `zoom` 속성으로 같은 걸 할 수도 있다. 쓰지 않는 이유는 §3.3에 적었다 — 레이아웃을 재계산해서 반올림이 층마다 누적되고 브라우저 편차가 있다.

## 3. 권장안 — 고정 스테이지

### 3.1 캔버스 크기 결정 — **단위 선택일 뿐이다** (2026-08-22 정정)

> ⚠ **이 절의 초판은 틀렸다.** "캔버스를 작게 잡으면 태블릿에서 글자가 커진다"고
> 썼지만, 균일 배율에서는 **캔버스 크기가 표시 크기에 아무 영향을 주지 않는다.**

**증명**

캔버스 `W×H`, 논리값 `v`, 배율 `s = min(vw/W, vh/H)` → 표시 크기 `v·s`.
캔버스를 `c` 배로 키우고 값도 `c` 배로 환산하면:

```
s' = min(vw/cW, vh/cH) = s/c
표시 = v'·s' = (c·v)·(s/c) = v·s     ← 원래와 동일
```

실제로 대입해도 같다 (iPad 11 가로 1194×798, 논리 본문 13px 상당):

| 캔버스 | 논리값 | 표시 |
|---|---:|---:|
| 1440×810 | 13.00px | **10.78px** |
| 1920×1080 | 17.33px | **10.78px** |
| 2560×1440 | 23.11px | **10.78px** |

초판의 표는 캔버스만 바꾸고 **값은 15px로 고정**해서 비교했다. 그건 캔버스
선택의 효과가 아니라 **디자인을 성기게 다시 그린 효과**다. 태블릿에서 글자를
키우려면 캔버스가 아니라 **글자를 레이아웃 대비 크게** 그려야 하고, 그건
훈련장 PC 에서 글자가 커지는 대가를 치른다 — 별개의 디자인 결정이다.

**따라서 캔버스를 고르는 기준은 하나뿐이다: 환산 작업이 가장 적은 크기.**

| 캔버스 | 훈련장 PC 배율 | 기존 px 환산 |
|---|---:|---|
| 1440×810 | 1.733 | 전량 ×0.577 필요 (1,157곳) |
| 1920×1080 | 1.300 | 전량 ×0.769 필요 |
| **2560×1440** | **0.975** | **불필요 — 그대로 쓴다** |

> **가로 캔버스 `2560×1440` (16:9) · 세로 캔버스 `1440×2560` (9:16)**
>
> 훈련장 PC 훈련영역이 2560×1404 라 배율이 0.975 로 거의 1:1 이 되고,
> 지금 코드의 px 1,157개가 **환산 없이 그대로 정답이 된다.** 초판이 T-5 의
> 가장 큰 작업으로 잡았던 "치수 전량 환산"이 통째로 사라진다.

**태블릿 글자 크기는 별도 문제로 남는다.** 캔버스와 무관하게, iPad 11 가로에서
본문은 약 9px 로 표시된다. 태블릿이 **보는 용도**(무전플레이어 화면 모니터링)
라는 전제에서는 수용 가능하며, 필요하면 브라우저 확대로 보완한다. 조작까지
해야 한다면 그때는 "글자를 레이아웃 대비 키우는" 별도 디자인 과제가 된다.

### 3.2 이 결정이 만드는 저작 규칙

캔버스가 고정되면 **규칙이 단순해진다.** 이게 C안의 진짜 이익이다.

```
1. 스테이지 안에서는 px로 그린다.        ← rem·%·vh·clamp 금지
2. 논리 최소 글자 = 12px.                 ← 훈련장 PC 배율 0.975 기준
3. 논리 최소 클릭 타깃 = 32px.
4. --ui-scale, --font-scale, useUiScale 은 삭제한다.
5. 캔버스 밖 치수는 존재하지 않는다.
```

4번이 핵심이다. **배율 변수를 없애는 것이 이 계획의 목표다.** 배율 변수가 있는 한 "따르는 것"과 "안 따르는 것"이 갈리고, 갈리면 무너진다.

### 3.3 구현 골격

```tsx

const PORTRAIT  = { w: 1440, h: 2560 };

function StageRoot({ children }) {
  const hostRef = useRef<HTMLDivElement>(null);
  const [box, setBox] = useState({ w: 0, h: 0 });

  useLayoutEffect(() => {
    const el = hostRef.current!;
    const ro = new ResizeObserver(([e]) => {
      const { width, height } = e.contentRect;
      if (width > 0 && height > 0) setBox({ w: width, h: height });  // 0 측정 무시
    });
    ro.observe(el);
    return () => ro.disconnect();
  }, []);

  const canvas = box.w >= box.h ? LANDSCAPE : PORTRAIT;   // §3.8 전환 규칙
  const scale  = Math.min(box.w / canvas.w, box.h / canvas.h) || 1;

  return (
    <div ref={hostRef} className="stage-host">
      <div
        className="stage"
        style={{
          width:  canvas.w,
          height: canvas.h,
          transform: `translate(-50%, -50%) scale(${scale})`,
        }}
      >
        {children}
      </div>
    </div>
  );
}
```

```css
.stage-host {                     /* 레터박스 바탕 */
  position: relative;
  width: 100%; height: 100%;
  overflow: hidden;
  background: var(--color-bg);
}
.stage {
  position: absolute;
  top: 50%; left: 50%;
  transform-origin: center center;
  will-change: transform;
}
```

**`transform: scale()`을 쓰는 이유** — `zoom`은 레이아웃을 다시 계산해서 서브픽셀 반올림이 층마다 누적되고, 브라우저마다 다르다. `transform`은 합성 단계에서 처리돼 GPU가 하며 **구성이 절대 어긋나지 않는다.**

### 3.4 상황판은 **정사각 1440×1440**으로 고정한다 ★

가로·세로 두 구성을 관통하는 단 하나의 결정이다. 이것이 정해지면 나머지가 따라 나온다.

**현재는 4:3이고, 그 때문에 화면을 버리고 있다.**

[`PlayPage.css:292`](../src/pages/PlayPage.css:292)의 `.tactical-board-inner { aspect-ratio: 4/3; height: 100%; }`를 실측 대입하면:

| | 값 |
|---|---|
| 훈련장 PC 뷰포트 | 2560×1404 |
| 운영 패널 / 지휘절차 | 550 / 307 |
| 보드에 주어진 영역 | **1702×1404** |
| 4:3로 실제 그려지는 보드 | **1702×1277** |
| **버려지는 세로 여유** | **127px** |

폭에 묶여 높이를 다 못 쓴다. [반응형 계획 §0.2](RESPONSIVE_16_9_TABLET_LAYOUT_PLAN.md)가 *"회수한 폭이 현재 좌측 여백이 된다"*고 기록한 그 문제다.

**정사각으로 바꾸면 두 가지를 동시에 회수한다.**

│  │임시의료소│카테고리 │  │   └──────── A면 ─────────┘   │

| | 현재(환산) | 정사각 | 증감 |
|---|---:|---:|---|
| 보드 | 1703×1277 | **1440×1440** | 높이 +13%, 세로 여유 0 |
| 운영 패널 | 550 | **719** | **+31%** |

**보드가 폭 263px을 내주고 높이 163px을 얻는다.** 건물 입면은 원래 세로로 긴 정보이므로 이 교환은 이득이고, 내준 폭은 그동안 좁다고 했던 두 패널에 그대로 간다.

> 배치는 현재 관례를 따른다 — 패널 대역이 좌측, 보드가 우측. `justify-content: flex-end`로 D면을 지휘절차 쪽에 붙여 온 의도와 같다.

### 3.5 세로 구성 (1440×2560) — 캔버스를 **전치**한다

사용자 제안 그대로다: **좌우 패널을 아래로 내린다.** 계산해보니 이게 우연히 잘 맞는 정도가 아니라 **구조적으로 정확하다.**

```
캔버스 1440×2560
┌────────────────────────────┐
│   ┌──────── C면 ───────┐   │
│   │  B면 │ 건물 │ D면  │   │  810   ← 가로와 완전히 동일한 정사각 보드
│   └──────── A면 ───────┘   │
├──────────────┬─────────────┤
│  운영 924    │ 지휘절차 516│ 1120   ← 가로와 완전히 동일한 1120px 대역
│ 임시의료소   │  카테고리   │
│ 출동대현황   │   ├ 항목    │
│ 자원대기소   │   └ 항목    │
│ 대기1단계    │             │
└──────────────┴─────────────┘
```

**두 구성이 같은 부품 두 개를 90° 돌려 쓴다.**

| 부품 | 가로 2560×1440 | 세로 1440×2560 |
|---|---|---|
| 정사각 보드 | 1440×1440 (우) | 1440×1440 (상) |
| 패널 대역 | **1120**×1440 (좌) | 1440×**1120** (하) |
| 운영 : 지휘절차 | 719 : 401 | 924 : 516 |

캔버스가 서로 전치(2560×1440 ↔ 1440×2560)이고 보드가 정사각이므로, 남는 대역이 **양쪽 모두 정확히 1120px**이 된다. 우연이 아니라 산술적 필연이다.

**따라서 세로 구성에서 새로 만들 것은 딱 하나다** — 패널 두 개의 **내부 배치**. 운영 패널이 `719×1440`(세로로 긴 1열)에서 `924×1120`(가로로 넓은 상자)이 되므로 5개 섹션을 **2열 그리드**로 접는다. 면적은 오히려 늘어난다.

보드·좌표계·드래그·토큰은 **가로와 100% 동일**하다. 이것이 T-6의 규모를 크게 줄인다 — 애초 예상 L에서 **M**으로 내려간다.

### 3.6 판 안의 고정 px를 캔버스 단위로 환산해야 한다 ⚠

정사각 전환에서 **반드시 같이 해야 하는 작업**이다. 빠뜨리면 구성이 지금보다 나빠진다.

[`TacticalArea.css`](../src/components/building/TacticalArea.css)와 [`ZoneCell.css`](../src/components/building/ZoneCell.css)는 **2560 화면의 실제 px**로 쓰여 있다.

```css
.tactical-area { grid-template-rows: 140px 1fr 200px; }   /* C면 / 중앙 / A면 */
/* ZoneCell.css */  flex: 0 0 110px;   /* 계단실   */
                    flex: 0 0  88px;   /* 화재표현 */
/* FloorRow.css */   width: 34px;      /* 층라벨   */
```

TacticalArea.css의 주석이 스스로 위험을 적어 두었다.

> ※ 계단실 110px·화재표현 88px은 ZoneCell.css에 px로 고정되어 있어 **컬럼 비율과 무관하게 항상 그대로 유지됨.**

이 232px(34+110+88)은 보드 폭이 1702일 때 **13.6%**지만, 보드가 좁아져도 줄지 않는다. 1280 화면에서는 같은 232px이 보드의 **28%**를 먹는다. **§1의 "각각 따로 축소확대"가 보드 내부에서 한 번 더 일어나고 있는 것이다.**

**환산 계수**

| 대상 | 계수 | 근거 |
|---|---:|---|
| 판 밖 (패널·간격) | **환산 불필요** | 캔버스가 2560 이라 기존 px 가 그대로 맞다 |
| **판 안** (보드 내부 전부) | **×0.8456** | 정사각 1440 / 현재 보드 폭 1703 |

| 값 | 현재 | 환산 | 채택 |
|---|---:|---:|---:|
| C면 행 높이 | 140px | 118.4 | **118px** |
| A면 행 높이 | 200px | 169.1 | **169px** |

환산 후 고정부는 보드 폭의 **13.7%**로 고정되고, **모든 해상도에서 13.7%를 유지한다.** 이게 스테이지가 주는 것이다.

### 3.7 B : 건물 : D 비율을 설정값으로 뺀다

사용자 제안이다. 정사각 결정과 맞물려 **지금이 넣기 가장 좋은 시점**이다.

이미 단일 숫자로 존재한다 — [`TacticalArea.css:31`](../src/components/building/TacticalArea.css:31):

```css
grid-template-columns: 1fr 1.744fr 1fr;
```

`1.744`는 2560 화면 실측에서 나온 상수다. 보드가 정사각으로 고정되면 이 비율은 **순수한 취향·시나리오 변수**가 된다 — 화면 크기와 무관해진다. 설정으로 빼기에 딱 맞는 조건이다.

**캔버스 1432px(보드 내부 = 1440 − padding 4px×2) 기준 비율별 결과**

| N (B:건물:D = 1:N:1) | B면 | 건물 | D면 | 건물 가변부 |
|---:|---:|---:|---:|---:|
| 1.00 | 477 | 477 | 477 | 281 |
| 1.40 | 421 | 590 | 421 | 394 |
| **1.744 (현재)** | **382** | **667** | **382** | **471** |
| 2.00 | 358 | 716 | 358 | 520 |
| 2.50 | 318 | 796 | 318 | 600 |
| 3.00 | 286 | 859 | 286 | 663 |

**슬라이더 범위는 `1.0 ~ 3.0`, 기본 `1.744`를 권장한다.**

- **하한 1.0**: B/D면이 건물보다 넓어질 이유가 없다. (산술 하한은 약 0.63 — 그 아래에서 건물 가변부가 0이 된다)
- **상한 3.0**: B면 286px에서 출동대 토큰 1열이 여유 있게 들어간다. **상한은 취향이 아니라 "토큰 1열이 들어가는 폭"으로 정한다.**

**구현**

| 항목 | 내용 |
|---|---|
| 설정 위치 | 「건물 · 소방시설」 화면의 "상황판 구역 비율" 카드 (2026-08-24 탭 통합으로 하위 탭 없이 한 화면) |
| UI | 슬라이더 1개 + 비율 미리보기 바 (`B ▏████ 건물 ████▕ D`) + 숫자 표시 |
| 저장 | `SettingsExport`에 `boardColumnRatio?: number` 추가. **선택 필드로 두고 없으면 1.744** — 기존 저장 파일이 안 깨진다 |
| 적용 | `.tactical-area`에 `style={{ '--board-col-ratio': N }}`, CSS는 `grid-template-columns: 1fr var(--board-col-ratio, 1.744)fr 1fr` |
| 반영 시점 | **`훈련 세팅` 버튼** — [MASTER_PLAN.md](MASTER_PLAN.md) D-6 M-1을 따른다. 훈련 중에는 안 바뀐다 |

> ⚠ **좌표 영향 확인 필요.** 출동대·구조대상자는 **구역 대비** 0~1로 저장된다(CLAUDE.md). B면 폭이 바뀌어도 *구역 안에서의 상대 위치*는 보존되므로 안전하다. 다만 **이벤트 토큰은 보드 대비**로 저장되므로, 비율을 바꾸면 이벤트 토큰이 다른 구역 위로 옮겨 갈 수 있다. 훈련 세팅 시점에만 바뀌므로 실무상 문제는 없지만, **§8 Q-7로 확인이 필요하다.**

> 대칭(`1:N:1`)만 지원한다. B면·D면을 따로 조절하는 비대칭은 슬라이더가 2개가 되고 얻는 것이 불분명하다 — 필요해지면 그때 연다.

### 3.8 가로/세로 전환 규칙

`window.orientation`이 아니라 **컨테이너 종횡비**로 판단한다. 데스크톱에서 창을 세로로 좁혀도 동작해야 하고, 태블릿 분할화면도 잡아야 한다.

```
aspect = box.w / box.h

aspect ≥ 1.15  →  가로 구성 (1440×810)
aspect ≤ 0.87  →  세로 구성 (810×1440)
그 사이         →  직전 구성 유지 (히스테리시스)
```

**히스테리시스가 필요한 이유**: 경계값 하나로 자르면 1.0 근처에서 창을 조금만 흔들어도 구성이 왕복한다. 훈련 중 이런 깜빡임은 치명적이다. 0.87~1.15 구간에서는 **이전 구성을 유지**하고, 사용자가 명시적으로 바꿀 수 있게 상단에 전환 버튼을 둔다.

### 3.9 태블릿 종횡비 — 레터박스를 감추는 법

`1440×810`(1.78)과 iPad Pro(1.38)는 안 맞는다. 레터박스 22.2%가 위아래로 생긴다.

세 가지 처리 방식:

| 방식 | 내용 | 판정 |
|---|---|---|
| **그대로 둔다** | 위아래 검은 띠 | ❌ 22%는 눈에 띈다 |
| **`--stage-bleed` 확장** | 스테이지 배경만 뷰포트 전체로 넓히고 콘텐츠는 캔버스 안에 | ✅ **권장** |
| 캔버스를 기기별로 | iPad용 4:3 캔버스를 따로 | ❌ 구성이 3벌이 된다 |

**권장 처리**: 스테이지의 **배경·테두리만** 뷰포트를 채우고, 그 위에 캔버스를 얹는다. 남는 띠는 "검은 여백"이 아니라 **상황판 바탕의 연장**으로 보인다. 훈련 정보는 캔버스 안에만 있으므로 어디서 보든 동일하다.

띠가 넉넉할 때(≥120px 실효) 선택적으로 **부가 정보 슬롯**을 넣을 수 있다 — 훈련 경과 시간, 대상명 등. 다만 **캔버스 안 정보와 중복되지 않는 것만.** 이건 2차 과제로 남긴다.

### 3.10 보드 크기를 가변으로 — 가변 캔버스 + 드래그 조절 (통합 검토, 구현 보류)

두 요청을 하나로 묶는다. **둘 다 "보드 크기는 더 이상 고정이 아니다"라는 같은 전제를 만들기 때문**에 따로 하면 두 번 고치게 된다.

- (1) 남는 폭을 상황판이 쓰게 한다 — 레터박스 제거
- (2) 가로는 좌/우 패널 폭, 세로는 보드↔대역 높이를 드래그로 조절

#### 3.10.1 제1원칙 — **꼬이지 않는 것이 기능보다 먼저다** ★

> 드래그 조절 때문에 오류가 나거나 상황판이 꼬이는 상황이 발생해서는 안 된다.

이 원칙이 아래 설계 전부를 결정한다. 편의를 위해 안전을 양보하지 않는다. 구체적 규칙으로 옮기면:

| # | 규칙 | 근거 |
|---|---|---|
| **R1** | **드래그가 바꾸는 값은 언제나 1개.** 나머지는 전부 계산으로 나온다(저장하지 않는다) | 저장값 2개가 서로 어긋날 경로 자체를 없앤다 |
| **R2** | 저장값은 **읽을 때마다 클램프**한다 | 손상된 값·구버전 값·다른 기기 값 어느 것도 범위 밖으로 나올 수 없다 |
| **R3** | 클램프 범위는 **콘텐츠 최소치에서 유도**해 상수로 박는다 | "왜 이 숫자냐"가 코드에 남는다 |
| **R4** | 저장 단위는 **캔버스 px**(고정 높이 1440 기준). ~~px~~·~~뷰포트 비율~~ 금지 | §1.2에서 겪은 기기 간 오염 재발 방지 |
| **R5** | 다른 모드(그리기·방수지점·전개지점) 중에는 **핸들 비활성**, 드래그 중에는 **모드 진입 차단** | 상호작용 충돌 제거 |
| **R6** | 포인터 캡처 + `pointercancel`·`lostpointercapture` 처리 | 창 밖으로 나가도 드래그 상태가 남지 않는다 |
| **R7** | 저장은 **놓을 때 1회**. 드래그 중에는 메모리만 | 중간 상태가 디스크에 남지 않는다 |
| **R8** | **더블클릭 → 기본값 복귀** | 어떤 상태에서도 알려진 좋은 상태로 돌아올 길이 있다 |
| **R9** | 드래그 시작 **임계값 4px** | 클릭을 드래그로 오인하지 않는다 |

**가장 큰 안전판은 이미 확보돼 있다** — 좌표가 전부 정규화(0~1)라 보드가 커지든 작아지든 **토큰이 움직이거나 사라질 경로가 없다.**

| 대상 | 기준 | 리사이즈 영향 |
|---|---|---|
| 출동대·구조대상자 | 구역 대비 0~1 | 없음 |
| 이벤트 토큰 | 보드 대비 0~1 | 없음 |
| 그리기 획 | `.drawing-board__input`(=보드) 대비 0~1 | 없음 |
| 송수·방수·전개 오버레이 | 매 프레임 `getBoundingClientRect` 재계산 | 없음 |
| B : 건물 : D | `fr` 비율 | 없음 |

#### 3.10.2 가변 캔버스 — 레터박스가 **구조적으로** 0이 된다

캔버스 **높이는 1440 고정**, **폭만 화면 종횡비에서 역산**한다.

```
canvasW = 1440 × (훈련영역 종횡비)
배율    = 훈련영역높이 / 1440
```

이러면 `hostW/canvasW` 와 `hostH/1440` 이 **항상 정확히 같아져** `min()` 이 무의미해지고 여백이 0이 된다. 검산:

```
전체보기 1920×1080 → min(0.725000, 0.725000) = 0.725000 → 그린폭 1920.0 = 훈련영역 1920 ✓
훈련장 PC          → min(0.975000, 0.975000) = 0.975000 → 그린폭 2560.0 = 훈련영역 2560 ✓
```

| 기기 | 지금 좌우여백 | 가변 후 | 보드 폭 |
|---|---:|---:|---:|
| 현재 창(1920×958) | **140px** | **0** | 1879 |
| 전체보기 1920×1080 | 32px | **0** | 1528 |
| 훈련장 PC | 32px | **0** | 1506 |
| 울트라와이드 3440 | 472px | **0** | 2408 |
| iPad Pro 가로 | 0 (상하 219) | **0** | 871 |

**넓어진 폭은 전부 "토큰 놓는 자리"로 간다.** 건물 열의 고정부(계단실 93 + 화재표현 74 + 층라벨 29 = 196)는 그대로다.

| 기기 | 보드 | B면 | 건물 가변구역 | D면 |
|---|---:|---:|---:|---:|
| 지금(고정) | 1440 | 382 | 471 | 382 |
| 훈련장 PC | 1506 | 400 | **502** | 400 |
| 울트라와이드 | 2408 | 641 | **922** | 641 |

#### 3.10.3 통합 모델 — **드래그는 패널을 정하고, 보드는 남는 것을 먹는다**

두 요청을 합치면 규칙이 하나로 떨어진다. R1(변수 1개)을 만족한다.

| | 고정 | **드래그 변수 (저장)** | 계산으로 나오는 값 |
|---|---|---|---|
| **가로** | 캔버스 높이 1440<br>`canvasW` = 종횡비에서 역산 | `opW` (캔버스 px) | `procW` = 상수<br>`boardW` = `canvasW − opW − procW` |
| **세로** | 캔버스 폭 1440<br>`canvasH` = 종횡비에서 역산 | `bandH` (캔버스 px) | `boardH` = `canvasH − bandH` |

**보드가 언제나 흡수자(absorber)다.** 패널은 내용에 맞춰 설계된 크기를 유지하고, 화면이 넓든 좁든 남거나 모자란 만큼은 보드가 받는다. 이게 §3.10.1 R1을 자연스럽게 만족시킨다 — 저장값이 하나뿐이고 나머지는 전부 뺄셈이다.

> 가로에서 "좌측을 줄이면 우측이 늘어난다"는 요청은 **가변 캔버스에서 의미가 바뀐다.** 보드가 흡수자이므로 좌측을 줄이면 **보드가 넓어진다.** 우측(지휘절차)까지 같이 조절하고 싶으면 `procW` 도 두 번째 드래그 변수로 두면 되는데, **R1을 깨므로 권하지 않는다.** 필요하면 지휘절차 폭은 설정값(§3.7의 `boardColumnRatio` 처럼)으로 빼는 편이 안전하다.

#### 3.10.4 ⚠ 반드시 같이 고쳐야 하는 것 — `BOARD_INNER_H` 상수

[`TacticalArea.tsx`](../src/components/building/TacticalArea.tsx) 에 이런 상수가 있다.

```ts
const BOARD_INNER_H      = 1432;   // 정사각 보드 1440 − padding 8 을 가정
const NATURAL_BUILDING_H = BOARD_INNER_H - C_FACE_HEIGHT - A_FACE_MIN_HEIGHT;
```

`NATURAL_BUILDING_H` 는 **기존 건물↔A면 높이 비율의 클램프 기준**이다(`BUILDING_MIN_RATIO 0.6` ~ `MAX 1.4`).

세로에서 보드 높이가 가변이 되면 **이 상수가 거짓이 된다.** 그대로 두면 건물 높이 클램프가 엉뚱한 범위로 잡혀 — 정확히 사용자가 우려한 — **상황판이 꼬인다.**

→ `BOARD_INNER_H` 를 상수에서 **현재 보드 높이에서 파생되는 값**으로 바꿔야 한다. 가로에서는 여전히 1432이므로 가로만 쓰는 동안에는 표면화되지 않는다. **세로 드래그를 구현하는 커밋에서 반드시 함께 처리한다.**

#### 3.10.6 잃는 것 — 정직하게

**"구성이 모든 해상도에서 동일하다"는 보장이 사라진다.** §2·§3에서 스테이지를 고른 이유가 그것이었다. 다만 무엇이 깨지고 무엇이 남는지는 구분해야 한다.

| | 상태 |
|---|---|
| 배수가 **하나뿐**이라 글자·기하·px 가 갈라지지 않는다 | ✅ **유지** — §1의 병은 돌아오지 않는다 |

## 4. 스테이지 도입의 실제 비용 — 반드시 먼저 볼 것

`transform: scale()`은 좌표계를 바꾼다. 코드에 **좌표를 직접 다루는 곳**이 이미 많고, 그중 일부가 깨진다. 실측했다.

### 4.1 ⚠ `createPortal` — 가장 큰 비용

**10개 컴포넌트가 `document.body`로 포털한다.**

```
ChecklistPanel · UnitAddPanel · TokenCard · VictimCard · UnitStatusBarMenu
TokenContextMenu · BadgeManagerModal · VictimContextMenu · RadialMenu · VictimContextBarMenu
```

`document.body`는 **스테이지 밖**이다. 상황판이 0.8배로 줄어도 컨텍스트 메뉴는 1.0배로 뜬다. 크기도 위치도 어긋난다.

**대응**: 포털 대상을 `document.body` → **스테이지 엘리먼트**로 바꾼다. 컨텍스트를 하나 둔다.

```tsx
const StagePortalContext = createContext<HTMLElement | null>(null);
// 사용처: createPortal(node, useContext(StagePortalContext) ?? document.body)
```

부수 효과 하나가 **이득**이다 — `transform`이 걸린 조상 아래에서는 `position: fixed`가 **그 조상 기준**으로 해석된다. 스테이지 안 16개 CSS 파일의 `position: fixed`가 자동으로 "스테이지 기준"이 되어, 메뉴가 캔버스를 벗어나지 않는다. 지금은 뷰포트 기준이라 큰 화면에서 엉뚱한 데 뜬다.

### 4.2 ⚠ `offsetWidth` / `offsetHeight` — 좌표계 혼용

**12곳**에서 쓴다. `offsetWidth`는 **변환 전** 레이아웃 px이고, `getBoundingClientRect()`는 **변환 후** 화면 px이다. 지금은 배율이 1이라 같지만, 스테이지를 도입하면 갈라진다.

가장 명확한 사례 — 드롭 좌표:

```ts
// dragDrop.ts:14      변환 후 공간
e.dataTransfer.setData('grabOffsetX', String(e.clientX - rect.left));
// TokenCard.tsx:135   변환 전 공간   ← 섞였다
e.dataTransfer.setData('tokenW', String(el.offsetWidth));
```

`computeDropCenter`가 이 둘을 더한다([dragDrop.ts:44](../src/utils/dragDrop.ts:44)). 배율 0.8에서 40px 토큰이면 약 4px 오차가 **항상 같은 방향으로** 생긴다.

나머지 8곳은 컨텍스트 메뉴의 화면 경계 뒤집기(`menuW`, `menuH`)다 — 메뉴가 잘못된 쪽으로 뒤집힌다.

**대응**: 12곳 전부 `getBoundingClientRect()`로 통일. 기계적이고 위험이 낮다.

### 4.3 좌표 정규화는 **이미 안전하다** — 이 계획의 최대 자산

CLAUDE.md의 원칙이 여기서 값을 한다.

> 출동대·구조대상자는 **구역 대비**, 이벤트 토큰은 **보드 대비** 0~1로 저장한다.

정규화 좌표는 **배율과 무관하다.** `(clientX - rect.left) / rect.width`는 `rect`가 변환 후 값이면 분자·분모가 같이 스케일되어 비율이 보존된다. **저장된 모든 배치 데이터가 스테이지 도입 후에도 그대로 유효하다.** 데이터 마이그레이션이 0건이다.

Phase 4(좌표 정규화)를 먼저 끝내 둔 것이 이 전환을 가능하게 한다.

## 5. 설정모드는 스테이지를 쓰지 않는다

사용자 요청의 앞부분(설정모드 UI 개선)에 대한 답이다.

**이유**: 설정모드는 폼과 표다. 고정 캔버스에 넣으면 2560px 화면에서 레터박스로 화면을 버리고, 표는 좁아진다. 저작 화면은 **넓으면 넓게 써야 한다.**

[SETTINGS_MODE_UI_PLAN.md](SETTINGS_MODE_UI_PLAN.md)의 3단 브레이크포인트를 유지하되, **태블릿 대응을 추가**한다.

| 폭 | 사이드바 | 본문 | 보조 열 | 대상 |
|---|---|---|---|---|
| < 900px | **상단 드롭다운으로 접힘** | 100% | 없음 | 태블릿 세로 (800~834px) |
| 900–1279px | 200px 축약 | 유동 | 없음 | 태블릿 가로 (1194~1366px) |
| 1280–1799px | 240px | max 1180px | 없음 | 노트북 |

### 6.3 글자 크기 재판정 — 주 사용 환경은 32" 4K (2026-08-23) ★

§6.2 를 쓴 뒤 **주 사용 환경이 32인치 3840×2160 모니터**임을 확인했다. 이 조건에서 다시 재니 결론이 뒤집힌다.

#### 6.3.1 Windows 배율은 **물리 크기를 바꾸지 않는다**

CSS 뷰포트는 배율에 따라 달라지지만, 화면에 찍히는 실제 크기는 셋 다 같다. 스테이지가 훈련영역 **높이를 채우도록** 배율을 잡기 때문이다 — CSS px 는 단위일 뿐이고, 캔버스가 물리 화면에 대응되는 비율은 배율 설정과 무관하다.

| Windows 배율 | CSS 뷰포트 | 스테이지 배율 | 본문 실효(CSS px) | **본문 실효(device px)** |
|---|---|---:|---:|---:|
| 100% | 3840×2160 | 1.4750 | 22.1 | **22.1** |
| 150% | 2560×1440 | 0.9749 | 14.6 | **21.9** |
| 200% | 1920×1080 | 0.7250 | 10.9 | **21.8** |

세 값이 1.6% 안에서 같다(차이는 상단 nav 36 CSS px 가 배율마다 device px 를 다르게 먹기 때문이다). **같은 그림인데 §7.2 의 CSS px 기준은 100% 합격 · 150% 합격 · 200% 불합격으로 세 가지 판정을 낸다. 기준이 잘못된 것을 재고 있다.**

#### 6.3.2 실측 — 3840×2160 (100% 배율)

스테이지 안 글꼴 **18종 전수**를 측정했다.

| | 캔버스 px | 실효(CSS=device px) | 32" 4K 물리 크기 |
|---|---:|---:|---:|
| 가장 작은 글자 (로그 항목·"미지정") | 9.8 | **14.4** | 2.64 mm |
| 패널 헤더·본문 | 15.0 | **22.1** | 4.06 mm |
| 층 라벨 | 19.5~20.3 | 28.8~29.9 | 5.3~5.5 mm |
| B/C/D 면 표기 | 36.0 | 53.1 | 9.8 mm |

레터박스 0.3px · 가로 스크롤 0 · 캔버스 2603×1440 · 보드 폭 1483.

**§7.2 의 ≥12px 기준을 전 항목이 통과한다.** 가장 작은 글자조차 14.4px 이다.

체감 기준점: 32" 4K 는 137.7 PPI 다. 본문 4.06mm 는 **표준 96 PPI 화면의 브라우저 기본 글자(16px = 4.23mm)와 거의 같고**, 가장 작은 글자 2.64mm 는 **표준 화면의 10px** 에 해당한다. 로그 목록 같은 보조 정보로는 통용되는 크기다.

#### 6.3.3 결론 — §6.2 의 선택지 A/B/C 는 **불필요하다**

주 환경에서 글자가 작지 않다. 특히 **C(루트 글꼴 키우기)를 하면 오히려 넘친다** — 22.1px 에서 더 키울 이유가 없다.

§6.2 가 "미달"로 본 것은 태블릿과 노트북이고, 그건 **화면이 물리적으로 작아서**지 배율 체계의 결함이 아니다. 태블릿은 Q-2 답변대로 보는 용도이므로 우선순위가 낮다.

#### 6.3.4 ⚠ 남은 확인 — 배율 1.0 **초과** 구간의 선명도

100% 배율에서는 스테이지 배율이 **1.475 로 처음 1을 넘는다.** 지금까지 실측한 8종은 전부 1 미만(축소)이었다.

[`StageRoot.css`](../src/components/stage/StageRoot.css) 의 `.stage` 에 `will-change: transform` 이 걸려 있다. 이 힌트는 합성 레이어의 래스터를 **변환 전 크기로 고정**시킬 수 있고, 그러면 1.475 배 확대가 비트맵 확대가 되어 글자가 흐려진다. 축소일 때는 드러나지 않던 문제다.

- 이 변환은 **애니메이션되지 않으므로** `will-change` 가 얻는 것이 없다. 3840×2160 레이어를 강제로 잡아 메모리만 더 쓴다.
- 흐리면 `will-change: transform` 한 줄을 지우면 된다. 브라우저가 실효 배율로 다시 래스터한다.
- **개발용 브라우저 패널은 캡처가 축소돼 판정이 불가능하다. 실기기에서 봐야 한다.**
- 150% 배율(스테이지 0.975)에서는 애초에 발생하지 않는다 — 흐리면 그쪽이 회피책이기도 하다.

### 6.6 이벤트 토큰 크기를 층 행 높이에 묶다 (2026-08-23) ★

사용자 요청: **건물 내부 이벤트 토큰이 "몇 층에 있는지"가 한눈에 읽혀야 한다.**

#### 6.6.1 문제 — 층 높이는 9.3배 움직이는데 토큰은 고정이었다

층 행은 **전부 같은 높이**이고 공식이 하나다.

```
층 행 높이 = 건물높이 / 총가중치        (건물높이 = 1048 × 비율,  비율 0.6~1.4)
```

총행수는 옥상 1 + 상단묶음 0~1 + 개별 4개층 + 하단묶음 0~2 → **2~8행**. 따라서 층 높이는 **79~734px** 로 움직인다. 그동안 토큰은 `calc(100px * var(--ui-scale,1))` — `--ui-scale` 이 삭제됐으니 **고정 100px** 이었다.

| 상황 | 행수 | 비율 | 층 높이 | 토큰 100px 비중 |
|---|---:|---:|---:|---:|
| 기준 시나리오 (10층·화재 1F) | 6 | 1.0 | 175 | 57% |
| 지하 있는 고층 + 건물 축소 | 8 | 0.6 | 79 | **127%** ⚠ |
| 저층 + 건물 확대 | 2 | 1.4 | 734 | 14% |

**⚠ 놓친 환산** — T-4b(판 안 px 환산)에서 `EventTokenCard.css` 만 커밋에 들어가지 않았다. `TacticalArea.css`·`ZoneCell.css`·`FloorRow.css` 는 전부 포함됐다. 아래 변경으로 고정 상수가 사라지면서 이 누락은 자연히 해소된다.

#### 6.6.2 결정

| 항목 | 값 | 근거 |
|---|---|---|
| 계수 | **0.8** (층 행 높이 대비) | "해당 층에 있다"만 명확하면 된다 |
| 하한 | **없음** | 층이 얇아지면 토큰도 같이 얇아지는 게 맞다 |
| 상한 | **140px** (예전 고정 크기 100 의 1.4배) | 저층에서 층이 아주 높아져도 과하게 커지지 않게 |
| 건물 밖 토큰 | **같이 적용** | 위치마다 크기가 다르면 "크기에 의미가 있나" 하는 오해를 부르고, 드래그로 드나들 때 크기가 변한다 |

#### 6.6.3 크기만 바꿔선 안 됐던 것 — 좌표를 중심 기준으로 전환

저장된 `pos` 는 토큰의 **좌상단**이었고 중심은 `pos + half(px)` 로 구했다. **크기가 변하면 같은 저장값이 다른 중심을 가리켜 토큰이 저절로 움직인다.** 건물 높이를 드래그할 때마다 이벤트가 흘러가는 셈이라 그대로 둘 수 없었다.

`pos` 를 **중심**으로 바꿨다(`transform: translate(-50%,-50%)`). 크기가 아무리 변해도 중심은 고정이다. 부수 효과로 `EVENT_TOKEN_HALF_BASE` 가 아예 필요 없어졌다 — **그 값은 26 이었는데 카드 크기 100 의 절반도, `TOKEN_W_BASE` 104 의 절반도 아니었다.** 구역 판정 중심이 실제 중심에서 24px(층 높이의 14%) 어긋나 있었다는 뜻이다.

저장 형식은 기존 선례대로 `posFormat` 을 `'norm'` → **`'norm-center'`** 로 올리고, 맞지 않으면 위치를 폐기해 EventLayer 가 A면 상단에 재배치한다.

#### 6.6.4 단일 출처로 통합

크기 상수가 세 곳에 흩어져 있었고 서로 맞지 않았다(CSS 100 / `TOKEN_W_BASE` 104 / `EVENT_TOKEN_HALF_BASE` 26). 이제 **`TacticalArea` 한 곳**이 층 행 높이에서 크기를 내어 `--event-token-size` 로 심고, 나머지는 전부 그 변수를 읽는다. 이벤트 경로의 `--ui-scale` 잔재 6곳도 함께 걷어냈다.

**핵심은 마지막 줄이다 — 크기는 층을 따라가고 위치는 움직이지 않는다.**

#### 6.6.6 남은 것

`zoneKeys` 는 저장값이라 **건물 높이가 바뀌어도 다시 판정되지 않는다**(보정 로직이 "구역 값이 없는 이벤트"만 채운다). 토큰은 보드 대비 좌표라 제자리에 있는데 층이 움직였으므로, 저장된 구역이 낡을 수 있다. **Q-7 과 같은 계열의 문제**이므로 함께 다룬다.

### 6.5 실 시나리오 검증 — 패널 최소 폭 실측 · 드롭 정확도 (2026-08-23) ★

지금까지 검증은 전부 **빈 시나리오**에서 했다. 실제 시나리오(「테스트」 — 10층·출동대 25대·`boardColumnRatio: 3`)를 가져와 다시 쟀다.

#### 6.5.1 `opW` 하한 실측 — 추정치 420 은 틀렸다

`--op-panel-w` 를 1px 씩 줄이며 운영 패널 전 하위요소의 넘침이 시작되는 지점을 찾았다.

| 분류 열 수 | 최소 폭 (캔버스 px) |
|---:|---:|
| 3 | 236 |
| 4 | 308 |
| 5 (이 시나리오) | **379** |
| **6 (최악)** | **451** |

완전한 선형이다 — **열당 71.5px + 고정비 21.5px.**

**핵심: 최소 폭을 정하는 것은 출동대 *개수* 가 아니라 분류 *열 개수* 다.** [`PoolTokenGrid`](../src/components/shared/PoolTokenGrid.tsx) 의 `.ptg` 가 `flex-flow: row nowrap` 이고 열이 `COLUMN_ORDER` 6종(`suppression`·`rescueEms`·`waterTank`·`special`·`agency`·`custom`)으로 고정돼 있다. 빈 열은 렌더에서 빠지므로 실제 열 수는 시나리오가 어떤 종류를 쓰는지에 달렸고, **상한은 언제나 6** 이다. 유닛이 늘면 열이 길어질 뿐 넓어지지 않는다.

바인딩 제약은 `.ptg__column` 의 `min-width: 44px` 이 아니라 [`TokenCard.css`](../src/components/shared/TokenCard.css) 의 `min-width: 60px` 이다.

> ⚠ **`.ptg__column` 의 `min-width: calc(44px * var(--ui-scale, 1))` 는 이제 폴백 1 로 동작한다** — `--ui-scale` 은 삭제됐다. 값이 44 로 굳었을 뿐 동작은 정상이지만, `calc` 를 지우고 `44px` 로 쓰는 편이 정직하다(§3.1 의 "폴백 1 로 자동 정합"에 해당하는 사례).

**결론 — 클램프 하한은 451 로 잡는다.** 여유를 두려면 460~470. 420 으로 두면 6열 시나리오에서 토큰이 조용히 잘린다(`.ptg` 가 `overflow: auto hidden` 이라 **세로는 스크롤이 아니라 클리핑**이다).

#### 6.5.2 실 출동대 드롭 정확도 — 전부 기준 통과

| 구역 | 구역 폭 | 목표 | 실제 | 오차 |
|---|---:|---|---|---:|
| `face-B` | 288 | 0.25 / 0.40 | 0.2499 / 0.4001 | **0.01% / 0.01%** |
| `face-D` | 288 | 0.70 / 0.65 | 0.7018 / 0.6501 | **0.18% / 0.01%** |
| `1F-center` | 700 | 0.60 / 0.50 | 0.5989 / 0.5038 | **0.11% / 0.38%** |

§7.2 기준 0.5% 를 전부 통과한다. **288px 짜리 좁은 B/D면에서도 토큰이 구역 안에 완전히 들어간다.**

부수 확인:
- `5F-10F-right`(74px 화재표현 열) 드롭은 `isDropTarget=false` 로 **설계대로 거부**됐다(CLAUDE.md 의 그 게이트).
- 진압대를 배치하자 짝 펌프 3대가 대기1단계로 자동 이동 — 정상.

> ⚠ 검증 시 함정: 드롭 두 개를 **같은 틱에** 실행하면 React 리렌더 전이라 같은 카드를 두 번 집게 되어 앞 결과가 덮인다. 드롭 사이에 300ms 이상 둘 것.

#### 6.5.3 Q-8 답 — B/D면 폭은 **설정값**이지 정사각 전환의 결과가 아니다

Q-8 은 "정사각 전환으로 보드 폭이 줄어 B/D면 배치가 그대로 읽히는가"였다. 실측하니 질문의 전제가 바뀌었다.

가로 캔버스가 가변이 되면서 보드는 **1506×1440** 으로 오히려 넓다(정사각 1440 이 아니다 — 남는 폭을 흡수한다). 그 안에서 B : 건물 : D = **288 : 896 : 288** 인데, 이건 사용자가 설정한 `boardColumnRatio: 3` 을 정확히 따른 결과다(896/288 = 3.11).

**즉 B/D면이 좁다면 그건 정사각 전환 탓이 아니라 비율 설정 탓이고, T-8 슬라이더로 즉시 조절된다.** 288px 에서도 토큰 배치·가독성에 문제가 없음은 위 표로 확인했다. **Q-8 은 해소로 본다.**

#### 6.5.4 이 시나리오로 확인하지 못한 것

시나리오에 데이터가 없어 검증 범위 밖으로 남았다 — **소화전 `[]`**(수관 연결·`WaterConnectionOverlay`), **구조대상자 `[]`**(`VictimCard`), **이벤트 `[]`**(이벤트 토큰의 보드 대비 정규화 = Q-7), **`fireStatus: null`**(화재 표현). 이 넷을 채운 시나리오가 있어야 남은 오버레이 검증이 끝난다.

### 6.4 W-4 좌표계 회귀 검증 (2026-08-23) ★

`transform: scale()` 은 좌표계를 바꾼다. 스테이지 도입 후 **좌표를 직접 다루는 코드를 한 번도 검증하지 않은 상태**였다. 2560×1440(배율 0.9749)에서 전수 확인했다.

#### 6.4.1 통과한 것

| 대상 | 방법 | 결과 |
|---|---|---|
| **드래그&드롭 좌표** | 구역의 30%/70% 지점에 합성 드롭 후 저장값·렌더 위치 실측 | 저장 `x=0.30096 / y=0.69982`, 렌더 중심 `0.30035 / 0.69982`. **오차 0.1% 이내** (§7.2 기준 0.5%). 잔여 오차도 합성 이벤트의 `clientX` 정수 절삭 탓 |
| 포털 메뉴 위치 | 추가출동대 메뉴 · 출동대 상태 바메뉴 | 메뉴 상단이 박스 하단(y=316)에 정확히 일치. 바메뉴는 앵커 중심(x=1362.5)에 정확히 정렬, GAP 6px 정확 |
| 오버레이 SVG 3종 | 코드 검증 | `.spray-svg`·`.wco-svg`·`.aerial-svg` 전부 `stagePortalTarget()` 포털 + `getBoundingClientRect` — 둘 다 뷰포트 공간이라 정합 |
| 메뉴 클램프 6곳 | 코드 검증 | `rectToStage`(앵커) · `stageBounds`(경계) · `offsetWidth`(메뉴)가 **모두 포털 공간**이라 정합. 포털이 body 에 있어 그 공간이 곧 뷰포트다 |

#### 6.4.2 발견해서 고친 것 — 원인은 하나다

**`position: fixed` 인데 포털로 나가지 않은 요소.** 변환이 걸린 조상 아래에서 `fixed` 는 뷰포트가 아니라 **그 조상(캔버스)** 기준으로 해석되는데, 넣는 값은 전부 뷰포트 px(`clientX`·`rect.left`·`window.innerWidth`)였다.

| # | 대상 | 증상 | 조치 |
|---|---|---|---|
| **1** | 그리기 툴바 (`DrawingBoard`) | 저장값 `(1000,200)` 이 `(974.9, 231.1)` 에 렌더. **잡는 순간 25.1/31.1px 튀고**, 드래그하면 커서보다 2.5% 뒤처짐 | 위치·클램프를 **캔버스 px 로 통일**(§3.10.1 R4). `stageMetrics()` 로 배율·원점을 재고 이동량을 배율로 나눈다. 실측 튐 **0/0** |
| **2** | 방수 무효클릭 말풍선 (`PlayPage`) | `clientX/clientY` 를 캔버스 px 인 `left/top` 에 넣어 판 우측에서 가로 50px 어긋남 | **포털로 이전** — 좌표 변환 자체를 없앴다 |
| **3** | 분석창·구조활동통계 백드롭 | `.overlay-backdrop` 이 `[0,36,2560,1404]` 로 그려져 **상단 nav 36px 을 덮지 못함**. 모달이 열린 채 `훈련 세팅`·`종료` 클릭 가능 | **포털로 이전.** 실측 `[0,0,2560,1440]`, `elementFromPoint` 로 nav 버튼이 백드롭에 가려짐 확인 |

**규칙으로 굳힌다 — 스테이지 안에서 `position: fixed` 를 쓰려면 포털로 나가거나, 좌표를 캔버스 px 로 다뤄야 한다. 둘을 섞으면 안 된다.**

`position: fixed` 사용처를 전수 조사했고, 위 3건 외에는 전부 포털을 쓰고 있었다. `ScenarioModal` 은 App·설정모드 레벨(스테이지 밖)이라 해당 없음.

#### 6.4.3 남은 것

- **방수 무효클릭 말풍선(#2)은 화면으로 확인하지 못했다.** 방수 모드가 수관·화재 등 시나리오 전제조건을 요구해 빈 시나리오로는 띄울 수 없었다. 이미 실측 검증된 포털 경로와 **동일한 코드 경로**이지만, 실제 훈련 시나리오에서 한 번 볼 것.
- `DragDiagnosticsPanel`(개발 전용)이 포털 없이 `position: fixed` 다. 화면 모서리에 고정되는 패널이라 캔버스 모서리에 붙을 뿐 기능 영향은 없다.
- `ChecklistDrawer.tsx` 는 **어디서도 import 되지 않는 죽은 코드**다.

### 7.3 "구성 동일성"을 재는 법

주관을 빼기 위해 수치로 잰다. 각 해상도에서:

```js
// 스테이지 기준 상대 좌표 — 모든 해상도에서 같아야 한다
const stage = document.querySelector('.stage').getBoundingClientRect();
const rel = el => {
  const r = el.getBoundingClientRect();
  return [(r.left-stage.left)/stage.width, (r.top-stage.top)/stage.height,
          r.width/stage.width, r.height/stage.height].map(v => v.toFixed(4));
};
```

주요 요소 15개(운영 패널·상황판·B/D면·건물·A면·지휘절차 등)에 대해 8개 해상도의 값이 **소수 4자리까지 일치**하면 합격이다. 이 검사는 스크린샷 눈대중을 대체한다.

> 브라우저 검증 시 CLAUDE.md의 두 주의사항이 그대로 적용된다 — sessionStorage 500ms 디바운스, 개발용 브라우저 패널의 `ResizeObserver` 미전달. **리사이즈 검증은 실기기에서 한다.**
