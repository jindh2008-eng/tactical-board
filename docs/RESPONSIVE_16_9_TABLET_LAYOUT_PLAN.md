### 0.1 Phase 0 실측 결과 — 기준 뷰포트는 3840이 아니라 **2560**

기준 PC 브라우저에서 실측한 값이다.

| 항목 | 값 |
|---|---|
| `screen.width × height` | **2560 × 1440 CSS px** |
| `devicePixelRatio` | **1.5** (Windows 150% 배율) |
| 물리 해상도 환산 | 3840 × 2160 ✓ |
| 루트/본문 글꼴 | 15px |

이 문서 §7의 최상위 위험("3840 물리 픽셀을 CSS 기준으로 오인")이 실측으로 확인됐다.
**모든 비율 계산의 기준은 2560 CSS px이다.** 3840을 기준으로 삼았다면 태블릿에서 글자가 1.5배 더 축소돼 5~8px까지 내려갔을 것이다.

이에 따라 §3.3의 우측 패널 비율도 정정한다.

- (오류) `550 / 3840 = 14.32%`
- (정정) **`550 / 2560 = 21.5%`**

### 0.2 Phase 1 완료 — 2열 그리드 전환

`.play-layout`을 절대배치에서 **그리드**로 바꾸고 진행상황 패널을 기본 숨김으로 돌렸다.

```css
.play-layout {
  --op-panel-w:  clamp(300px, 21.5%, 620px);
  --checklist-w: clamp(200px, 12%, 340px);
  display: grid;
  grid-template-columns: 1fr var(--op-panel-w);
  grid-template-rows:    minmax(0, 1fr);
}
```

측정 결과 (`.tactical-board-inner` 실제 폭):

| 뷰포트 | 이전 | 이후 | |
|---:|---:|---:|---|
| 2560×1400 (기준) | 1790 | 1819 | 우측 패널이 정확히 550.4px로 재현됨 |
| 1280×720 | 510 | **912** | +79% |
| 800×1280 | **30** | **500** | §2.2가 "사실상 붕괴"로 기록한 케이스 해소 |

확인 사항: 가로 스크롤 0건, 드롭 좌표 오차 1px 이내(구역 중앙 기준), 타입체크·빌드 통과.

**기준 해상도에서 상황판이 아직 넓어지지 않는 이유** — `.tactical-board-inner`의 `aspect-ratio: 4/3`가 남아 있어 높이에 묶여 있다. 회수한 폭은 현재 좌측 여백이 된다. 이걸 B/D면에 배정하는 것이 Phase 2다.

**부수 결정** — 진행상황 관리는 상단 `표시옵션`에서 다시 켤 수 있다(기본 꺼짐, `tacticalBoardShowChecklistPanel`). 태블릿 도입 전이나 서버 장애 시의 폴백이며, 켜면 3열로 돌아간다. 드래그 폭 조절과 `tacticalBoardChecklistPanelWidth` 저장은 제거했다.

### 0.3 Phase 5(Pointer Events)를 범위에서 제외하는 근거

상황판은 **무전플레이어가 PC 마우스로 드래그**해서 사용한다. 지휘교수 태블릿은 체크리스트 탭만 하므로 HTML5 Drag & Drop 제약에 걸리지 않는다. 따라서 이번 범위에서 뺀다.

되살려야 하는 조건: **태블릿에서 출동대를 직접 옮겨야 할 때.** 그때는 드래그 전면 재작성이므로 독립 과제로 잡는다.

### 0.4 신규 작업 — D면 지휘절차를 무플이 직접 체크

현재 구조:

```
진행상황관리 procedure 항목 체크 → ChecklistProgressContext.checked
                                    └→ D면 CommandProcedureStatusBox 에 ✓ (읽기 전용)
```

`CommandProcedureStatusBox.tsx`(**삭제됨** — D-5 로 우측 [`CommandProcedureTrainingBox`](../src/components/right/CommandProcedureTrainingBox.tsx) 가 대체했다)가 `sourceCommandProcedureItemId`가 붙은 체크리스트 항목만 골라 표시한다.

**변경 방향**: 이 연결을 끊고, D면이 `commandProcedureConfigs`(지휘절차 관리)를 직접 읽어 **무플이 그 자리에서 체크**한다. 진행상황관리에서는 해당 절차 항목을 뺀다.

효과:

- 진행상황관리의 `procedure` 항목이 로그만 남기는 순수 기록용이 되고, D면은 온전히 무플의 것이 된다
- 화면 분리 시 교수 → 무플 명령 중 **화면에 영향을 주는 것이 6종**(화재·이벤트·출동대·도착·메시지·구조대상자)으로 줄어든다

필요한 작업:

1. `CommandProcedureStatusBox`를 읽기 전용 → 체크 가능으로 변경
2. D면 체크 상태 전용 Context + `sessionStorage` 영속화 신설
   (`ChecklistProgressContext`와 같은 패턴 — `tactical-board.runtime.command-procedure`)
3. 설정창에서 지휘절차 → 진행상황관리 가져오기 흐름 정리

**미결 — 착수 전 확정 필요**: 훈련 중 D면이 **어느 레벨**의 지휘절차를 표시하는가?
`CommandProcedureConfigs`는 `beginner`/`intermediate`/`advanced`로 나뉘는데, 현재 레벨 선택은 설정창 `ChecklistSetupPanel`의 "가져오기" 단계에서 일회성으로만 일어난다([ChecklistSetupPanel.tsx:125](../src/components/settings/ChecklistSetupPanel.tsx:125)의 로컬 state). **훈련 실행 시점에 참조할 저장된 레벨 값이 없다.** 선택지:

| 안 | 내용 | 영향 |
|---|---|---|
| A | 설정에 "훈련 레벨" 필드 추가 (건물 설정처럼) | 설정창 작업 필요, 시나리오별로 고정 |
| B | D면 박스에 레벨 드롭다운 | 무플이 훈련 중 전환 가능 |
| C | 지금처럼 설정창에서 가져온 항목을 쓰되 체크 주체만 D면으로 이동 | 최소 변경, 가져오기 흐름 유지 |

### 0.6 Phase 4 완료 — 좌표 정규화

모든 배치 좌표를 **0~1 정규화**로 바꿨다. 생산 지점에서 나누고, 렌더는 퍼센트로 넘겨 CSS가 따라가게 했다 — 리사이즈 재계산 코드가 없다.

| 대상 | 기준 | 생산 지점 |
|---|---|---|
| 출동대 | 구역 | `dragDrop.computeDropCenter` |
| 구조대상자 | 구역 | `victimPlacement.computeVictimOffsets` + 드롭 |
| 이벤트 토큰 | 보드 | `EventLayer.placeUnplaced` + `EventTokenCard` 드래그 |

검증: 구역 폭 125.6 → 555.3px(4.4배) 변화에도 상대 위치 0.2573 → 0.2584(오차 0.11%). 이벤트 토큰은 보드 1702 → 780px에서 저장 좌상단 0.4695 = 실측 0.4694.

**마이그레이션**: `posFormat` 필드를 두고, 없으면 구버전 px로 보아 좌표를 버린다. 로드 시점에는 구역 크기를 모르므로 px를 환산할 수 없다. `zoneKey`는 유지되므로 구역 배치는 남고 구역 내 세부 위치만 기본 흐름 배치로 돌아간다.

### 0.7 Phase 3 기반 완료 — 공통 배율

**루트 글꼴을 지렛대로 썼다.** 이 코드베이스는 치수를 `rem`으로 쓰는 곳이 많아, `useUiScale`이 `html` 글꼴을 배율에 맞춰 조정하면 훈련 화면 전체의 `rem` 값이 한 번에 따라온다. px로 박힌 값만 `--ui-scale`로 개별 환산하면 된다. `/play`와 `/settings`는 다른 라우트라 동시 마운트되지 않고, 언마운트 시 복원한다.

이때 `App.css`의 `body, #root { font-size: 15px }`를 `1rem`으로 바꿔야 했다. 그대로 두면 상속이 끊겨 **명시적 `rem`을 쓴 글자만 줄고 나머지는 15px로 남는다.**

기하와 글꼴 배율을 분리했다(계획서 §3.1의 두 변수).

| 변수 | 범위 | 적용 대상 |
|---|---|---|
| `--ui-scale` | 0.50 ~ 1.60 | 패딩·토큰·아이콘 등 치수 |
| `--font-scale` | **0.78** ~ 1.60 | 글꼴. 본문이 11.7px 밑으로 안 내려간다 |

글꼴 하한을 별도로 둔 것은 §3.2 원칙("작은 화면에서는 조작·가독 가능성을 우선")의 구현이다. 작은 화면일수록 글자가 상대적으로 커지는데, 이게 의도한 절충이다.

**결과 — 보드 대비 토큰 폭**

| | 이전 @2560 | 이전 @1280 | 이후 @2560 | 이후 @1280 |
|---|---:|---:|---:|---:|
| 이벤트 토큰 | 5.87% | 12.82% | 5.87% | 6.41% |
| 출동대 토큰 | 5.87% | 11.72% | 3.82% | 5.75% |

기준 2560×1400에서 `--ui-scale`이 정확히 `1.0000`으로 나와 기준 상수(2560×1364)도 검증됐다.

**잔여 작업** — 아래는 아직 px 고정이다.

- 우측 운영 패널 내부 섹션들
- 상단 내비게이션
- 전술상황판 내부 고정 치수(`140px`, `200px`, `110px`, `88px` 등)
- 배지·카운트다운·상태 메시지의 px 값 (다수는 `rem`이라 이미 따라옴)
- 원형 메뉴·컨텍스트 메뉴·드로어·모달
- 수관·방수·고가차·그림판 오버레이

**검증 한계**: 개발용 브라우저 패널이 프레임을 합성하지 않아 `ResizeObserver`와 `window resize` 콜백이 전달되지 않는다. 각 해상도의 배율 값은 새로고침으로 검증했고, 실시간 리사이즈 경로는 합성 이벤트로만 확인했다(0.625 → 1.0000 갱신). **실기기에서 창 크기 변경·회전 검증이 필요하다.** 이 때문에 `ResizeObserver` 외에 `window resize`/`orientationchange`를 백스톱으로 함께 걸어 뒀다.

### 0.5 알려진 취약점 (Phase 2에서 함께 처리)

`TacticalArea`가 `grid-template-rows`를 **JS 측정값으로 인라인 계산**한다. 측정 시점에 컨테이너 높이가 0이면(숨겨진 탭에서 로드되는 등) `140px 0px 0px minmax(200px,1fr)`처럼 굳어 건물 층이 전부 무너지고, 새로고침 전까지 복구되지 않는다. 검증 중 실제로 재현됐다.

→ Phase 2의 "건물/A면 높이를 픽셀 대신 비율로 저장" 작업에서 `ResizeObserver` 기반 재계산과 0 측정값 무시를 함께 넣는다.

## 1. 요청사항 정리

1. 3840×2160(16:9) 화면에서 정한 구성 비율을 기준으로 훈련창을 설계한다.
2. 화면 해상도가 달라도 전술상황판, 우측 패널, 텍스트, 출동대 토큰, 이벤트 토큰 등 화면 구성요소가 같은 비율로 축소·확대되어야 한다.
3. 갤럭시탭 가로 화면에서도 PC와 같은 전체 구성을 볼 수 있어야 한다.
4. 현재 좌측의 `진행상황 관리` 패널은 운영 화면에서 제거한다.
5. 회수한 좌측 공간은 전술상황판에 배정하고, 특히 B면과 D면의 가용 폭을 넓힌다.
6. 세로 화면에서는 우측 운영 패널을 전술상황판 아래로 자동 이동한다.
7. 이번 작업은 계획 수립까지만 진행하고 실제 코드는 후속 작업에서 수정한다.

## 2. 현재 구현 검토 결과

### 2.1 현재 레이아웃 구조

훈련 화면은 [`PlayPage.tsx`](../src/pages/PlayPage.tsx)에서 다음 세 영역을 한 화면에 절대 배치한다.

```
┌──────────────┬─────────────────────────────┬──────────────────┐
│ 진행상황 관리 │         전술상황판           │  우측 운영 패널   │
│ 최소 220px    │  남은 폭, 내부 보드는 4:3   │  고정 550px       │
└──────────────┴─────────────────────────────┴──────────────────┘
```

- 진행상황 패널: 최소 `220px`, 사용자 저장 폭 사용
- 우측 운영 패널: 항상 `550px`
- 전술상황판 래퍼: `calc(100% - 진행상황폭 - 550px)`
- 전술상황판 내부: `aspect-ratio: 4 / 3`, 높이 우선
- 앱 기본 글자: `15px`
- 이벤트 토큰: `100×100px`
- 출동대 토큰: `14px` 또는 `1.13rem` 글자와 고정 패딩 사용
- 전술상황판 내부에도 `140px`, `200px`, `110px`, `88px` 등 다수의 고정 치수가 존재한다.

즉, 바깥 패널 폭과 상당수 내부 요소는 고정인데 중앙만 남은 폭을 받는 구조다. 해상도가 작아질수록 중앙 상황판만 급격히 손해를 본다.

### 2.2 대표 해상도 실측

현재 코드를 로컬 브라우저에서 동일한 방식으로 렌더링하여 측정한 결과다. 상단 내비게이션 높이 `36px`을 포함한다.

| 뷰포트(CSS px) | 진행상황 폭 | 우측 패널 폭 | 전술상황판 실제 폭 | 결과 |
|---:|---:|---:|---:|---|
| 3840×2160 | 220 | 550 | 약 2,832 | 정상 표시, 좌측에 약 238px 잔여 여백 |
| 2560×1600 | 220 | 550 | 약 1,790 | 두 고정 패널 비중 증가 |
| 1920×1200 | 220 | 550 | 약 1,150 | 중앙 상황판이 크게 축소 |
| 1600×2560(세로) | 220 | 550 | 약 830 | 패널이 좌우에 계속 남음 |
| 800×1280(세로) | 220 | 550 | 약 30 | 상황판 사실상 붕괴 |

기본 글자 크기는 모든 경우 `15px`, 우측 패널은 모든 경우 `550px`이었다. 따라서 현재 구현은 “전체가 같은 비율로 축소”되는 구조가 아니다.

### 2.3 전술상황판 내부 구조

[`TacticalArea.css`](../src/components/building/TacticalArea.css)의 현재 열 비율은 다음과 같다.

```text
B면 : 건물 : D면 = 1 : 1.744 : 1
```

현재 3840×2160 실측 보드 폭 약 2,832px을 기준으로 환산하면 대략 다음과 같다.

- B면: 756px
- 건물: 1,319px
- D면: 756px

진행상황 패널을 제거하고 우측 패널만 유지하면 상황판에 약 3,290px을 배정할 수 있다. 중앙 건물 폭을 약 1,319px로 유지하고 새 공간을 B/D면에 절반씩 배정할 경우 다음 초기 비율이 적합하다.

```text
B면 : 건물 : D면 ≈ 1 : 1.34 : 1
```

이 경우 B/D면은 각각 약 985px이 되어 현재 대비 약 30% 넓어진다. 최종 비율은 실제 토큰 배치 검증 후 `1 : 1.30~1.45 : 1` 범위에서 확정한다.

### 2.4 반응형 작업 시 함께 해결해야 하는 기술 문제

화면 치수만 줄이는 것으로는 태블릿 대응이 끝나지 않는다.

| 문제 | 현재 상태 | 필요한 대응 |
|---|---|---|
| 물리 해상도와 CSS 해상도 차이 | 4K PC와 갤럭시탭 모두 OS 배율/DPR에 따라 `window.innerWidth`가 물리 픽셀보다 작음 | 기준값은 3840이라는 숫자를 직접 쓰기 전에 **기준 PC의 실제 CSS 뷰포트**로 보정 |
| 이벤트 토큰 위치 | 전술상황판 내부 픽셀 좌표로 저장 | `x/boardWidth`, `y/boardHeight` 형태의 정규화 좌표로 전환하거나 스케일 변환 계층 추가 |
| 출동대 토큰 위치 | 구역 내부 픽셀 좌표 저장 | 구역별 정규화 좌표로 전환하고 기존 저장값 마이그레이션 |
| 그림판 | 좌표는 이미 0~1 정규화되어 유리함 | 툴바/선 두께/지우개 반경의 공통 스케일 적용 확인 |
| 토큰 조작 | 출동대는 HTML5 Drag & Drop, 이벤트 토큰·일부 리사이즈는 mouse 이벤트 중심 | 태블릿 조작을 위해 Pointer Events와 pointer capture로 통일 |
| 우클릭 메뉴 | PC 우클릭 중심 | 태블릿 길게 누르기 또는 명시적 메뉴 버튼 제공 |
| 오버레이/팝업 | `position: fixed`와 픽셀 좌표 사용 | 스케일 적용 후 뷰포트 경계 계산 재검증 |
| 사용자 저장 높이 | 전술상황판 건물 높이를 픽셀로 저장 | 비율 저장으로 변경하고 방향 전환 때 다시 계산 |

## 3. 권장 설계

### 3.1 기준 화면과 공통 스케일

화면 전체를 `transform: scale(...)`로 감싸는 방식은 권장하지 않는다. 현재 드래그 계산은 `clientX/clientY`, `getBoundingClientRect()`, 저장된 픽셀 좌표를 혼합하므로 보이는 위치와 계산 좌표가 달라질 가능성이 크다.

권장 방식은 다음과 같다.

1. 기준 PC에서 실제 `window.innerWidth`, `window.innerHeight`, `visualViewport`를 측정한다.
2. 기준 뷰포트를 CSS 변수로 정의한다.
3. `ResizeObserver`와 방향 변경 이벤트로 현재 가용 크기를 측정한다.
4. 화면 모드별 공통 배율을 계산한다.

가로 모드의 기본 계산식:

```text
scaleX = availableWidth  / referenceWidth
scaleY = availableHeight / referenceHeight
uiScale = min(scaleX, scaleY)
```

공통 CSS 변수 예시:

```text
--ui-scale       전체 UI 배율
--font-scale     텍스트 배율
--token-scale    토큰 배율
--panel-scale    패널 치수 배율
--line-scale     테두리/선 굵기 배율
```

`--ui-scale` 하나를 원칙으로 사용하되 가독성과 터치 영역만 별도 하한을 둔다. 치수는 `calc(기준값 * var(--ui-scale))` 또는 공통 디자인 토큰으로 치환한다.

> 중요: 사용자가 말한 3840×2160은 물리 해상도다. Windows 150% 배율에서는 브라우저 CSS 폭이 약 2560px일 수 있다. 기준 PC를 실제 측정하지 않고 `3840`을 CSS 기준으로 고정하면 태블릿 글자가 5~8px 수준까지 축소될 수 있다.

### 3.2 비율 유지와 가독성의 원칙

화면의 기하학적 비율은 기준 화면과 동일하게 유지하되 아래 요소에는 최소값을 둔다.

- 본문 글자: 권장 최소 `10~12 CSS px`
- 핵심 상태 글자: 권장 최소 `12 CSS px`
- 터치 조작 영역: 권장 최소 `44×44 CSS px`
- 테두리: 최소 `1 CSS px`

따라서 “완전히 동일한 축소”와 “태블릿에서 실제로 조작 가능한 크기”가 충돌하는 작은 화면에서는 조작 가능성을 우선한다. 이 하한 적용 여부는 구현 전 시안에서 최종 승인한다.

### 3.3 가로 화면 레이아웃

진행상황 패널을 제거한 뒤 가로 모드는 두 열로 구성한다.

```text
┌───────────────────────────────────────────────────────────┐
│ 상단 내비게이션 — 공통 배율 적용, 좁으면 일부 메뉴 접기   │
├───────────────────────────────────────────┬───────────────┤
│ 전술상황판                                │ 우측 운영 패널 │
│ B면 확장 | 건물 | D면 확장                │ 기준 550 단위  │
│                                           │ 비율 축소      │
└───────────────────────────────────────────┴───────────────┘
```

- 기준 3840 폭에서 우측 패널 비율: `550 / 3840 = 약 14.32%`
- 전술상황판 비율: 약 `85.68%`
- 우측 패널은 더 이상 실제 `550px` 고정값이 아니라 기준 폭의 비율 또는 스케일된 기준 단위를 사용한다.
- 전술상황판 내부의 기존 `4:3` 제한은 제거한다. 회수한 폭을 B/D면에 배정하여 전체 남은 공간을 사용한다.
- B/건물/D 초기 열 비율은 `1fr 1.34fr 1fr`로 시작한다.
- 16:10 갤럭시탭 가로 화면은 16:9 구성을 그대로 맞추고 남는 세로 공간을 균등 여백 또는 상황판 내부 여유 공간으로 처리한다. 콘텐츠를 찌그러뜨리지 않는다.

### 3.4 세로 화면 레이아웃

방향 판단은 특정 갤럭시탭 모델명이 아니라 `orientation: portrait`와 실제 컨테이너 비율을 함께 사용한다.

```text
┌─────────────────────────────┐
│ 상단 내비게이션(축약형)      │
├─────────────────────────────┤
│                             │
│ 전술상황판                  │
│ B면 | 건물 | D면            │
│                             │
├─────────────────────────────┤
│ 기존 우측 운영 패널          │
│ 전체 폭으로 아래 배치        │
│ 필요 시 내부 2열/1열 전환    │
└─────────────────────────────┘
       세로 스크롤 허용
```

- 우측 패널의 `position: absolute; right: 0`을 해제하고 상황판 다음 행으로 이동한다.
- 세로 모드에서는 페이지 세로 스크롤을 허용한다. 한 화면에 모든 요소를 강제로 축소하면 글자와 토큰이 조작 불가능해진다.
- 넓은 세로 태블릿에서는 우측 패널의 4개 섹션을 `2×2`로 배치하는 안을 우선 검토한다.
- 폭이 더 좁으면 1열로 전환한다.
- 상황판을 먼저 보여 주고 운영 패널은 아래에서 이어지도록 DOM/탭 순서를 맞춘다.
- `env(safe-area-inset-*)`를 적용하여 카메라 홀, 시스템 바, 브라우저 UI와 겹치지 않게 한다.

세로 모드는 구조상 전체 화면이 16:9가 될 수 없다. 따라서 **상황판의 내부 비율 유지 + 패널 하단 배치 + 세로 스크롤**을 세로 모드의 승인 기준으로 삼는다.

### 3.5 진행상황 관리 패널 제거 범위

`/play`의 주 운영 화면에서 아래 항목을 제거한다.

- `ChecklistPanel` 렌더 영역
- `checklistWidth` 상태
- 로컬 저장 키 `tacticalBoardChecklistPanelWidth` 사용
- 패널 리사이즈 핸들과 mousemove 로직
- 상황판의 `marginLeft: checklistWidth`
- `calc(100% - checklistWidth - 550px)` 계산

다만 [`DUAL_SCREEN_SYNC_PLAN.md`](./DUAL_SCREEN_SYNC_PLAN.md)에서는 교수 태블릿에 진행상황 관리만 제공하는 별도 화면을 계획하고 있다. 따라서 `ChecklistPanel` 컴포넌트 자체를 삭제하지 않고 **주 훈련 화면에서만 분리**해야 두 계획이 충돌하지 않는다.

### 3.6 크기 토큰화 범위

`src`에는 px 사용이 광범위하므로 모든 값을 일괄 치환하면 위험하다. 다음 순서로 화면 영향 범위를 한정해 전환한다.

1. 훈련 화면 셸과 내비게이션
2. 전술상황판 행/열, 층, 방면, 대기 영역
3. 우측 운영 패널과 4개 하위 섹션
4. 출동대·구조대상자·이벤트 토큰
5. 배지, 상태 메시지, 카운트다운
6. 원형 메뉴, 컨텍스트 메뉴, 드로어, 모달
7. 수관·방수·고가차·화재·그림판 오버레이

설정 화면(`/settings`)은 이번 반응형 범위에서 제외하고 별도 작업으로 유지한다.

## 4. 구현 단계

### Phase 0 — 기준값 확정과 회귀 기준 캡처

- 기준 4K PC에서 물리 해상도, OS 배율, 브라우저 배율, `innerWidth/innerHeight`, DPR을 기록한다.
- 현재 3840×2160 화면 스크린샷과 주요 영역 실측값을 보존한다.
- 갤럭시탭 대상 모델과 실제 브라우저 CSS 뷰포트를 가로/세로 각각 기록한다.
- 기준 토큰 10개 이상, 이벤트 토큰, 구조대상자, 수관, 방수, 배지를 포함한 테스트 세션을 준비한다.

**완료 기준:** 물리 픽셀과 CSS 픽셀을 혼동하지 않는 기준표가 승인됨.

### Phase 1 — 레이아웃 셸 재구성

- `PlayPage`에서 진행상황 패널과 폭 저장/리사이즈 로직을 분리한다.
- 메인 화면을 `전술상황판 + 우측 패널` 2열 Grid/Flex 구조로 변경한다.
- 550px 하드코딩을 스케일 가능한 패널 디자인 토큰으로 변경한다.
- 방향/컨테이너 비율에 따라 `landscape`와 `portrait` 모드를 부여한다.
- 세로 모드에서 우측 패널을 다음 행으로 이동하고 스크롤 정책을 전환한다.

**완료 기준:** 800px 폭에서도 상황판 폭이 0에 가깝게 붕괴하거나 우측 패널 뒤에 가려지지 않음.

### Phase 2 — 전술상황판 확대와 B/D면 재배분

- `.tactical-board-inner`의 고정 4:3 제한을 제거하거나 새 가용 영역 비율로 변경한다.
- 전술상황판이 우측 패널을 제외한 폭과 높이를 모두 사용하도록 한다.
- 열 비율을 `1 : 1.34 : 1`에서 시작해 시각 검증한다.
- C/A면 전폭 영역, 1층 슬래브, 소방통제선, 직전대기 코너의 정렬을 재검증한다.
- 건물/A면 높이 값을 픽셀 대신 비율로 저장한다.

**완료 기준:** 기준 화면에서 건물 폭을 불필요하게 늘리지 않으면서 B/D면이 현재보다 유의미하게 넓어짐.

### Phase 3 — 공통 크기·글꼴·토큰 스케일 적용

- 훈련 화면 전용 크기 토큰과 `--ui-scale`을 도입한다.
- 글꼴, 패딩, 간격, 아이콘, 토큰, 선 굵기에 동일 계열 배율을 적용한다.
- `rem`만 사용하면 루트 전체/설정 화면까지 영향이 번질 수 있으므로 훈련 화면 루트 아래로 범위를 제한한다.
- 가독성 하한과 터치 영역 하한을 적용한다.
- 상단 내비게이션이 좁을 때 중요도가 낮은 옵션을 `더보기`로 접는다.

**완료 기준:** 대표 해상도 사이에서 패널/텍스트/토큰의 상대 비율이 유지되고 텍스트 잘림이 없음.

### Phase 4 — 좌표 정규화 및 저장값 마이그레이션

- 이벤트 토큰 위치를 보드 대비 0~1 정규화 좌표로 변경한다.
- 출동대·구조대상자 절대 위치를 각 드롭 구역 대비 정규화한다.
- 기존 픽셀 저장값에는 버전 번호를 붙이고 최초 로드 시 한 번 변환한다.
- 화면 회전, F11, 브라우저 UI 크기 변경, 리사이즈 뒤에도 같은 상대 위치를 유지한다.
- 고가차 전개점, 방수 목표, 수관 연결, 화재 이벤트 위치 판정과의 호환성을 검증한다.

**완료 기준:** 가로에서 배치한 토큰이 세로 전환 후 같은 방면/층/상대 위치에 유지됨.

### Phase 5 — 태블릿 입력 방식 전환

- HTML5 Drag & Drop 및 mouse 이벤트 의존 조작을 Pointer Events로 통일한다.
- `setPointerCapture()`를 사용하여 손가락이 요소 밖으로 나가도 드래그가 유지되게 한다.
- 우클릭 메뉴는 길게 누르기와 명시적 메뉴 버튼을 함께 제공한다.
- 스크롤과 토큰 드래그가 충돌하지 않도록 드래그 핸들 또는 이동 임계값을 둔다.
- 세로 모드의 아래쪽 패널은 자연스러운 터치 스크롤을 허용한다.

**완료 기준:** 실제 갤럭시탭에서 토큰 이동, 상태 변경, 메뉴 열기, 그림 그리기/지우기가 마우스 없이 가능함.

### Phase 6 — 오버레이·팝업·전체 회귀 검증

- 원형 메뉴와 컨텍스트 메뉴가 화면 밖으로 잘리지 않도록 재배치 계산을 적용한다.
- 수관, 방수, 고가차, 연결송수구, 화재/연기, 그림판 좌표를 검증한다.
- 모달/드로어/분석창의 크기와 z-index를 가로·세로에서 검증한다.
- 회전 도중 열린 메뉴는 닫거나 새 위치로 안전하게 재계산한다.
- 빌드, lint, 주요 사용자 흐름 회귀 테스트를 수행한다.

## 6. 검증 해상도와 승인 기준

### 6.1 필수 검증 매트릭스

아래 값은 물리 해상도만 입력하지 않고 실제 브라우저 CSS 뷰포트와 함께 기록한다.

| 구분 | 방향/대표 해상도 | 확인 목적 |
|---|---|---|
| 기준 PC | 3840×2160 가로 | 기준 비율과 B/D면 확대 |
| Full HD PC | 1920×1080 가로 | 일반 모니터 축소 |
| 갤럭시탭 고해상도 | 2560×1600 가로 | 16:10에서 16:9 구성 유지 |
| 갤럭시탭 고해상도 | 1600×2560 세로 | 우측 패널 하단 이동 |
| CSS 뷰포트 예시 | 1280×800 가로 | DPR 적용 환경의 실사용 가독성 |
| CSS 뷰포트 예시 | 800×1280 세로 | 좁은 세로 화면과 스크롤 |

### 6.2 기능 승인 기준

- 가로 화면에서 진행상황 패널이 표시되지 않는다.
- 상황판과 우측 패널의 기준 비율이 해상도에 따라 함께 변한다.
- 상황판이 우측 패널 뒤로 들어가거나 가로 스크롤을 만들지 않는다.
- 기준 화면에서 B/D면의 실제 배치 폭이 현행보다 넓다.
- 모든 훈련 화면 글자와 토큰이 공통 배율을 따른다.
- 최소 글자/터치 크기 이하에서는 가독성 하한이 작동한다.
- 세로 화면에서 우측 패널이 상황판 아래에 표시된다.
- 화면 회전 뒤 토큰·이벤트·그림 좌표와 훈련 상태가 유지된다.
- 갤럭시탭 터치로 주요 조작이 가능하다.
- PC 마우스 조작은 기존과 동일하게 동작한다.

### 6.3 시각 회귀 허용치

- 주요 열/패널 비율 오차: 기준 대비 ±1%
- 정규화 토큰 위치 오차: 해당 컨테이너 폭/높이 대비 ±1%
- 텍스트 겹침·잘림: 0건
- 의도하지 않은 가로 스크롤: 0건
- 방향 전환 후 화면 밖 토큰/메뉴: 0건

## 9. 최종 권고

이번 변경은 “고정 폭 2개를 미디어쿼리로 줄이는 작업”이 아니라 **훈련 화면의 기준 좌표계와 입력 방식을 반응형으로 전환하는 작업**으로 진행해야 한다.

우선순위는 다음과 같다.

1. 진행상황 패널을 주 훈련 화면에서 제거한다.
2. 전술상황판과 우측 패널을 기준 비율의 2열로 재구성한다.
3. 회수한 폭을 B/D면에 배정한다.
4. 공통 스케일 토큰으로 글자·토큰·간격을 함께 조절한다.
5. 위치 좌표를 정규화한다.
6. 갤럭시탭을 위해 Pointer Events와 세로 하단 배치를 적용한다.

이 순서를 지키면 4K 기준 화면의 시각 비율을 유지하면서도 Full HD, 갤럭시탭 가로, 갤럭시탭 세로에서 중앙 상황판이 붕괴하지 않는 구조로 전환할 수 있다.
