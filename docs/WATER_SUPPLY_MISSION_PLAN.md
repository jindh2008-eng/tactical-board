## 1. 요구사항 (사용자 사양, 2026-09-09)

1. **소화전**에 송수라인으로 연결된 펌프·물탱크는 **「중요」(중요물탱크)** 로 자동 지정된다.
2. **「중요」** 차량에 송수라인으로 연결된 펌프·물탱크는 **「1선」(1선펌프)** 으로 자동 지정된다.
3. 소화전 **거리가 150m 이상**이면 그 소화전 **위에 「순환급수」 임무지정칸**이 생긴다.
   여러 대를 놓을 수 있고 **최대 5대**, **위로 쌓아 올린다**.
4. 순환칸의 차량은 **개별 송수라인을 갖지 않는다.** 칸에 놓인 것 자체가 순환보수 임무
   수행이다. 소화전과도, 서로도 선을 긋지 않는다.
5. **순환칸에서** 호스를 연장해, 순환보수가 아닌 펌프·물탱크로 송수라인을 **하나** 뺀다.
   그 선은 **그 소화전의 순환보수 차량들이 함께 보내는 물**이다 — 출발점은 개별 차량이
   아니라 무리다.
6. 순환의 뜻 — 세 자리를 돌아간다. **1번 소비**(중요물탱크에 보수) · **2번 대기** ·
   **3번 보수·이동**(소화전에서 받고 온다). **최소 3대**, 차량 속도는 **시속 40km** 기준.
   → **순환보수**. 규칙엔진용 기록은 §6.
7. **급수 부족은 훈련 화면에서 벌하지 않는다.** 디브리핑·분석자료에서 보여주거나,
   나중에 수량 소모를 본격 반영할 때 적용한다 — §6.4.

> 4·5 는 2026-09-09 사용자 보충. Q-2 를 「배치 = 급수」로 정하면서 **송수라인의 출발점이
> 무리**라는 것까지 함께 확정됐다. 설계에서 이것이 가장 크게 갈린 지점이다(§3.2·§3.3).

## 3. 설계

세 덩어리다. **①임무 파생 ②순환칸 ③수량 반영** — 서로 의존하므로 순서가 있다.

### 3.1 임무는 **파생값**이다 — 손으로 붙이지 않는다

「중요」·「1선」·「순환급수」는 **연결과 배치가 결정한다.** 그러니 두 경로(자동·수동)를
두지 않는다. 이 저장소가 이미 같은 판단을 두 번 했다 — 역할 슬롯의 ✕ 버튼을 없앤
이유([RoleSlot.tsx](../src/components/shared/RoleSlot.tsx) 주석)와 임시의료소의 「설치」 토글을
없앤 이유([StandbyColumn.tsx](../src/components/building/StandbyColumn.tsx) 의 `changeChief`)가 같다.
**지우는 방법이 둘이면 어느 쪽이 정본인지 흐려진다.**

→ `missionPresetsFor()` 에서 펌프·물탱크의 「1선」·「중요」를 **뺀다**. 우클릭 임무 메뉴에는
「단위」만 남는다. (Q-1)

#### 계산은 순수 함수 하나로 — 신규 `src/utils/waterMissions.ts`

```ts
export type WaterMissionLabel = '순환급수' | '중요' | '1선';

/** 토큰 id → 임무. 없으면 그 차량은 임무가 없다 */
export function deriveWaterMissions(
  connections:    readonly ConnectionLike[],
  circulationIds: ReadonlySet<string>,   // 순환칸에 놓인 차량
  vehicleTypeOf:  (id: string) => string | undefined,
): Map<string, WaterMissionLabel>
```

판정 순서(먼저 정해진 것이 이긴다 — 재지정이 없어 **사이클이 돌지 않는다**):

1. **순환급수** — 순환칸에 놓인 차량. 배치가 곧 지정이라 연결을 보지 않는다.
2. **중요** — `fromType === 'hydrant'` 인 연결의 도착 차량.
3. **중요** — `fromType === 'circulation'` 인 연결의 도착 차량.
   순환칸이 출발점이므로 **개별 순환 차량을 따라갈 필요가 없다**(Q-3·§3.2).
4. **1선** — 「중요」 차량에서 나가는 연결의 도착 차량.
5. 그 밖 — 임무 없음. **1선 아래로는 전파하지 않는다**(Q-4).

대상은 `pump`·`water_tank` 뿐이다. 관창·고가·연결송수구는 임무를 갖지 않는다
(`missionPresetsFor` 의 기존 기준과 같다).

#### 화면·저장에 옮기는 것은 브릿지가 한다 — 신규 `WaterMissionBridge`

파생 결과를 `missionTags` 에 반영하고 **로그를 남긴다**. `UnitCommanderBridge` 와 같은
모양이다 — `TokenProvider` 안이어야 `toggleMissionTag` 에 닿고,
`WaterConnectionProvider` 안이어야 연결을 본다. 둘 다 만족하는 자리가 이미 있다
([PlayPage.tsx:593](../src/pages/PlayPage.tsx) 안쪽).

> **왜 렌더 시점 파생으로 끝내지 않는가.** 「몇 분에 어느 대를 중요물탱크로 세웠는가」가
> 평가 항목이다. 로그와 분석창이 `missionTags` 와 `logType: 'status-tag'` 를 읽으므로
> 저장까지 가야 훈련 기록이 남는다. 대신 **쓰는 곳은 이 브릿지 하나**로 묶어 이중 출처를 막는다.

배타 그룹을 셋으로 넓힌다 — `['1선', '중요', '순환급수']`. 「단위」와는 그대로 겹칠 수 있다.

### 3.2 순환칸 — 소화전 위의 다중 슬롯

#### 언제 생기는가

`distanceM >= 150` 인 소화전에만 그린다. 상수는 `config/unitMissions.ts` 옆에 둔다
(`CIRCULATION_MIN_DISTANCE_M = 150`). 훈련 중 거리는 바뀌지 않는다 — 설정은 읽기 전용이고
「훈련 세팅」을 다시 누르면 `runKey` 로 세션이 통째로 리셋되므로
「칸이 사라졌는데 차가 남는」 상태는 생기지 않는다.

#### 토큰은 **구역을 떠나지 않는다**

순환칸에 놓아도 `zoneKey` 는 `face-A`~`face-D` 그대로 두고 **칸이 그 토큰을 그린다.**
`UnitCommanderSlot` 과 같은 방식이고, 그래야 두 가지가 저절로 지켜진다.

- **건물 밖 단위지휘관 소속이 풀리지 않는다.** `isInCommandScope('exterior', …)` 는
  `face-` 로 시작하는 zoneKey 만 밖으로 친다([unitCommandScope.ts](../src/utils/unitCommandScope.ts)).
  전용 zoneKey(`hyd-3-circ` 따위)를 새로 만들면 순환칸에 넣는 순간 지휘 관계가 끊긴다.
- **직전대기·대기1단계 이동 시 연결 자동 해제**([WaterConnectionContext.tsx](../src/context/WaterConnectionContext.tsx))
  같은 기존 zoneKey 분기에 새 값이 끼어들지 않는다.

그 대신 `ExteriorZone` 이 순환칸 차량을 **자유 배치 렌더에서 걸러야** 한다.
바스켓 탑승 토큰을 거르는 것과 같은 처리다(`isDrawnInBasket`).

#### 목록은 새 Context 가 든다 — `HydrantCirculationContext`

```
{ [hydrantId]: string[] }   // 순서 = 들어온 순서, 최대 5
```

- 저장은 `runtimeSession.ts` 에 **15번째 키** `tactical-board.runtime.hydrant-circulation` 을 더한다.
  CLAUDE.md 의 「런타임 상태는 반드시 `save*`/`load*` 쌍으로」 규칙 그대로다.
- **순서를 저장하는 이유**는 §6 이다 — 누가 보수 중이고 누가 대기인지가 순환보수의 전부다.
  재정렬 UI 는 만들지 않는다(빼고 다시 넣으면 줄 끝으로 간다).
- 해제는 `RoleReleaseContext` 에 등록한다. **순환칸 차량이 어디로든 움직이면 즉시 빠진다** —
  같은 면 안에서 자리만 옮겨도 마찬가지다(층 단위지휘관과 같은 「자리 하나」 규칙).
- 5대가 차면 드롭을 **조용히 거절**한다(툴팁만 — 토출구 `--full` 과 같은 문법).

#### 그리는 자리

`ExteriorZone.cornerStyle` 이 만든 소화전 기둥의 **소화전 위**에 얹는다. A면은
`flex-direction: column`, 나머지 면은 `column-reverse` 라 「위로 쌓임」의 방향이 면마다
다르다. 그래서 소화전과 칸을 `.hydrant-stack` 으로 한 번 감싸 **자기 안에서** 세로를
정한다 — 부모의 방향은 이 상자 하나만 뒤집는다.

#### A면 실측 (2026-09-09, 1600×900)

| | 값 |
|---|---|
| A면 구역 높이 | **130px** |
| 소화전 아이콘 높이 | 116px (구역 위로 **54px 넘침 — 기존 상태**, HydrantIcon.css 주석) |
| 순환칸 5대(한 줄) | 142px → 구역 위로 **199px** |
| 순환칸 5대(접힌 뒤) | **93px** → 구역 위로 **150px** |

**A면은 세로가 없다** — 구역이 소화전보다도 낮다. 그래서 5대를 세로로 세우면
건물 쪽으로 넘어간다. `--circ-max-h: 124px` 로 성장 높이를 묶어 **세 대까지 쌓고
그 위는 옆 열로 접는다**(`flex-flow: column-reverse wrap`). B~D면은 값을 주지 않아
`max-height: none` 이므로 접힐 일이 없다 — 이미지대로 한 줄로 쌓인다.

**남은 겹침 150px 은 A면 소화전이 원래 갖고 있던 성질이다.** 이 저장소의 기존 해법과
같다 — A면 경계 핸들을 끌어 A면을 키우면 해소된다(HydrantIcon.css 주석의 비율 0.84).
A면에 굳이 150m 이상 소화전을 두는 시나리오가 흔해지면 그때 **가로 배치**(소화전 옆에
눕히기)를 검토한다. A면은 폭이 914px 이라 자리는 넉넉하다.

#### 순환칸에서 나가는 송수라인 — **출발점은 무리다** ★

사양 §1-5 가 정한 것이 이 절이다. 순환 차량은 개별 연결을 **하나도 갖지 않고**,
순환칸에서 밖으로 나가는 선 하나가 그 무리 전체의 송수다.

- 이름은 **「순환급수」**다(2026-09-09). 교리 용어인 「순환보수」는 문서와 로그에 남기고,
  판 위에서는 그 자리가 무엇을 하는지가 바로 읽히는 이름을 쓴다.
- **차가 서 있을 때만 파랗다.** 비면 회색 점선으로 배경에 묻는다 — 역할 슬롯의 빈 자리와
  같은 문법이다(RoleSlot.css). 빈 칸이 파랗게 떠 있으면 「이미 돌아가는 중」으로 읽힌다.
- 순환칸이 **하나의 급수원처럼** 동작한다. 합성 id `circ-<hydrantId>` 와 새 종류
  `'circulation'` 을 준다. 칸의 겉 요소에 `data-token-id="circ-…"` 를 달면
  선 오버레이가 지금 코드 그대로 그 자리에서 선을 뽑는다
  (`connectionAnchor` — [WaterConnectionOverlay.tsx](../src/components/overlay/WaterConnectionOverlay.tsx)).
- 연결 규칙에 한 줄 — `circulation: new Set(['pump', 'water_tank'])`
  ([waterConnectRules.ts](../src/utils/waterConnectRules.ts)). 급수 판정의
  `SUPPLY_FROM_TYPES` 에도 넣는다([waterSupply.ts](../src/utils/waterSupply.ts)).
- **라인 수는 1개로 제한**한다 — `MAX_CONNECTIONS['circulation'] = 1`. 한 무리는
  한 중계 지점을 먹인다는 것이 순환보수다(Q-7).
- **순환칸에 있는 동안 그 차량은 제 이름으로 물을 대지도, 쏘지도 않는다**
  (2026-09-09 사용자 결정). 개별 송수 손잡이·「송수」 단추와 함께 **방수포**도 뗀다 —
  물을 실어 나르는 것이 임무인 차가 제 물을 쏘면 그 임무가 무너진다.
  구체적으로는 우클릭의 「송수」·「방수포」 단추와 토큰의 송수·방수 손잡이를 감춘다
  ([UnitStatusBarMenu.tsx](../src/components/shared/UnitStatusBarMenu.tsx) 의
  `canWaterConnect`·`isMonitorUnit`, [TokenCard.tsx](../src/components/shared/TokenCard.tsx) 의
  `showNozzle` 과 게이지 `draggable`). **게이지는 남긴다 — 잔량은 여전히 읽어야 한다.**
  칸에 넣기 전에 걸어 둔 선이 있으면 **넣는 순간 끊는다** — 직전대기로 옮길 때 연결을
  자동 해제하는 것과 같은 처리다([WaterConnectionContext.tsx](../src/context/WaterConnectionContext.tsx)).
- 소화전의 **토출구 2구는 그대로**다. 그 두 구는 중요물탱크 직결용이고, 순환칸은 별개다.
- **칸 안에서는 「순환급수」 임무 칩을 숨긴다**(2026-09-09 사용자 지적). 칸 아래에 이미
  「순환급수」 이름표가 있고 그 안에 선 차는 전부 순환대라, 줄마다 칩을 또 달면 같은 말이
  대수만큼 반복된다. 역할 슬롯이 「단위」 칩에 하는 처리와 같다(RoleSlot.css).
  **임무 자체는 그대로**여서 로그·분석에는 남는다.
- 빈 순환칸에서도 선은 뽑을 수 있게 둔다. 물이 안 갈 뿐이고, 그것은 잔량이 이미 말한다
  — 「선은 그었는데 순환대를 안 붙였다」는 상황 자체가 훈련에서 지적할 거리다.

### 3.3 수량 — 무리가 하나의 물통이다

지금 `computeNetFlowRates` 는 **연결 객체가 있는 것만** 계산한다. 순환칸 배치는
연결이 아니므로, 그대로 두면 순환 차량은 물을 받지도 보내지도 못한다.

#### 줄의 세 자리 (2026-09-09 사용자 확정)

순환칸의 순서가 곧 자리다. **최소 3대**여야 순환이 성립한다.

| 줄 | 자리 | 하는 일 | 어디 있는가 |
|---|---|---|---|
| **1번** | **소비** | 중요물탱크에 보수한다 — 자기 물이 줄어든다 | 중계 지점 |
| **2번** | **대기** | 만수로 바로 뒤에 선다 — 1번이 비면 **즉시** 교대한다 | 중계 지점 |
| **3번** | **보수·이동** | 소화전에서 물을 받고, 중계 지점까지 이동한다 | 소화전 ↔ 도중 |
| 4번~ | 여유 | 3번이 떠나면 그 자리로 | — |

**이동은 3번 자리 안에 든다.** 「소화전에서 받고 → 온다」가 한 자리다.
그래서 거리가 멀어지면 3번 자리가 오래 비고, 그만큼 대수가 더 필요해진다(§6.2).

**2번이 중계 지점에 만수로 서 있다는 것이 3대가 최소인 이유다.** 2대뿐이면 1번이 비었을 때
소화전에 있던 차가 와야 해서 그 이동 시간만큼 급수가 끊긴다.

**교대 — 1번이 0 이 되면 줄 끝으로 보낸다.** 2번이 앞으로 나와 소비를 잇고, 3번이 그 뒤에
붙고, 4번(없으면 방금 빈 1번)이 소화전으로 간다. **목록 회전이 곧 순환이다.**

#### 계산은 가상 연결 둘로 편다

순환칸 연결 하나를, 계산 직전에만 두 개로 펼친다. 저장하지 않는다.

| 가상 연결 | 뜻 | 기존 계산 단계 |
|---|---|---|
| 소화전 → **줄 3번** | 보수 — 소화전에서 채운다 | 3단계 `hydrantGroups` (1000ℓ/min) |
| **줄 1번** → 목적지 | 소비 — 중요물탱크에 보낸다 | 2단계 차량→차량 (demand-pull) |

**기존 유량 코드를 한 줄도 바꾸지 않고** 순환보수의 물리가 그대로 나온다. 특히
2단계의 demand-pull 이 핵심이다 — 중요물탱크가 만수면 1번은 **아래에서 실제로 쓰는 만큼만**
보낸다(1500 은 상한일 뿐이다). 그래서 §6.2 의 안정 조건이 저절로 성립한다.

줄 2번은 어느 가상 연결에도 들지 않아 **만수 그대로 서 있는다.** 그것이 대기다.

Q-5(동시에 몇 대가 채우는가)는 이 모형에서 **1대**로 정해진다 — 줄 3번 하나다.

## 6. 순환보수 — 규칙엔진용 기록 ★

> **이 절이 이 문서를 남기는 이유다.** 아래는 지금 구현하지 않는다.
> 규칙엔진(훈련 평가)을 쓸 때 여기서 시작한다.

### 6.1 정의

소화전에서 중계 지점까지 거리가 멀어(**150m 이상**) 호스 연장만으로는 압력과 시간이
나오지 않을 때, 차량이 **물을 실어 나르는** 급수 방식. 여러 대가 세 자리를 돌아가며 맡는다.

| 줄 | 자리 | 하는 일 | 끝나는 조건 |
|---|---|---|---|
| 1번 | **소비** | 중요물탱크에 보수한다 | 자기 탱크 소진 |
| 2번 | **대기** | 중계 지점에 **만수로** 서서 즉시 교대할 준비 | 1번이 빌 때 |
| 3번 | **보수·이동** | 소화전에서 받고 중계 지점까지 온다 | 도착 (만수) |

전이는 한 방향이다 — **보수·이동 → 대기 → 소비 → (소화전으로) → 보수·이동**.
순환칸의 **순서가 곧 이 줄**이다. 그래서 §3.2 에서 목록을 순서 있는 배열로 든다.

**최소 3대다.** 2대면 1번이 비었을 때 소화전에 있던 차가 와야 해서 그 이동 시간만큼
급수가 끊긴다. 대기 차량이 **현장에 만수로 서 있는 것**이 순환보수의 성립 조건이다.

### 6.2 소요량과 필요 대수 — 계산의 뼈대 (2026-09-09 사용자)

물이 흐르는 길은 **소화전 → 순환대 → 중요물탱크 → 1선펌프 → 진압대**다.
숫자는 전부 이미 코드에 있다([WaterLevelContext.tsx](../src/context/WaterLevelContext.tsx) 상단 상수).

| 값 | 크기 | 상수 |
|---|---|---|
| 진압대 1대 소모 | **300ℓ/min** (초진 구역은 100) | `SUPPRESSION_FLOW_PER_MIN` |
| 소화전 → 차량 | **1000ℓ/min** | `HYDRANT_FLOW_PER_MIN` |
| 차량 → 차량 상한 | 1500ℓ/min | `VEHICLE_FLOW_PER_MIN` |
| 펌프 / 물탱크 용량 | 2800ℓ / 6000ℓ | `WATER_CAPACITIES` |
| **차량 주행 속도** | **시속 40km** = 667m/min | 신규 (2026-09-09 사용자) |

**소비 `C` = 1선펌프에서 수관을 연장한 진압대 수 × 300.**

- `C ≤ 1000` — 소화전 유입만으로 감당된다. **진압대 3대(900)까지가 그 선**이고,
  이때 3대 편성이 안정적으로 돈다. 이것이 사양의 「3대까지는 안정적」이다.
- `C > 1000` — 무리의 총량이 분당 `C − 1000` 씩 줄어든다. 순환대를 늘려도
  **적자 자체는 메워지지 않는다** — 버티는 시간만 늘어난다(`총 적재량 / (C − 1000)`).
  진압대 4대(1200)면 분당 200 적자다.

**필요 대수**는 한 대가 한 바퀴 도는 데 걸리는 시간을, 자기 차례(소비 `t_s`)로 나눈 값이다.
줄이 끊기지 않으려면 **`n` 대가 각자 `t_s` 만큼 서는 동안 한 바퀴가 끝나야** 한다.

```
소비 지속   t_s = 용량 / C                (2800ℓ · C=900 → 3.11분)
보수 소요   t_f = 용량 / 1000             (2800ℓ         → 2.80분)
왕복 이동   t_m = 2 × distanceM / 667     (m/min — 시속 40km)

한 바퀴 = t_s + t_f + t_m  ≤  n × t_s
      ⇒  n ≥ 1 + (t_f + t_m) / t_s
```

펌프(2800ℓ)·진압대 3대(C=900)로 풀면 이렇게 된다.

| 소화전 거리 | 왕복 이동 `t_m` | 필요 대수 `n` |
|---|---|---|
| 150m | 0.45분 | **3대** |
| 500m | 1.50분 | 3대 |
| 1000m | 3.00분 | 3대 |
| **1500m** | 4.50분 | **4대** |
| 3000m | 9.00분 | **5대** |

**150m 에서 정확히 3대가 나온다** — 사양의 「최소 3대」가 계산에서 그대로 떨어진다.
그리고 **최대 5대**라는 칸의 한도는 대략 3km 까지를 감당하는 값이다.

계산값이 3 미만으로 떨어지는 경우(관창이 적어 `t_s` 가 길 때)에도 **교리상 최소는 3대**다 —
소비·대기·보수이동 세 자리가 채워져야 순환이라는 말이 성립한다.

### 6.3 규칙엔진이 지적할 것

1. **대수 부족** — 위 식의 `n` 보다 적게 배치했다. 3대 미만이면 거리와 무관하게 지적.
2. **중계 차량이 0 이 된 시간** — 순환이 끊긴 시간이 곧 방수 중단 시간이다.
3. **순환 미지정** — 거리 150m 이상 소화전을 쓰면서 순환칸을 비워 둔 채 직결 송수만 했다.
4. **순환 주기** — 한 대가 보수 → 수수 → 다시 보수로 돌아오는 시간. 대수가 모자라면 벌어진다.
5. **소비 초과** — `C > 1000` 인 채로 방수를 이어 갔다. 관창을 줄이거나 소화전을 하나 더 써야 한다.

### 6.4 부족은 **훈련 화면에서 벌하지 않는다** (2026-09-09 사용자 결정)

§3.3 의 회전에는 **차량이 오가는 시간(`t_m`)이 들어 있지 않다.** 그래서 거리가 멀어도
줄이 마르지 않고, §6.2 의 「거리가 멀수록 대수가 늘어야 한다」가 화면에서는 드러나지 않는다.

**그대로 둔다.** 순환보수 부족은 다음 두 자리에서만 나타낸다.

- **디브리핑·분석자료** — §6.3 의 지표를 종료 후에 계산해 보여준다. **여기가 본자리다.**
- **나중에 수량 소모를 본격 반영할 때** — 그때 `t_m` 을 교대 지연으로 태우면 판 위에서도
  줄이 마른다. 지금은 하지 않는다.

훈련 중에는 순환칸이 **돌아가는 모습만** 보이면 된다. 화면에서 물을 끊어 벌하면
훈련생이 지휘가 아니라 급수 관리에 매달리게 된다.

따라서 **지금 할 일은 로그를 빠짐없이 남기는 것 하나다** — 순환 배치·해제 시각, 교대 시각,
연결 시각, 잔량 0 시각. 이것이 있으면 분석창이 §6.2·§6.3 을 전부 사후에 계산할 수 있고,
나중에 교대 지연을 얹을 때도 같은 로그를 쓴다.

2. 소화전 → 물탱크1 연결 → 물탱크1 에 「중요」. 물탱크1 → 펌프2 → 펌프2 에 「1선」.
3. 연결을 끊으면 두 임무가 함께 사라진다. 소화전 고장에도 사라진다(C-5 이후).
4. 순환칸에 5대까지 들어가고 6번째는 거절된다. 끌어내면 「순환」이 떨어진다.
5. 순환칸 → 펌프 연결 시 그 펌프에 「중요」가 붙는다. 두 번째 선은 거절된다(Q-7).
6. 순환 차량은 **개별 송수를 걸 수 없다** — 우클릭 「송수」와 손잡이가 없다.
   연결을 걸어 둔 차량을 칸에 넣으면 그 선이 끊긴다.
7. **줄 3번** 게이지가 차오르고 **1번**이 줄어든다. **2번은 만수 그대로다.**
   1번이 0 이 되면 줄 끝으로 가고 순번이 한 칸씩 밀린다.
   **세션 저장은 500ms 디바운스**라 바로 읽지 말고 DOM 을 본다(CLAUDE.md).
8. 진압대 3대(900ℓ/min)까지는 순환 3대로 **무한히 버틴다.** 4대(1200)를 걸면 소화전 유입을
   넘어 무리 총량이 분당 200 씩 줄어든다 — 게이지로 확인한다.
9. 순환칸이 3대 미만이어도 **화면에는 아무 경고가 없다**(§6.4). 로그에는 남는다.
10. A~D 네 면 각각에서 5대 쌓임이 잘리지 않는지 — A면 하단 밴드 위 공간이 가장 좁다.
