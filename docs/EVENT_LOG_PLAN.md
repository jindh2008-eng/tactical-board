## 0. 이 문서의 목적 · 원칙 · 범위

이벤트 로그는 훈련 중 "무슨 일이 있었는가"를 남기는 유일한 기록이고, 앞으로 **분석창·훈련 재생·지휘모드 동기화**가 전부 여기에 의존한다. 그런데 현재 구현은 로그를 **출동대 이동 기록에 다른 사건을 얹은 형태**로 만들어 놨다(§2). 지금 바로잡지 않으면 위 세 기능이 전부 같은 왜곡 위에 쌓인다.

사용자 지시에 따라 이 계획은 두 원칙 위에서 작성했고(0.1·0.2), 여기에 **로그를 무엇에 쓸 것인가**(0.3)와 **무엇을 기록하지 않을 것인가**(0.4)가 더해졌다.

### 0.1 원칙 1 — 다른 기능에 영향을 주지 않는다

로그 기록 방식을 고치면서 **현재 동작하는 전술보드 기능의 동작·화면·타이밍이 바뀌어서는 안 된다.** 구체적 불변식은 §3에 명시했고, 각 단계마다 "무엇을 건드리지 않는가"를 완료 기준에 넣었다.

### 0.2 원칙 2 — 다른 기능의 선반영이 필요한 것은 미룬다

로그를 더 잘 만들려면 **다른 기능이 먼저 정리돼야 하는 항목**이 있다(예: 그림판 좌표계, 분석창, 지휘모드). 그런 항목은 이번에 하지 않고 **§6 표에 따로 모았다.** 해당 기능이 반영된 뒤 §6을 펼쳐 로그 기능을 추가로 손본다.

이 두 원칙 때문에 이 계획은 "한 번에 이상적인 로그 시스템을 만드는" 형태가 아니라, **지금 안전하게 할 수 있는 것 / 나중에 해야 하는 것**을 가르는 형태다.

### 0.3 이벤트 로그의 목적 — AI 분석 파이프라인의 입력 (2026-08-20 확정) ★★

**이 절이 이 문서의 모든 설계 판단을 지배한다.** 로그는 화면에 보여주기 위한 것이 아니라 **분석에 먹이기 위한 데이터**다.

#### 훈련 운영 방식

- 훈련은 **XVR 화면**으로 진행한다. 전술상황판은 XVR 안에서 벌어지는 상황을 **기록·표시**하는 별도 화면이다.
- **무전플레이어**가 두 역할을 겸한다 — ① 각 출동대의 무전을 받아주는 상대역, ② 이벤트가 발생하면 해당 출동대 역할로 지휘관에게 보고. 그리고 그 결과를 상황판에 기록한다.
- 따라서 **상황판 로그 한 줄 뒤에는 대응하는 무전 교신이 있다.** 로그는 무전 교신의 결과를 무플이 대리 입력한 것이다.

#### 최종 산출 파이프라인

```
① 전술상황판 이벤트 로그          ─┐
② 실제 무전 내용 (STT로 텍스트화)  ─┼→ 시간축 정렬 → AI 분석 → 지휘관 평가 결과
③ RAG 3종 (지휘전술 · 소방SOP · 지휘관평가표) ─┘
```

앱이 책임지는 것은 **①의 생산과, ②와 합칠 수 있는 형태로 내보내는 것까지**다. 정렬·취합·분석은 앱 밖에서 한다.

#### 여기서 나오는 설계 기준 네 가지

| # | 기준 | 이 문서에 미치는 영향 |
|---|---|---|
| **G-1** | **1순위는 각 출동대의 이동 기록과 이벤트 발생 기록이다.** 나머지는 부수적 | 기록 항목의 우선순위(§5 E-4)를 여기에 맞춰 재배치했다 |
| **G-2** | **이벤트 발생 시점에 각 출동대가 어디에 어떤 상태로 배치돼 있었는가**가 분석의 핵심 질문이다 | 현재 구조로는 **답할 수 없다**(L-9). E-5를 신설한 이유 |
| **G-3** | ②와 합치려면 **절대 시각**이 반드시 필요하다 | E-2가 "있으면 좋은 개선"에서 **파이프라인의 전제 조건**으로 승격됐다(L-10) |
| **G-4** | 읽는 주체가 AI다. **구조화 형식이 사람이 읽는 문장보다 우선**한다 | CSV(사람용)와 별개로 AI용 내보내기를 신설(E-6). [MASTER_PLAN.md](MASTER_PLAN.md) D-6 M-4가 CSV를 "사람이 읽는 산출물"로 규정한 것과 일치한다 |

### 0.4 기록하지 않는 것 (확정)

| 대상 | 판정 | 근거 |
|---|---|---|
| **그림판** | **기록하지 않는다** (사용자 확정 2026-08-20) | 상황판 위 임시 표시일 뿐 분석 대상이 아니다. [DRAWING_FEATURE_IMPLEMENTATION.md](DRAWING_FEATURE_IMPLEMENTATION.md) §7의 기존 서술("그림은 이벤트 로그에 기록되지 않는다")과도 일치한다. 좌표계 확정을 기다릴 이유가 사라져 **§6 LD-2를 폐기**했다 |
| 토큰 색 변경 | 기록하지 않는다 | 표시 보조. 의미가 사용자마다 다르다 |
| 메모(`customNote`) | 기록하지 않는다 | 표시용 주석이지 사건이 아니다 |
| UI 조작(패널 접기·표시옵션) | 기록하지 않는다 | 훈련 사건이 아니다 |

## 2. 관측된 문제

사실만 적는다. 각 항목에 코드 근거를 붙였다.

### L-1. 로그 창구가 `TokenContext`에 묶여 있다

로그의 절반 이상이 토큰과 무관한 사건(체크리스트·이벤트·방화문·연기·송수·소화전)인데, 기록하려면 반드시 `useTokens()`를 거쳐야 한다. 그 결과:

- `EventContext`는 Provider 바깥이라 직접 기록하지 못하고 `EventLayer`를 우회 경로로 쓴다(§1.2).
- 새 로그 종류를 추가할 때마다 **"이 컴포넌트가 `TokenProvider` 안쪽인가"를 먼저 따져야 한다.** 바깥이면 훅이 throw한다.
- `TrainingContext`(훈련 시작·종료)와 `DrawingContext`는 구조상 기록 자체가 불가능하거나 우회가 필요하다.

### L-2. 로그가 출동대 세션에 얹혀 있다 — 세 가지 부작용 ★

[`TokenContext.tsx:226`](../src/context/TokenContext.tsx:226), [`TokenContext.tsx:479`](../src/context/TokenContext.tsx:479)

1. **토큰이 0개면 로그가 통째로 버려진다.** 복원 조건이 `s.tokens.length > 0`이다. 출동대를 전부 지우거나 로스터 없이 훈련하다 새로고침하면 그때까지의 로그가 사라진다.
2. **토큰·좌표가 바뀔 때마다 로그 배열 전체가 다시 직렬화된다.** 로그가 길어질수록 모든 드래그·이동의 저장 비용이 선형으로 늘어난다.
3. **로그 길이에 상한이 없다.** sessionStorage 용량(약 5MB)을 넘기면 `saveTokenSession`의 `catch {}`가 예외를 삼켜 — **로그뿐 아니라 토큰·좌표 저장까지 조용히 함께 실패한다.** 새로고침 전까지 아무도 모른다.

### L-3. 시간 기준이 두 체계로 섞이고, 구조화된 값은 쓰이지 않는다

- 표시·CSV·PDF가 전부 `timestamp` **문자열**만 쓴다. `elapsedSec`은 타입 정의 외 참조가 **0건**이다(정렬·구간 집계에 쓸 수 있는데 안 쓴다).
- 절대 시각(`Date.now()`)이 어디에도 남지 않는다. 훈련 재생·다중 화면 정렬의 기준이 없다.
- 훈련 시작 전 기록이 전부 `00:00`이라 순서를 알 수 없다.

### L-4. `logSource`가 사실상 미사용

`'user' | 'system' | 'ai-event'` 타입이 있지만 `'system'`을 넣는 곳이 3군데뿐이고([`TokenContext.tsx:336`](../src/context/TokenContext.tsx:336) 외 2), **표시·필터·내보내기 어디서도 읽지 않는다.** 무플이 직접 한 조작과 타이머가 자동으로 한 조작을 구분할 수 없다.

### L-5. 스키마가 이동 전용이라 표시가 문자열 비교로 분기한다 ★

체크리스트 로그의 실제 모습:

```ts
addLog({ logType: 'checklist', tokenId: '', tokenName: '', fromZoneId: '', toZoneId: '', note: itemText });
```

정보는 전부 `note` 문자열에 들어간다. 그래서 표시 코드가 이렇게 된다:

```ts
const isRelease = note === '해제';         // LogPanel.tsx  (fire-status)
const isRelease = note?.includes('해제');  // LogPanel.tsx  (water-relay, status-tag)
const isOpen    = note === '개방';         // LogPanel.tsx  (door)
const isClear   = note === '클린존';       // LogPanel.tsx  (smoke)
```

**로그 문구를 한 글자만 바꾸면 색상·스타일 분기가 조용히 깨진다.** 같은 이유로 필터·집계·재생이 전부 불가능하다. [PROJECT_PLAN.md](PROJECT_PLAN.md) §10이 "문자열 중심 로그 → 정확한 재생·평가 불가"로 이미 지목한 항목이다.

### L-6. 레이블 규칙이 두 파일에 복제돼 있다

`STATIC_LABELS`·`ZONE_NAMES`·`zoneLabel()`이 [`LogPanel.tsx:11`](../src/components/right/LogPanel.tsx:11)과 [`exportLog.ts:5`](../src/utils/exportLog.ts:5)에 **글자 단위로 동일하게** 존재한다. 구역이 늘면 두 곳을 같이 고쳐야 하고, 한쪽만 고치면 화면과 CSV가 어긋난다.

### L-7. 기록이 남지 않는 조작

| 조작 | 위치 | 현재 |
|---|---|---|
| 출동대 생성 | `TokenContext.createToken` | 로그 없음 |
| 출동대 삭제 | `TokenContext.removeToken` | 로그 없음 |
| 토큰 색 변경 | `TokenContext.changeTokenColor` | 로그 없음 |
| 메모 입력 | `TokenContext.setCustomNote` | 로그 없음 |
| 훈련 시작·종료 | `TrainingContext.start` / `stop` | 로그 없음 |
| 그림판 전체 | `DrawingContext` | 로그 없음 |
| 이벤트 토큰 이동 | `EventContext.moveEvent` | 로그 없음 (상태 변경만 기록) |

훈련 시작·종료가 기록되지 않는 것이 특히 문제다. **모든 `MM:SS` 값의 기준점이 로그 안에 없다.**

### L-8. 상태 업데이터 안에서 `addLog`를 호출하는 패턴이 남아 있다

[`ChecklistPanel.tsx:58`](../src/components/panels/ChecklistPanel.tsx:58) `toggleItem`:

```ts
setChecked(prev => {
  ...
  addLog({ ... });   // ← React StrictMode가 업데이터를 이중 호출 → 로그 2건

```

## 2-A. 목적(§0.3) 기준으로 다시 본 문제 — AI 분석 관점

위 L-1~L-8은 "로그 기능 자체의 결함"이다. 아래는 **§0.3의 목적에 비춰 다시 검토했을 때 드러난 것**으로, 사용자가 요청한 검토의 본론이다.

### L-9. 이벤트 발생 시점의 배치 상태를 복원할 수 없다 ★★ — 가장 중요

G-2가 요구하는 바로 그 정보를 현재 구조로는 만들 수 없다. 세 가지가 동시에 막고 있다.

1. **로그는 변화(delta)만 기록한다.** "지금 어디에 있는가"는 어디에도 없다.
2. **시작 상태가 없다.** 훈련 시작 시점에 어느 출동대가 어디에 있었는지 기록되지 않는다. 기준점이 없으면 delta를 아무리 쌓아도 절대 상태를 복원할 수 없다.
3. **구역 안 좌표가 로그에 없다.** `moveToken(id, zoneKey, { x, y })`의 `{x, y}`는 `positions`에만 들어가고, 로그에는 `toZoneId`(구역)만 남는다. "B면"까지는 알아도 B면 어디인지는 모른다. 방수 지점(`sprayTarget`)·고가차 전개점(`aerialTarget`)도 좌표는 버리고 `"전개 (3층)"` 같은 문자열만 남는다.

**결과** — "이벤트 A가 터진 순간의 배치도"를 만들 수 없다. 사용자가 가장 중요하다고 지목한 정보다. → **E-5 신설**로 정면 해결한다.

### L-10. 절대 시각이 없어 무전 STT와 정렬할 수 없다 ★★

- 로그의 시간은 `'MM:SS'` **문자열 하나**뿐이고, `elapsedSec`은 소비처가 없다(L-3).
- STT 결과는 녹음 파일 오프셋 또는 벽시계 기준으로 나온다. 둘을 맞추려면 **훈련 시작의 절대 시각**과 각 로그의 절대 시각이 필요하다.
- `TrainingSessionState.startedAt`(ms)이 세션에는 있지만 **로그에도 내보내기에도 실리지 않는다.**
- G-3에 따라 이건 편의 개선이 아니라 **파이프라인이 성립하기 위한 최소 조건**이다. E-2의 성격이 바뀐다.

### L-11. 이벤트(돌발상황) 기록이 지나치게 얇다

G-1이 이동과 나란히 1순위로 지목한 항목인데, 지금 남는 것은 `이벤트명 + 상태 문자열` 두 개뿐이다.

- `EventContext`가 `floorIds`(이벤트가 놓인 층)·`positions`·`firePercentages`를 갖고 있는데 **로그에 하나도 실리지 않는다.**
- 이벤트 토큰 이동(`moveEvent`)에 로그가 없다(L-7). **이벤트가 어디서 발생했는지 로그만으로는 알 수 없다.**
- 발생→해제 지속시간을 계산하려면 상태 문자열을 짝지어야 하는데, 그 판정이 문자열 비교라 불안정하다(L-5).

### L-12. 부서 지정이 기록되지 않는다 — 그리고 애초에 구현돼 있지 않다

코드 실측 결과 **죽은 비계(scaffolding)** 가 남아 있다.

| 대상 | 상태 |
|---|---|
| `LogType`의 `'assignment'` | 타입에만 존재. **생성처 0곳** |
| `LogEntry.face` · `LogEntry.assignmentType` | 타입에만 존재. **채우는 곳 0곳** |
| `getFaceZoneLogText()` (`data/faceZoneData.ts`) | `"진압1대 B방면 부서 1선 펌프차 지정"` 문구 생성기. **호출자 0곳** |
| `A-pump` · `A-tank` 부서칸 | `getFaceZones()`가 만들지만 **드롭 존으로 렌더되지 않는다.** `ExteriorZone`·`BFaceWithStandby` 모두 `category === 'face'` 하나만 쓰고 모든 드롭이 `face-A`~`face-D`로 떨어진다 |

즉 **1선펌프 부서·중요물탱크 부서 지정은 UI 자체가 없다.** 실제 부서·임무는 배지·임무태그·상태태그로 표현되고 `status-tag` 로그에 **문자열로** 남는다.

→ **결정이 필요하다** (§9 미결 1).

### L-13. 지휘관의 결정과 출동대의 보고가 구분되지 않는다

§0.3의 운영 방식에서 따라 나오는 문제다. 무플의 상황판 조작은 실제로 셋 중 하나다.

1. **지휘관의 지시**를 반영 (예: "진압1대 B면 진입하라")
2. **출동대의 보고**를 반영 (예: "3층 도착했습니다")
3. **무플 자신의 진행** (이벤트 투입, 자동 타이머)

로그에는 셋이 **전부 같은 모양**으로 남는다. `logSource`는 `user`/`system`뿐이고 그나마 읽히지 않는다(L-4).

**지휘관 평가표 기반 분석에서는 "누가 결정했는가"가 평가 항목 그 자체다.** 이 구분이 없으면 AI는 지휘관의 판단과 대원의 자율 판단을 나눌 수 없다. 다만 무플에게 매 조작마다 주체를 고르게 하면 훈련 진행이 느려진다.

→ **결정이 필요하다** (§9 미결 2).

### L-14. 지휘 판단에 해당하는 조작인데 상태도 로그도 없다

| 대상 | 현재 |
|---|---|
| `MedicalPostContext` — 임시의료소 **설치 여부**·담당 출동대 | `useState`뿐. 세션 저장 없음, 로그 없음. **새로고침하면 사라진다** |
| `ResourceStatusContext` — 자원대기소 **지정 여부** | 동일 |

둘 다 소방 SOP상 지휘관이 내리는 명시적 결정이고 **"언제 설치했는가"가 평가 대상**인데 아무 데도 남지 않는다. [MASTER_PLAN.md](MASTER_PLAN.md) §7.5도 이 둘을 "세션에 없는 상태"로 이미 지목했다.

### L-15. 내보내기 형식이 AI 입력에 맞지 않는다

- CSV는 `시간,유형,내용` 3열이고 `내용`은 `entryContent()`가 만든 **한국어 문장**이다(`"펌프1 3층 내부 → 3층 화재"`).
- LLM이 읽을 수는 있지만 집계·정렬·조인이 불가능하고, **토큰 ID가 없어 같은 출동대의 궤적을 이어 붙일 수 없다.**
- [MASTER_PLAN.md](MASTER_PLAN.md) D-6 M-4가 CSV를 **사람이 읽고 보고서에 붙이는 산출물**로 규정했다. G-4에 따라 AI 입력은 **별도 형식**이어야 한다.

| **I-4** | 구버전 세션(현재 형식)이 들어와도 깨지지 않는다 | 새 필드가 없으면 기존 경로로 폴백. `posFormat` 처리와 같은 방식 |

## 4. 목표 상태

```
[생성]  어느 Context·컴포넌트에서든 useLog().addLog(...)  — Provider 위치를 따지지 않는다
   ↓
[모델]  구조화된 사건 + 사람이 읽는 문구를 함께 보관       — 문자열 비교 분기 제거
   ↓
[시간]  절대시각(wallClockMs) + 경과초 + 훈련 기준시각      — 무전 STT와 정렬 가능 (G-3)
   ↓
[상태]  이벤트 발생 시점의 전 출동대 배치 스냅샷            — "그 순간의 배치도" (G-2)
   ↓
[저장]  runtime.logs 독립 키, 상한 있음                    — 토큰 저장과 운명을 공유하지 않는다
   ↓
[표시]  LogPanel — payload 있으면 구조로, 없으면 note로 폴백
[출력]  CSV(사람용) · JSON(AI용) 두 갈래                    — G-4
```

**두 갈래 출력의 역할 분담** ([MASTER_PLAN.md](MASTER_PLAN.md) D-6 M-4 · §7.5와 일치)

| 산출물 | 독자 | 내용 | 근거 |
|---|---|---|---|
| `yymmdd-hhmm.csv` | **사람** | 시간·유형·내용 (보고서 첨부용) | D-6 M-4 |
| `tactical-board-run-{yymmdd-hhmm}.json` | **AI·프로그램** | 로그 원본 객체 + 훈련 메타 + 시점 스냅샷 배열 | §7.5 C안 |

**하지 않는 것** — 완전한 이벤트 소싱(로그를 되감아 상황을 복원하는 리플레이)은 이번 범위가 아니다. [MASTER_PLAN.md](MASTER_PLAN.md) §7.5가 B안(로그 리플레이)을 "비용이 압도적"으로 판정하고 **C안(스냅샷 배열)을 채택**했다. 이 계획은 그 결정을 따른다 — E-5가 만드는 것이 바로 C안의 `snapshots` 배열 원소다.

## 5. 작업 순서

```
E-0 무해한 결함 차단 (0.5일)   ← 단독으로 언제든 가능
  │
E-1 LogContext 분리 + 독립 저장 (1일)          ★ 구조의 본체
  │
E-2 시간축 확립 — 절대시각 + 훈련 기준시각 (0.5일)  ★ STT 정렬의 전제 (G-3)

  │

  │

  │

```

합계 **약 7일.** 각 단계 종료 시점에 훈련 가능한 상태를 유지한다.

> **재현은 최종단계다 (사용자 확정 2026-08-20).** 로그·스냅샷을 기반으로 **훈련 상황을 상황판에 되살리는 것**은 이 계획의 범위가 아니다. E-5는 "그 순간의 배치"를 **데이터로 남기는 데까지**만 하고, 화면 복원은 [MASTER_PLAN.md](MASTER_PLAN.md) §7.5·§7.4(분석창)와 §6 LD-6으로 미룬다. **당면 목표는 기록의 완결성**이다 — §5-A.

**순서의 근거** — E-2 없이 E-6을 하면 STT와 못 붙이는 파일이 나오고, E-3 없이 E-5를 하면 스냅샷 안에 또 문자열이 들어간다. E-5는 E-1(독립 저장)이 없으면 토큰 세션을 더 부풀린다. **거꾸로 할 수 있는 단계가 없다.**

**[MASTER_PLAN.md](MASTER_PLAN.md) §4와의 관계** — 이 계획은 W-2(전술상황판 확대)·W-3(px 토큰화)·W-4(오버레이 회귀)와 **파일이 거의 겹치지 않는다**(§3 파일 소유권). W-0 직후에 끼워 넣든 W-4 뒤에 붙이든 순서 제약이 없다. 다만 **E-1이 `PlayPage.tsx`의 Provider 중첩을 한 줄 건드리므로**, W-2~W-4 중 하나가 진행 중일 때 동시에 하지는 않는다.

00:00 | dispatch | 초기 출동: 진압 2개대, 구조 1개대, 구급 1개대, 펌프차 2대

- `dispatch-initial` payload에 **출동대 6건의 `tokenId`·`label`·`unitType`이 전부** 담긴다 — 이후 이동 로그를 이 기준에 붙일 수 있다
- 진압대와 함께 자동 생성되는 펌프가 요청 집계에 포함된다
- 회수는 창을 열 때의 스냅샷에 종류까지 담아 요청과 같은 형식으로 남는다

**3차 검증 (인명검색 N-9~N-12)** — 화재 3층 시나리오, 구조대상자 3명(3층 내부 2 · 2층 계단실 1)

```
01:28 | search       | 3층 인명검색 해제                        payload.reason = 'manual'
01:26 | search       | 3층 인명검색 투입 (2차)                  payload.phase  = 'secondary'
01:08 | search       | 3층 초진 도달 → 1차 인명검색 종료 (진압1)  payload.kind   = 'search-primary-frozen'
01:08 | fire-status  | 3층 초진
00:11 | search       | 3층 인명검색 투입 (1차)                  payload.phase  = 'primary'
──── 별도 회차 ────
04:04 | search       | 3층 인명검색 이탈 (층 이동)               payload.reason = 'moved-away'
03:38 | victim-found | 남/40대/중상 — 3층 내부 구조대상자 발견 (인명검색)
00:34 | victim-found | 남/60대/중상 — 2층 계단실 구조대상자 발견 (계단실)
```

발견 로그에 **구조대상자의 신원 표기(성별/연령대/상태)와 위치**가 함께 남는다.
진행상황관리 경로(`via: 'checklist'`)는 그 패널이 무플 화면에 렌더되지 않아 브라우저로는 확인하지 못했다 — 코드 경로는 나머지 둘과 동일하다.

**검색 점수 자체는 기록하지 않는다** — 1초마다 변하는 연속값이라 로그를 뒤덮는다.
투입·이탈·전환·발견 네 시점만 남기면 그 사이는 유도된다.

**4차 검증 (이벤트·위치·거점)**

```
      | event-status | 3층 연소확대                    floorId = '3F'
      | event-status | 3층 진행 80%                    kind = 'event-fire-pct'
      | event-status | 해제                            resolved = true
      | status-tag   | 방수 100% → 3층                 targetFloorId = '3F', fromZoneKey = '3F-center'
      | post         | 임시의료소 설치                  post = 'medical', installed = true
      | post         | 자원대기소 운영 지정             post = 'resource', installed = true
      | post         | 자원대기소장 지명: 진압1
```

- 새로고침 후에도 임시의료소 `설치`·자원대기소 `지정` 상태가 유지된다 — 로그와 상태가 어긋나지 않는다
- `resolved` 덕분에 "이벤트 발생 → 해제까지 몇 초"를 문자열 비교 없이 계산할 수 있다

**진행 %를 20% 구간으로 자른 이유** — %는 1초마다 연속으로 변한다. 상태 전환(최성기→큰불잡음→…)이
이미 이정표를 잡고 있으므로, 여기서는 같은 상태 안의 **진행 속도만** 보완하면 된다.
촘촘하게 보려면 `EventLayer.tsx`의 `EVENT_PCT_LOG_STEP` 하나만 줄이면 된다.

**상태메시지와 메모의 구분** — 둘 다 `customNote` 한 필드를 쓴다.
설정된 목록에서 **고른 상태메시지**는 무전 교신 내용이라 기록하고(`source: 'preset'`),
**자유 입력 메모**는 표시용 주석이라 기록하지 않는다(§0.4). `setCustomNote`의 세 번째 인자로 가른다.

**5차 검증 (이벤트 배치 구역 · 방수 타겟)**

```
자동 배치     → data-event-zone="face-A"    title="LPG가스통 — A면"
건물로 이동   → data-event-zone="3F-center"  title="LPG가스통 — 3층 내부"
계단실로 이동 → data-event-zone="4F-stair"   title="전기실 — 4층 계단실"

event-status | 3층 내부 최성기    zoneKey='3F-center' floorId='3F' face=null
event-status | 4층 계단실 화재    zoneKey='4F-stair'  floorId='4F' face=null
status-tag   | 방수 100% → LPG가스통 (A면)   targetEventId='ev1'
```

- 진압 판정(`BuildingBoard`)이 **저장된 배치 구역을 우선 사용**한다 — 화면을 다시 hit-test 하던 것과 달리 토큰이 가진 값과 어긋나지 않는다
- 돌발상황 토큰을 겨눈 방수가 그 토큰의 구역에 점수를 쌓는 것까지 확인(100% → 92%로 하강)

**`data-zone-key`를 쓰지 않은 이유** — 그 속성명은 출동대 드롭 존 선택자(`useTouchDrag`의
`DROP_TARGET_SELECTOR`)라, 이벤트 토큰에 붙이면 출동대를 이벤트 위에 떨어뜨릴 수 있게 된다.
전용 속성 `data-event-id` / `data-event-zone`을 새로 뒀다.

**진행 % 기록 기준을 두 번 고쳤다.**
① 구간값(70%→"60%")을 그대로 적어 실제와 어긋났다 → 실제 값을 적고 구간은 기록 시점만 정하게 바꿨다.
② 고정 경계(100/80/60…)라 100%에서 조금만 내려가도 즉시 첫 줄이 찍혔다 →
**직전에 남긴 값에서 얼마나 떨어졌는지**로 판단하게 바꿨다(`EVENT_PCT_LOG_STEP` = 20%p 하락).

**단위 표기** — 활동대는 `N개대`, 차량·유관기관은 `N대`로 센다.
사용자 예시는 전부 `개대`였으나 `구조대`와 `구조차`가 둘 다 "구조"로 줄어 섞이므로,
차량은 전체 이름(`펌프차`·`물탱크차`)에 `N대`를 붙였다.

> `TrainingLogBridge`의 `getElapsed`를 처음에 ref로 넘겼더니 훈련 시작 로그가 `elapsedSec: null`(시작 전)로 찍혔다 —
> 자식 effect가 부모 effect보다 먼저 실행돼 ref가 한 박자 늦기 때문이다. 렌더 시점 값을 담은 클로저로 바꿔 해결했다.

## 5-A. 기록 누락 전수 목록 (2026-08-20 실측) ★

재현을 최종단계로 미룬 이상 **당면 목표는 기록의 완결성**이다. 아래는 코드를 전수 확인해 뽑은 "지금 로그에 없는 것"과 "있지만 부족한 것"의 전체 목록이다. `N-n`은 신규 기록, `X-n`은 기존 기록의 보강이다.

### A. 시간·기준 — 없으면 나머지 전부의 해석이 막힌다

| ID | 항목 | 현재 | 왜 필요한가 |
|---|---|---|---|
| **N-1** | **훈련 시작 / 종료** | 로그 없음. `TrainingContext.start`/`stop`이 조용히 상태만 바꾼다 | 모든 `MM:SS`의 기준점. **이게 없으면 로그 전체가 떠 있는 값이다** |
| **N-2** | **절대 시각(`wallClockMs`)** | 필드 자체가 없음 | 무전 STT와 붙이는 유일한 축(G-3) |
| **N-3** | 훈련 세팅(초기화) 시각 | 로그 없음 | 한 세션에 여러 번 세팅했을 때 회차를 가른다. 우선순위 낮음 |

### B. 출동대 — G-1 1순위

| ID | 항목 | 현재 | 왜 필요한가 |
|---|---|---|---|
| **N-4** | **초기 배치** — 훈련 시작 시점 전 출동대의 `{tokenId, label, zoneKey}` | 로그 없음 | **기준 상태.** 없으면 이후 이동 로그를 아무리 쌓아도 "지금 어디"를 계산할 수 없다 |
| **N-5** | 출동대 **생성** | 로그 없음(`createToken`) | 추가 투입 시점·규모가 분석 기본 지표 |

| **X-1** | **이동 로그의 구역 내 좌표** | `moveToken(id, zone, {x,y})`의 `{x,y}`가 `positions`로만 가고 로그엔 구역만 남는다 | "B면"까지는 알아도 B면 어디인지 모른다 |

| **X-3** | **고가차 전개 지점**(`aerialTarget`) | `"○○ 전개 (3층)"` 문자열만. 좌표 없음 | 동일 |

### C. 이벤트(돌발상황) — G-1 1순위

| ID | 항목 | 현재 | 왜 필요한가 |
|---|---|---|---|
| **X-5** | **이벤트 발생 층**(`floorId`) | `EventContext.floorIds`에 있는데 **로그에 안 실린다** | 이벤트가 **어디서** 났는지 로그만으로 알 수 없다 |

`VictimContext`는 층별 1차/2차 검색, 감소율(구조대 2 · 진압대 1), 발견 스케줄까지 갖춘 정교한 시스템인데 **로그가 하나도 없다.** 세션 저장(`runtime.victim-search`)만 있다.

|---|---|---|---|
| **N-9** | **구조대상자 발견** | **로그 전무.** `discoveredVictimIds`가 늘어나는 시점(검색 점수 도달·계단실 자동 발견·체크리스트 발견) 어디에도 기록이 없다 | **훈련 성과의 핵심 지표.** 몇 분에 몇 명을 찾았는가 |

### E-5 — 이벤트 시점 배치 스냅샷 (1.5일) ★★ 목적의 본체

**G-2가 요구하는 "이벤트 발생 시점에 각 출동대가 어디에 어떤 상태로 있었는가"를 정면으로 해결하는 단계다.** L-9가 여기서 완전히 해소된다.

#### 설계 — delta 재생이 아니라 시점 저장

로그를 되감아 상태를 복원하는 방식(리플레이)은 [MASTER_PLAN.md](MASTER_PLAN.md) §7.5가 **B안으로 검토하고 "비용이 압도적으로 크다"로 기각**했다. 대신 채택된 **C안의 `snapshots: [...]` 배열**이 있다.

> §7.5 C안 원문: *"파일 최상위를 `snapshots: [...]` 배열로 두고 지금은 원소 하나(종료 시점)만 넣는다. 나중에 타임라인 스크럽이 필요해지면 저장 주기만 추가하면 되고, 파일 포맷은 그대로 간다."*

**E-5는 그 "저장 주기"를 이벤트 시점으로 정하는 것이다.** 파일 포맷을 바꾸지 않고 원소 개수만 늘어난다 — §7.5가 미리 열어 둔 확장점에 그대로 들어간다.

#### 트리거

| 시점 | 이유 |
|---|---|
| 훈련 **시작** | 기준 상태 |
| **이벤트 상태 변경**(발생·해제) | G-2의 핵심 질문이 걸리는 지점 |
| 화재상태 변경 | 이벤트에 준하는 상황 변화 |
| 훈련 **종료** | §7.5 A안이 원래 잡아 둔 시점 |

#### 스냅샷 1건의 내용

| 덩어리 | 필드 |
|---|---|
| 메타 | `atElapsedSec` · `atWallClockMs` · `triggerLogId`(이 스냅샷을 유발한 로그) |
| 출동대 | `tokenId` · `label` · `zoneKey` · `pos{x,y}` · `statusTag` · `missionTags` · `sprayState` · `sprayTarget` · `aerialTarget` · `badges` 요약 |
| 구조대상자 | `victimId` · `zoneKey` · `pos` · 상태 |
| 건물 | 층별 화재상태 · 방화문 · 연기 |
| 이벤트 | 전체 이벤트의 `status` · `floorId` |
| 자원 | 임시의료소 설치·담당 · 자원대기소 지정 · 송수 연결 목록 · 소화전 파손 |

**`triggerLogId`가 핵심이다** — 스냅샷과 로그가 서로를 가리키면 AI가 "이 이벤트 직후의 배치"를 조인 한 번으로 찾는다.

#### 비용

출동대 20대 + 구조대상자 10명 기준 스냅샷 1건이 **약 3~5KB**. 이벤트 20건이면 100KB 이하로, E-0-2의 로그 상한과 합쳐도 sessionStorage 여유 안에 들어온다. **다만 상한은 스냅샷에도 따로 건다**(예: 200건).

#### 완료 기준

- 이벤트를 발생시킨 뒤 스냅샷 1건이 생기고, 그 안에서 **전 출동대의 구역·좌표·상태를 읽을 수 있다**
- `triggerLogId`로 해당 이벤트 로그를 찾을 수 있다
- 스냅샷 저장이 화면 동작을 지연시키지 않는다 (기존 500ms 디바운스 경로에 얹는다)
- 토큰 이동·이벤트 조작의 기존 동작 회귀 0 (I-2)

#### 범위 경계 ★

**E-5는 §7.5 파일 전체를 구현하는 것이 아니다.** `snapshots` 배열의 **원소를 만들어 세션에 쌓는 것까지**만 한다. 파일로 내보내는 것은 E-6, 시나리오(①)를 동봉하는 것은 §7.5 착수 시점이다 — §7.5가 **M-1(설정 동결)이 선행**이라고 못박았기 때문이다.

### 6.2 「현장요소」 개명 — 남은 대상 (LD-14) ★

2026-08-20, 설정의 **「돌발상황」 메뉴가 실제 기능과 맞지 않는다**는 지적에 따라 **「현장요소」** 로 바꿨다.
그 목록은 사건이 아니라 **현장에 놓인 물체**(LPG가스통·탱크로리·전신주·승용차·페인트/신너 등)이고,
훈련 중 바뀌는 것은 등장이 아니라 그 물체의 **상태**다. 덧붙여 `이벤트`가
"이 물체"와 "훈련 중 일어난 일" 두 뜻으로 동시에 쓰여 로그 작업 내내 혼선의 원인이었다.

**이번에 바꾼 것 — 화면 문구뿐이다.**

| 위치 | 변경 |
|---|---|
| [`pages/SettingsPage.tsx`](../src/pages/SettingsPage.tsx) | 좌측 메뉴 라벨 · 섹션 제목 · 안내문 |
| [`components/settings/EventSetupPanel.tsx`](../src/components/settings/EventSetupPanel.tsx) | "등록된 현장요소가 없습니다" |
| [`components/panels/ChecklistView.tsx`](../src/components/panels/ChecklistView.tsx) · [`ChecklistSetupPanel.tsx`](../src/components/settings/ChecklistSetupPanel.tsx) · [`utils/exportChecklistMarkdown.ts`](../src/utils/exportChecklistMarkdown.ts) | 진행상황관리 항목 종류 라벨(`incident`) · 선택 드롭다운 · 안내문 |
| [`utils/sprayTarget.ts`](../src/utils/sprayTarget.ts) | 이름 없는 대상의 표시 기본값 |
| 주석 전반 | 화면과 같은 말을 쓰도록 정리(동작 영향 없음) |

| 종류 | 대상 |
|---|---|

| 체크리스트 항목 타입 | `ChecklistItemType`의 **`'incident'`** — 라벨만 '현장요소'로 바뀌었고 키는 그대로. `'event'`(일반 항목)와 이름이 뒤바뀐 듯 보이는 상태다 |

**주의** — 저장 키(`runtime.events`, 설정의 `eventSetup`)를 바꾸면 **기존 저장분이 끊긴다.**
개명 시 마이그레이션을 함께 넣거나, 키만 옛 이름으로 남기는 편이 안전하다.

이름과 기능이 어긋난 같은 종류의 문제라 개명 시 함께 검토한다.

- 화재·연기 파생 계산
- 좌측 운영 패널·우측 지휘절차 패널의 레이아웃 (**픽셀 단위로 동일해야 한다**)
- 새로고침 시 토큰·좌표·체크 상태 복원

### 7.4 브라우저 검증 시 주의 (`CLAUDE.md` 발췌)

- **sessionStorage 저장은 약 500ms 디바운스된다.** 조작 직후 읽으면 이전 값이 나온다.
- 드롭 존은 `isDropTarget` 게이트가 있다. 합성 이벤트로 드래그를 테스트하려면 실제 카드에 `dragstart`를 먼저 보내야 한다.
- 개발용 브라우저 패널이 프레임을 합성하지 않을 때가 있다. 리사이즈 관련 확인은 실기기에서 한다.

## 8. 미결 사항 — 사용자 결정이 필요한 것

아래 둘은 **어느 쪽을 택하느냐에 따라 작업 내용이 실제로 달라진다.** 답이 나오기 전에는 E-3에서 스키마 자리만 열어 두고 넘어간다.

### 미결 1. 부서 지정(1선펌프·중요물탱크)을 살릴 것인가 — L-12

현재 이 개념은 **타입·문구 생성기·구역 정의만 있고 UI가 없다.** 실제 부서·임무는 배지·임무태그로 표현되고 로그에는 문자열로 남는다.

| 선택 | 결과 |
|---|---|
| **A. 살린다** | 방면별 부서칸을 드롭 존으로 렌더하고 `zoneKey` 체계를 확장. 배치 상태가 구조적으로 기록된다. **다만 전술상황판 레이아웃을 건드려 W-2와 충돌** → LD-11로 미룸 |
| **B. 안 살린다** (현행 유지) | 배지·임무태그를 그대로 쓰되 E-3에서 **구조화**한다(`payload.mission: ['1선펌프']`). 문자열 파싱 없이 AI가 읽을 수 있게 되고, 레이아웃은 안 건드린다 |
| **C. 정리한다** | B + 죽은 비계(`assignment` LogType, `face`·`assignmentType` 필드, `getFaceZoneLogText`, 부서칸 정의) 제거 |

**→ 2026-08-20 사용자가 C(정리)를 선택했다. 죽은 비계를 제거했고, 배지·임무태그 구조화(3-7)는 E-3에서 이어간다.**

### 미결 2. 로그에 "누가 결정했는가"를 남길 것인가 — L-13

지휘관 평가표 기반 분석에서는 이 구분이 평가 항목 자체다. 다만 무플의 입력 부담과 맞바꿔야 한다.

| 선택 | 무플의 부담 | 분석 정확도 |
|---|---|---|
| **A. 안 남긴다** (현행) | 없음 | 지휘관 판단과 대원 자율 판단을 나눌 수 없다 |
| **B. 기본값 + 예외 표시** | 낮음 — 조작 종류별로 기본 주체를 정해 두고(이동=지휘관 지시, 도착 보고=출동대 보고, 이벤트=무플), 다를 때만 우클릭으로 바꾼다 | 대부분 맞고, 어긋난 것은 STT와 대조해 사후 보정 가능 |
| **C. 매번 선택** | 높음 — 훈련 진행 속도에 직접 영향 | 가장 정확 |

**권장은 B다.** 무전 STT가 어차피 함께 들어오므로, 로그의 주체 표시가 틀려도 교신 내용으로 교차 확인이 된다. 로그는 **1차 추정치**만 제공하면 된다.

> 두 미결이 정해지기 전에도 E-0 ~ E-2는 그대로 진행할 수 있다. 영향을 받는 것은 E-3 이후다.
