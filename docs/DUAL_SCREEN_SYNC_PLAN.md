> 작성일: 2026-08-14 (2차 개정 — 범위 축소 반영)
> 대상: 훈련장에서 **지휘교수 태블릿**과 **무전플레이어 PC**의 화면을 분리하고 실시간 동기화
> 상태: 계획(설계 확정 전) — 구현 착수 전 검토용

## 1. 요구사항

### 1.1 운영 형태

교수와 무플은 **바로 옆에 붙어 앉는다.** 따라서 교수 태블릿은 상황을 파악하는 창구가 아니라
**진행상황 관리 패널을 손에 들기 위한 장치**다. 상황 파악은 옆의 무플 화면을 보면 된다.

```
             [지휘관]
                │ 구두 지휘
                ▼
   ┌─────────────────────────────┐
   │   무플 화면 (서버 PC, 대형)  │  ← 지휘관이 보는 화면
   │   상황판 전체 + 모든 제어    │
   └─────────────────────────────┘
        무플 ●   ● 교수  (나란히 착석)
                    │
                    ▼
            [교수 태블릿]
             진행상황 관리 (그것만)
```

| 역할 | 기기 | 화면 구성 | 조작 권한 |
|------|------|-----------|-----------|
| 지휘교수 | 태블릿 | **진행상황 관리 패널만** | 체크리스트 체크/해제 |
| 무전플레이어 | 서버 PC | 현재 훈련창에서 **진행상황 관리를 뺀 전체** | 출동대 이동, 토큰 기능 전체, 건물 상태, **훈련 세팅·시작·종료** |
| 지휘관 | (화면 없음) | 무플 화면을 보며 구두 지휘 | — |

### 1.2 기능 요구사항

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| R1 | 교수가 체크한 항목의 **부수효과가 무플 화면에 즉시 반영** (화재상태·이벤트상태·출동대 배지·도착·구조대상자 발견·메시지) | 필수 |
| R2 | 무플에서 발생한 변화 중 **체크리스트 표시에 필요한 최소 상태**가 태블릿에 반영 (체크 현황, 도착항목 잠금) | 필수 |
| R3 | 무플 화면에서 진행상황 관리 패널 제거 → 상황판 영역 확대 | 필수 |
| R4 | 교수 태블릿에서는 체크리스트 외 **어떤 조작도 불가** | 필수 |
| R5 | 훈련 세팅·시작·종료는 **무플(서버 PC) 전담** | 필수 |
| R6 | 설정은 **서버 PC에서만 작성**, 태블릿은 서버 것을 그대로 수신 | 필수 |
| R7 | 교수 태블릿은 **별도 설치·설정 없이** 주소 접속만으로 사용 | 필수 |
| R8 | Wi-Fi 순단·화면잠금 후 **자동 재연결** | 필수 |
| R9 | 서버·태블릿 없이 **기존 단독 모드로도 훈련 가능** (현행 유지, 폴백) | 필수 |

### 1.3 이번 범위에서 **제외**되는 것

착석 배치 덕분에 아래는 만들지 않는다. 이것이 이 개정의 핵심이다.

| 제외 항목 | 사유 |
|-----------|------|
| 교수 화면의 상황 요약 패널 (화재/연기/구조/출동대 배치) | 옆의 무플 화면을 보면 된다 |
| 교수 화면의 최근 로그 뷰 | 동일 |
| 교수 화면의 훈련 타이머 | 동일 |
| 교수 화면의 훈련 제어 버튼 | 무플 전담 (R5) |
| 교수 화면의 이벤트 전용 패널 | 이벤트 발동은 체크리스트의 `이벤트`·`돌발상황` 항목으로 이미 처리됨 |
| 무플 → 교수 전체 런타임 스냅샷 전송 | 필요한 상태가 2종뿐 (§5.4) |

### 1.4 비기능 요구사항

- 지연: 체크 → 무플 반영 **200ms 이내**
- 인터넷 회선 **불필요**
- 설치: 서버 PC에서 **배치파일 1개 실행**
- 기존 훈련 진행에 **중단 없이** 단계적 배포

## 2. 현재 구조 분석

### 2.1 현 상태

| 항목 | 현재 |
|------|------|
| 아키텍처 | 순수 클라이언트 SPA (React 19 + Vite), **서버 없음** |
| 설정 저장 | `localStorage` 4키 |
| 런타임 저장 | `sessionStorage` 9키 (`tactical-board.runtime.*`) |
| 런타임 상태 | Context 15종 |
| 화면 | `/settings`, `/play` |
| 코드 규모 | `src` 약 21,700 LOC |

### 2.2 유리한 점

1. **체크리스트의 부수효과가 한 파일에 모여 있다.**
   [`ChecklistPanel.tsx`](../src/components/panels/ChecklistPanel.tsx)의 `toggle*Item` / `applyChildEffect` / `triggerLinkedChildren`이 화재·이벤트·출동대·도착·메시지·구조대상자 효과를 전부 담당한다. 이 로직을 헤드리스 훅으로 뽑으면 **그대로 "명령 실행기"가 된다.** 이번 작업의 성패는 사실상 이 리팩터링 하나에 달려 있다.

2. **분리 대상이 패널 1개뿐이다.**
   `PlayPage`에서 `.right-panel` 하나만 떼어내면 무플 화면이 완성된다. 나머지 레이아웃·Provider 구조는 손대지 않는다.

3. **교수 화면은 탭 조작만 필요하다.**
   상황판은 HTML5 Drag & Drop 기반이라 터치에서 동작하지 않는데, 체크리스트는 탭뿐이라 이 제약을 피해 간다.

4. **설정 번들 형식이 이미 있다.**
   [`settingsStorage.ts`](../src/utils/settingsStorage.ts)의 `SettingsExport`(= `exportSettings()`가 만드는 JSON)를 서버 페이로드로 그대로 쓸 수 있다.

### 2.3 해결해야 할 문제

| # | 문제 | 대응 |
|---|------|------|
| P1 | 서버가 전혀 없음 | 통신 계층 신규 (Phase 1~2) |
| P2 | 설정이 기기별 `localStorage`에 독립 저장 → 체크리스트 항목 `id` 불일치 시 **명령이 매칭되지 않음** | 서버를 설정의 단일 원천으로 (§4.3) |
| P3 | `checked` 상태가 메모리 전용 ([ChecklistProgressContext.tsx:18](../src/context/ChecklistProgressContext.tsx:18)) → 새로고침 시 소실 | `sessionStorage` 영속화 추가 |
| P4 | `ChecklistPanel`이 UI와 부수효과 결합 | 헤드리스 훅 분리 (Phase 0-1) |
| P5 | `PlayPage` 레이아웃이 `checklistWidth` + 고정 550px 계산에 하드코딩 ([PlayPage.tsx:645](../src/pages/PlayPage.tsx:645)) | `mode` prop 분기 |
| P6 | 상황판이 3840×2160 전제 | 교수 화면은 태블릿 전용 레이아웃을 **신규** 작성 |

`TrainingContext`의 타이머 동기화 문제는 **교수 화면에 타이머가 없어지면서 사라졌다.**

## 3. 구현 방안 비교

### 방안 A — 서버 PC에서 로컬 서버 실행 (WebSocket) ★권장

| 항목 | 평가 |
|------|------|
| 인터넷 | 불필요 ✅ |
| 지연 | LAN 1~5ms ✅ |
| 의존성 | `ws` 1개 |
| 설치 | 배치파일 1개 + 방화벽 규칙 1회 |
| 태블릿 | 무설치, 주소 접속만 ✅ |

### 방안 B — WebRTC P2P

시그널링 채널이 여전히 필요하고(QR로 SDP 수동 교환은 현장에서 비현실적), 디버깅이 어렵다. 방안 A 대비 이득 없음. ❌

### 방안 C — 클라우드 백엔드 (Firebase 등)

훈련장 인터넷 회선에 의존 → 끊기면 훈련 중단. 외부 서비스로 훈련 데이터 전송에 대한 보안 검토도 필요. ❌

### 방안 D — `BroadcastChannel` / `storage` 이벤트

동일 브라우저·동일 출처에서만 동작 → 기기 간 통신 불가. ❌
단, **같은 PC에 듀얼 모니터를 붙이고 교수 화면을 두 번째 창으로 띄우는** 운영이라면 이 방식만으로 끝난다 (§10-1 참고).

### 3.1 결론

> **방안 A 채택.** 서버 PC(=무플 PC)에서 Node 소형 서버(정적 서빙 + 설정 API + WS 릴레이)를 실행하고,
> 교수 태블릿은 **앱도 설정도 서버에서 받아오는 무설치 씬 클라이언트**로 둔다.

## 4. 아키텍처

### 4.1 권한 모델 — "무플이 진실의 원천"

15개 Context를 분산 상태로 바꾸지 않는다. 대신:

- **무플 화면이 모든 런타임 상태를 단독 소유** → 기존 코드 거의 무변경
- **교수 태블릿은 명령만 올려보내고, 체크 현황만 내려받는다**

```
 교수 태블릿                서버 (무플 PC)              무플 화면
 ───────────                ──────────────              ─────────
 체크 탭
   │ command ──────────────▶ 릴레이 ─────────────────▶ CommandExecutor
   │                                                      │
   │                                            useChecklistActions()
   │                                            = 기존 부수효과 로직 그대로
   │                                                      │
 낙관적 표시                 ◀──── checked / units ───────┘
   │
   ▼
 서버 상태로 확정
```

### 4.2 시스템 구성

```
              서버 PC (무플)
   ┌────────────────────────────────────┐
   │  server.mjs :8787                  │
   │   ├ /              앱 번들(dist)   │──── 태블릿이 앱을 여기서 받음
   │   ├ /api/settings  설정 원천        │──── 태블릿이 설정을 여기서 받음
   │   └ /ws            명령·상태 릴레이 │◀──▶ 실시간 동기화
   │        ▲                            │
   │        │ 설정 저장 시 자동 미러링    │
   │  Chrome — /settings → /player       │
   └────────────────────────────────────┘
```

### 4.3 태블릿 = 무설치 씬 클라이언트, 서버 = 설정의 단일 원천

태블릿에는 아무것도 설치하지 않는다. **앱 번들도 설정도 서버 PC에서 받아온다.**

**흐름**

1. 서버 PC `/settings`에서 시나리오 작성 → `localStorage` 저장(현행 그대로) → **동시에 서버로 자동 미러링**
2. 서버 PC `/player` 진입 → `훈련 세팅` → 서버가 세션 설정을 확정(freeze)
3. 태블릿: 주소 열기 → 앱 다운로드 → `GET /api/settings` → 접속 완료

**이 구조가 제거하는 것**

| 제거 대상 | 사유 |
|-----------|------|
| 설정 배포 WS 메시지 (`settings.push`/`sync`) | HTTP GET 한 번으로 대체 |
| `settingsHash` 불일치 검증·조작 잠금 UI | 설정이 한 벌뿐이라 **불일치가 원천적으로 불가** (P2 소멸) |
| 앱 버전 불일치 | 태블릿이 항상 서버 번들을 받으므로 구조적으로 일치 |
| 태블릿 업데이트 작업 | 서버 PC만 갱신하면 반영 |

**부수 이점** — 서버가 설정을 `server/data/settings.json`으로 보관하므로, 서버 PC 브라우저의 `localStorage`가 날아가도 설정이 복구된다. 현재는 브라우저 데이터 삭제 시 시나리오가 전부 소실되는데, 이 리스크가 함께 해소된다.

**구현이 가벼운 이유** — 설정 영속화가 [`settingsStore.tsx`](../src/store/settingsStore.tsx)의 `useEffect` 4개(`saveWorkingPresets` / `saveCommandProcedureConfigs` / `saveUnitStatusConfig` / `saveUnitTagPresetConfig`)에 모여 있어, 여기에 서버 POST만 덧붙이면 미러링이 완성된다.

**주의점**

| 항목 | 대응 |
|------|------|
| 태블릿 브라우저 캐시로 구버전 번들 로드 | `index.html`은 `Cache-Control: no-store`, 해시 asset은 장기 캐시 |
| `npm run dev`는 번들이 매번 달라짐 | 운영 시 `npm run build` 결과(`dist/`)를 서빙. 배치파일이 build → serve |
| 훈련 중 설정 수정 시 어긋남 | `훈련 세팅` 시점에 세션 설정 **freeze**, 이후 변경은 다음 세팅 때 반영 |

### 4.5 라우팅

| 경로 | 역할 | 비고 |
|------|------|------|
| `/play` | **기존 단독 모드 (현행 유지)** | 서버 없이 동작. 폴백 경로 |
| `/player` | 무플 화면 | 진행상황 관리 제거, 서버 연결 |
| `/instructor` | 교수 태블릿 | 체크리스트 전용 |
| `/settings` | 설정창 (기존) | 서버 PC 전용 |

`/play`를 **건드리지 않는 것**이 중요하다. 개발 중에도 기존 방식으로 훈련을 계속할 수 있어야 한다.

## 5. 통신 프로토콜

### 5.1 메시지 봉투

```ts
interface Envelope {
  v:    1;
  id:   string;                                  // 메시지 UUID (멱등 처리용)
  seq:  number;                                  // 서버 채번 단조증가
  ts:   number;
  from: 'player' | 'instructor' | 'server';
  type: string;
  payload: unknown;
}
```

### 5.2 WebSocket 메시지

**클라이언트 → 서버**

| type | 발신 | payload |
|------|------|---------|
| `hello` | 전체 | `{ role, clientId, settingsRev }` |
| `command` | instructor | `{ commandId, kind, args }` |
| `state.patch` | player | `{ scope, data }` |
| `ping` | 전체 | `{}` (5초 주기) |

**서버 → 클라이언트**

| type | 수신 | payload |
|------|------|---------|
| `session.state` | 전체 | `{ roles: {player, instructor}, settingsRev }` |
| `command` | player | `{ commandId, kind, args }` |
| `command.ack` | instructor | `{ commandId, ok, error? }` |
| `state.patch` | instructor | `{ scope, data }` |
| `settings.reloaded` | instructor | `{ settingsRev }` → `GET /api/settings` 재요청 |
| `peer.left` | 전체 | `{ role }` |
| `pong` | 전체 | `{}` |

### 5.3 HTTP API (설정)

| 메서드 | 경로 | 호출자 | 설명 |
|--------|------|--------|------|
| `POST` | `/api/settings` | player | 설정 변경 시 자동 미러링 (`SettingsExport` 번들) |
| `GET` | `/api/settings` | instructor | 세션 설정 수신 |
| `POST` | `/api/session/freeze` | player | `훈련 세팅` 시 세션 설정 확정, `settingsRev` 증가 |

### 5.4 명령 목록 — 교수 → 무플

교수 화면이 체크리스트뿐이므로 **명령이 사실상 1종으로 압축된다.**

| kind | args | 설명 |
|------|------|------|
| `checklist.toggle` | `{ itemId, checking }` | 항목 토글. 타입별 부수효과(절차/도착/화재/이벤트/출동대/메시지/구조대상자)와 **연동 하위 항목 연쇄까지 전부** 무플이 기존 로직으로 처리 |

> **원칙**: 명령은 "무엇을 눌렀는지"만 담는다. 결과 상태 계산은 언제나 무플이 한다.
> 이 원칙 덕분에 체크리스트에 새 항목 타입이 추가돼도 **프로토콜을 고칠 필요가 없다.**

### 5.5 상태 스코프 — 무플 → 교수

| scope | 내용 | 용도 | 전송 시점 |
|-------|------|------|-----------|
| `checklist` | `{ checkedIds: string[] }` | 체크 표시 | 변화 시 |
| `arrivalLocks` | `{ lockedOrders: number[] }` | 도착 항목 🔒 표시 | 변화 시 (500ms 스로틀) |

이게 전부다. `arrivalLocks`는 `isArrivalLocked()` 계산 결과만 보내면 되므로 토큰 목록을 통째로 보낼 필요가 없다.
**전송량이 훈련 1회 전체에 걸쳐 수십 KB 수준이다.**

### 5.6 무상태 미러 설계 ★

> 실제로는 이 항목이 §5.7의 복잡한 규칙들을 대부분 불필요하게 만든다.

**태블릿은 자기 체크 상태를 갖지 않는다.** 무플이 보내주는 `checkedIds`를 그대로 그린다.

```
탭 → command 송신 → (무플이 실행) → checkedIds 브로드캐스트 → 태블릿 화면 갱신
                     └─────────── LAN 왕복 ~5ms ───────────┘
```

| 이 결정이 없애는 것 | 이유 |
|---------------------|------|
| 낙관적 UI + 롤백 처리 | 왕복이 5ms라 탭 즉시 반응한 것처럼 보인다 |
| `command.ack` 왕복 | **체크 표시가 바뀌는 것 자체가 ack다.** 안 바뀌면 안 간 것 |
| 재연결 후 상태 재동기화 로직 | 무플이 주기적으로 브로드캐스트하므로 재연결하면 저절로 맞는다 |
| 상태 불일치 디버깅 | 진실이 한 곳(무플)에만 있어 어긋날 여지가 없다 |
| 도착 잠금 전송 | 잠긴 항목은 무플이 무시 → 체크가 안 풀림 → 태블릿에도 안 풀린 채 표시. **자동으로 올바르다** |

대신 포기하는 것: 네트워크가 느릴 때 탭 반응이 지연돼 보인다. 훈련장 LAN에서는 문제되지 않으며, 만약 체감된다면 그때 낙관적 UI를 얹으면 된다.

### 5.7 일관성·복구 규칙 (제품 수준 강화 시)

1. **멱등성**: 무플은 최근 `commandId` 200개를 링버퍼로 보관, 중복 수신 시 무시하고 ack만 재전송.
2. **순서**: 서버가 `seq` 채번. 무플은 역행 메시지 폐기.
3. **재연결**: 태블릿 재접속 시 서버가 `checklist` + `arrivalLocks` 전량 재전송. 낙관적 상태는 폐기하고 수신값으로 교체.
4. **오프라인 큐 금지**: 끊긴 동안의 명령을 **자동 재전송하지 않는다.** 시나리오 지시가 뒤늦게 일괄 적용되면 훈련이 꼬인다. 어차피 옆자리이므로, **끊기면 무플 화면에서 직접 체크하는 것이 가장 빠른 복구**다 (§8 K6).
5. **설정 갱신**: `settings.reloaded` 수신 시 태블릿이 `GET /api/settings` 재조회.

### 6.3 접속

태블릿에 설치할 것이 없으므로 접속은 **주소를 여는 것**이 전부다.

- 무플 화면 `접속 안내` 버튼 → **QR + URL(`http://192.168.x.x:8787/instructor`)** 표시
- 태블릿에서 QR 스캔 → 교수 화면 진입 (앱·설정 자동 수신)
- 태블릿 브라우저에 **홈 화면 추가**를 1회 해두면 이후엔 아이콘 탭 한 번

## 7. 단계별 작업 계획

각 Phase는 독립 배포 가능하며, 완료 전까지 기존 `/play` 단독 모드로 훈련을 계속할 수 있다.

### Phase M — 최소 구현 (약 5일) ★먼저 이것부터

아래 Phase 0~5는 **제품 수준의 견고함**을 전제한 계획이다. 그러나 "체크 기능만 태블릿으로 넘기고 무플에서 패널을 없앤다"는 목표만 놓고 보면 **훨씬 적은 코드로 동작하는 물건이 나온다.** 먼저 이것을 만들어 현장에서 써보고, 부족한 부분만 골라 Phase 0~5에서 보강하는 순서를 권장한다.

핵심은 **§5.7의 무상태 미러 설계**다. 태블릿이 자기 상태를 갖지 않기로 결정하는 순간, 초판 견적의 상당 부분(낙관적 UI, ack 왕복, 멱등 처리, 순서 보장, 재연결 재동기화, 도착 잠금 전송)이 **만들 필요가 없어진다.**

**M-1이 왜 0.5일인가** — [ChecklistPanel.tsx:315](../src/components/panels/ChecklistPanel.tsx:315)의 `handleClick`이 닫고 있는 값(`item`·`itemType`·`order`·`isLocked`·`isChecked`)은 전부 `item`과 `checked`에서 다시 구할 수 있다. 즉 **JSX 맵 밖으로 옮기기만 하면 되고 분기 로직은 손대지 않는다.** 노출 방식도 새로 설계할 필요 없이 [`FireCommandContext`](../src/context/FireCommandContext.tsx)의 `register(fn)` / `call(...)` 패턴을 그대로 복제하면 된다. 초판의 "헤드리스 훅 완전 분리(1.5일)"는 구조적으로 더 깔끔하지만, 지금 필요한 것은 아니다.

**M-2에서 패널을 제거하지 않고 숨기는 이유** — 부수효과 로직과 `message` 팝업 포털이 이 컴포넌트 안에 있다. 숨겨두면 리팩터링 없이 그대로 동작하고, 서버가 죽었을 때 `display` 한 줄만 되돌리면 즉시 현행 운영으로 복귀한다. 단독 모드 폴백 코드를 따로 만들 필요가 없다.

**MVP에서 의도적으로 생략하는 것**

| 생략 | 왜 괜찮은가 |
|------|-------------|
| 낙관적 UI · Undo 스낵바 | LAN 왕복이 ~5ms라 체감상 즉시 반응 (§5.7) |
| `command.ack` | 체크 표시가 바뀌는 것 자체가 ack |
| 멱등 처리(`commandId` 링버퍼) · `seq` 순서 보장 | 교수 1명 · 초당 1건 미만 · 단일 릴레이 |
| 도착 잠금(`lockedOrders`) 전송 | 무플이 잠금을 무시하면 체크가 안 풀리고, 그 결과가 그대로 태블릿에 비친다 — **자동으로 올바르게 동작한다.** 🔒 아이콘만 안 보일 뿐 |
| 설정 HTTP API · `freeze` | 태블릿 접속 시 WS로 설정 번들 1회 전송 |
| 서버 스냅샷 백업 | 무플의 `sessionStorage`로 복구됨 |
| 캐시 헤더 · QR · 방화벽 스크립트 | 초기엔 수동 (URL 직접 입력, 방화벽 1회 허용) |

**MVP 이후 우선 보강 순서** (현장에서 실제로 아쉬웠던 것부터)

1. `checked` 세션 영속화 (Phase 0-2) — 무플 새로고침 시 체크 현황 소실 방지. 0.5일
2. 접속 QR + 배치파일 + 방화벽 스크립트 (Phase 1-6, 5-2) — 준비 시간 단축. 1일
3. 도착 잠금 표시 + 연결 끊김 배너 (Phase 2-4, 4-2) — 0.75일
4. 캐시 헤더 (Phase 1-5) — 태블릿 구버전 문제 발생 시. 0.25일
5. 헤드리스 훅 완전 분리 (Phase 0-1) — 체크리스트를 더 손댈 일이 생길 때
6. 나머지(ack·멱등·seq·스냅샷 백업)는 **실제로 문제가 관측될 때만**

## 10. 착수 전 확인 사항

### 10-1. 태블릿이 정말 필요한가 — 듀얼 모니터 대안

교수와 무플이 **옆에 붙어 앉는다면**, 서버 PC에 모니터를 하나 더 달고 교수 화면을 두 번째 창으로 띄우는 방법이 있다.

| | 태블릿 (방안 A) | 듀얼 모니터 (방안 D) |
|---|---|---|
| 개발 공수 | 약 19일 | **약 6일** (Phase 0 + `BroadcastChannel` 동기화 + 교수 화면) |
| 네트워크 위험 | AP 격리·방화벽·순단 (K1·K2·K6) | **없음** |
| 교수 자세 | 태블릿을 들고 자유롭게 | 모니터 앞 고정 |
| 확장 | 평가관 태블릿 추가 용이 | 불가 |
| 장비 | 태블릿 | 모니터 + 케이블 |

교수가 **태블릿을 손에 들고 이동하며 진행할 필요가 없다면**, 듀얼 모니터 쪽이 공수 1/3에 위험은 0이다.
반대로 향후 원격 참관·평가관 화면·다른 강의실 운영을 염두에 둔다면 태블릿(방안 A)이 맞다.
**이 판단을 먼저 확정하는 것이 가장 중요하다.**

### 10-2. 훈련장 Wi-Fi에서 태블릿 ↔ PC 직접 통신 (방안 A 선택 시)

가장 중요한 사전 검증. 5분이면 확인된다.

```bash
npm run dev -- --host
```

서버 PC에서 실행 후 콘솔에 표시되는 `http://192.168.x.x:5173`을 태블릿 브라우저에서 열어본다.
안 열리면 AP 클라이언트 격리를 의심하고, 서버 PC 모바일 핫스팟으로 재시도한다.

### 10-3. 나머지 확인 사항

| # | 항목 | 영향 |
|---|------|------|
| 1 | 교수 태블릿 기종·해상도·브라우저 (iPad Safari / Android Chrome / Windows 태블릿) | 레이아웃 기준 해상도 결정 |
| 2 | `message` 타입 항목의 팝업을 **어느 화면에 띄울지** — 무전으로 읽어주는 사람이 무플이므로 무플 기본으로 잡았다. 교수도 봐야 하면 양쪽 표시 (+0.25일) | 소폭 |
| 3 | 향후 태블릿에서 출동대 이동이 필요해질 가능성 | 있다면 상황판 DnD를 Pointer Events로 재작성해야 함 (별도 대규모 작업, 이번 범위 밖) |

## 11. 부록 — Phase 0 리팩터링 상세

### 11-1. `useChecklistActions()` 시그니처(안)

```ts
// components/panels/useChecklistActions.ts
export interface ChecklistActions {
  /** 항목 토글 + 연동 하위 항목 연쇄까지 전부 처리. 명령 실행기가 그대로 호출한다. */
  toggleItem: (itemId: string, checking: boolean) => void;
  /** 도착 항목 잠금 여부 — 상태 발신 및 UI 표시용 */
  isArrivalLocked: (order: number) => boolean;
  /** 잠긴 도착 차수 전체 — StatePublisher가 구독 */
  lockedArrivalOrders: number[];
  activeMessages: ChecklistItem[];
  dismissMessage: (itemId: string) => void;
}
export function useChecklistActions(): ChecklistActions;
```

- 반드시 `TokenProvider` / `VictimProvider` / `EventProvider` / `FireCommandProvider` **내부**에서 호출되어야 한다.
  → `CommandExecutor`와 `StatePublisher`는 `PlayPage`의 `<div className="play-layout">` 안쪽에 배치한다.
- 현행 `ChecklistPanel`이 이 훅을 쓰도록 바꾸면 동작이 그대로 유지된다 (무손실 리팩터링).
- 교수 화면의 `ChecklistPanel`은 이 훅 **없이** 렌더되고, 탭 시 `checklist.toggle` 명령만 보낸다.

### 11-2. 표시 컴포넌트 공용화

`ChecklistPanel`을 두 화면이 공유하되, 동작 주입만 다르게 한다.

```tsx
<ChecklistView
  config={checklistConfig}          // 양쪽 동일 (서버 설정)
  checked={checked}                 // 무플: 로컬 / 교수: 서버 수신
  lockedOrders={lockedOrders}       // 무플: 로컬 계산 / 교수: 서버 수신
  onToggle={handleToggle}           // 무플: 로컬 실행 / 교수: 명령 송신
  variant="desktop" | "tablet"      // 밀도·타깃 크기
/>
```

### 11-3. 회귀 검증 시나리오 (Phase 0 완료 시 필수)

| # | 시나리오 | 기대 |
|---|----------|------|
| 1 | 훈련 세팅 → 시작 → 도착 항목 체크 | 해당 차수 출동대가 대기1단계로 이동 |
| 2 | 배치된 출동대가 있는 상태에서 도착 항목 해제 시도 | 🔒 잠금, 해제 불가 |
| 3 | 화재 항목 체크 | 지정 층 화재상태 변경 + 로그 기록 |
| 4 | 이벤트 항목 체크 | 이벤트 토큰 상태 변경 |
| 5 | 출동대 항목 체크 (statusMsg / mission / status 각각) | 배지·메모 반영, 해제 시 원복 |
| 6 | 하위 연동 항목이 있는 상위 항목 체크 | 하위까지 연쇄 적용 + 각각 로그 |
| 7 | 메시지 항목 체크 | 팝업 표시, 닫기 동작 |
| 8 | 구조대상자 항목 체크 | 발견/미발견 전환 |
| 9 | 새로고침 | 체크 현황 유지 (0-2 신규 동작) |
