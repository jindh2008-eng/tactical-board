## 1. 문서 목적

이 문서는 제품 기능 로드맵과 분리하여, 현재 기능을 안정적으로 유지하기 위한 기술 개선 작업을 관리한다. 반복 발생하는 오류는 증상만 수정하지 않고 재현 조건, 상태 전이, 원인, 수정 범위, 회귀 테스트와 완료 기준을 함께 기록한다.

제품 목표와 사용자 공개 순서는 `PROJECT_PLAN.md`를 기준으로 하고, 실제 안정화 작업의 우선순위와 검증 상태는 이 문서를 기준으로 한다.

## 2. 운영 원칙

- 간헐적 오류는 “재현 안 됨”으로 닫지 않고 상태성 결함으로 관리한다.
- 수정 전 정상 경로와 실패 경로를 각각 재현 가능한 절차로 기록한다.
- 빌드 성공만으로 완료 처리하지 않고 관련 회귀 시나리오를 통과해야 한다.
- 전역 상태, 전체화면 레이어, 드래그 상태는 진입과 함께 종료·취소·실패·중단 경로를 정의한다.
- 출동대, 구조대상자, 돌발 아이콘처럼 같은 사용자 개념을 다른 입력 방식으로 구현한 경우 공통 동작 계약을 먼저 정의한다.
- 원인이 확정되지 않은 항목은 “원인 후보”로 표시하고 코드 수정 후 검증 결과로 확정한다.

## 3. P0 장애: 출동대·구조대상자 간헐적 이동 불가

### 3.1 현상

- 훈련 타이머와 방수에 따른 화재 진화율 감소는 정상 작동한다.
- 돌발 아이콘은 이동할 수 있다.
- 최초 보고에서는 출동대와 구조대상자 이동 불가가 함께 언급됐으나, 재확인된 당시 핵심 증상은 출동대 토큰의 드래그만 되지 않는 현상이다. 구조대상자 동시 발생 여부는 다음 재현에서 다시 확인한다.
- 토큰의 상태 메뉴 등 다른 기능은 정상일 수 있다.
- 문제가 발생한 상태에서도 다른 출동대 토큰의 우클릭 메뉴를 열고 방수 기능을 새로 활성화할 수 있었다.
- 드래그 시 브라우저의 토큰 잔상도 나타나지 않았다. 따라서 실패 단계는 `drop`이나 좌표 계산 이전인 native `dragstart` 시작 구간이다.
- 항상 발생하지 않고 정상 사용 중 갑자기 발생한다.

### 3.2 증상 분리와 현재 판단

2026-08-06 브라우저 테스트에서 잔류 `ActionMode`가 출동대 이동을 잠그는 별도 결함은 재현했다. 그러나 사용자가 다시 확인한 실제 장애에서는 다른 토큰의 우클릭 메뉴와 방수 기능 진입이 정상 작동했다. 활성 `ActionMode` 상태라면 다른 토큰 우클릭은 메뉴를 열지 않고 기존 모드를 먼저 취소하므로, 이 재현은 실제 장애의 주원인으로 볼 수 없다.

1. **별도로 확인된 상태 잠금 오류**
   - 출동대는 어떤 `ActionMode`든 활성화되면 `draggable=false`가 된다.
   - 대기1단계에 있는 진압대에서도 `방수개시`를 선택할 수 있지만, 대기구역 키는 유효한 방수 대상 구역으로 판정될 수 없다.
   - 잘못된 지점을 클릭하면 아무 안내 없이 함수가 종료되고 `clearMode()`가 호출되지 않는다.
   - 자동 취소 시간도 없으므로 사용자가 ESC 또는 우클릭으로 취소할 때까지 이동 잠금이 계속된다.
   - 구조대상자는 구조 모드에서 `draggable=false`가 되며, 전체화면 선택 레이어가 활성화된 모드에서는 포인터 입력 자체가 차단될 수 있다.
2. **실제 장애의 우선 조사 대상 — HTML5 드래그 경로**
   - 출동대와 구조대상자는 모두 HTML5 `dragstart/dragover/drop`을 사용한다.
   - 클릭·우클릭은 되지만 이동만 실패하므로 포인터 전체 차단보다 `dragstart` 미발생·취소, payload 누락, `dragover/drop` 미수신을 구분해야 한다.
   - 두 카드에 `setDragGrabOffset()`이 추가됐고, 여러 드롭 영역이 `computeDropCenter()`로 동시에 변경됐다.
   - 돌발 아이콘은 이 경로를 사용하지 않으므로 정상 여부가 공통 드래그 경로의 정상성을 보장하지 않는다.
   - 잔상이 나타나지 않았으므로 드롭 처리와 좌표 계산은 이번 증상의 직접 원인에서 제외한다.
   - 장애 중 첫 우클릭에 메뉴가 열렸으므로 해당 렌더의 `mode.type`은 `null`이고, 같은 렌더에서 `draggable=true`다.
   - ESC 후에도 복구되지 않았으므로 잔류 ActionMode는 실제 장애 원인에서 제외한다.
   - 더블클릭 이동이 성공했으므로 `moveToken`, 토큰 상태와 구역 이동 로직은 정상이다.
   - 따라서 남은 실패 범위는 브라우저가 native `dragstart`를 발생시키지 않았거나 `dragstart` 핸들러 내부의 DataTransfer 처리에서 중단된 경우다.

확정된 판별 근거:

| 관측 | 배제 또는 확인되는 범위 |
|---|---|
| ActionMode 안내 없음, ESC 후 동일 | ActionMode 잠금 배제 |
| 다른 토큰 첫 우클릭에 메뉴 표시 | `mode.type === null`, 포인터 hit test 정상 |
| 다른 토큰 기능 실행 가능 | React 이벤트와 기능 상태 전이 정상 |
| 더블클릭 이동 가능 | `moveToken`과 토큰 Context 정상 |
| 돌발 아이콘 이동 가능 | 마우스·포인터 입력 정상, 별도 이동 경로 정상 |
| 드래그 잔상 없음 | native `dragstart` 시작 또는 핸들러 내부 실패 |

### 3.3 별도로 확인된 ActionMode 재현

재현 절차:

1. 진압대 토큰을 생성하고 대기1단계에 배치한다.
2. 토큰을 우클릭하고 `기능 → 방수개시`를 선택한다.
3. 대기 패널 등 유효하지 않은 지점을 클릭한다.
4. 토큰 이동을 시도한다.

관측 결과:

| 단계 | `draggable` | ActionMode 안내 | 결과 |
|---|---:|---|---|
| 방수개시 전 | `true` | 없음 | 이동 가능 상태 |
| 방수개시 직후 | `false` | `방수 지점을 클릭하세요` | 이동 잠금 |
| 잘못된 지점 클릭 후 | `false` | 계속 표시 | 모드가 종료되지 않음 |
| 시간 경과 후 | `false` | 계속 표시 | 자동 복구 없음 |
| ESC 취소 후 | `true` | 제거 | 즉시 복구 |

따라서 이 경로 자체는 반복 재현 가능한 상태 전이 결함이지만, 사용자가 보고한 실제 HTML5 드래그 장애와는 별도 항목으로 관리한다. 실제 장애는 드래그 시작·payload·드롭 수신 진단 정보를 확보한 뒤 원인을 확정한다.

- 새로고침 후에도 지속: 공통 드래그·드롭 계산과 DOM/CSS 충돌을 우선 조사한다.
- 특정 구역에서만 실패: 중첩 드롭 영역, `stopPropagation()`, 좌표 기준을 우선 조사한다.

### 3.6 개선 작업

#### P0-DRAG-01 진단 가능성 확보

- 개발 모드에서 현재 `ActionMode`, 선택 원본 토큰, 활성 메뉴·오버레이를 확인할 수 있게 한다.
- `dragstart`, `dragend`, `drop`, 취소 사유를 개발 로그로 기록한다.
- 최근 드래그 이벤트를 메모리 순환 버퍼에 보관해 장애 발생 뒤에도 `dragstart` 발생 여부, `DataTransfer types`, 마지막 `dragover/drop` 구역을 확인할 수 있게 한다.
- 진단 화면에서 토큰의 실제 `draggable` 속성, `data-dragging`, 현재 ActionMode와 마지막 드롭 결과를 한 번에 복사할 수 있게 한다.
- React 상태 변경과 DataTransfer 처리가 없는 최소 native draggable 진단 토큰을 개발 모드에 둔다. 장애 중 이 토큰에도 잔상이 없으면 브라우저·탭의 native DnD 상태, 진단 토큰은 정상인데 출동대만 실패하면 앱의 `dragstart` 핸들러를 원인으로 분류한다.
- 브라우저 종류·정확한 버전, localhost/Vercel, HMR 발생 횟수, 탭 실행 시간을 진단 정보에 포함한다.
- `draggable=false`, 잘못된 drop payload, 유효하지 않은 좌표를 구분한다.
- 사용자 피드백에 버전과 재현 절차가 함께 남도록 한다.

#### P0-DRAG-02 작업 모드 생명주기 정리

- 각 ActionMode에 성공, 취소, 잘못된 대상, 원본 삭제, 훈련 초기화 경로를 정의한다.
- 모든 종료 경로에서 `clearMode()`가 호출되는지 검증한다.
- 실행할 수 없는 구역에서는 `방수개시` 등 작업 모드 진입 버튼을 비활성화하고 사유를 표시한다.
- 잘못된 대상 클릭 시 모드를 계속 유지할지, 즉시 취소할지 정책을 정하고 사용자에게 결과를 안내한다.
- 모드가 일정 시간 입력 없이 유지되면 경고 또는 안전한 자동 취소를 제공한다.
- 모드가 참조하는 원본 토큰이 없으면 자동 해제한다.
- 훈련 설정 다시 불러오기와 Provider 재마운트 시 모드 초기화를 보장한다.
- 화면에 활성 모드와 명시적인 취소 버튼을 항상 표시한다.

#### P0-DRAG-03 드래그 가능 조건 분리

- 모든 ActionMode에서 출동대 드래그를 일괄 차단하는 조건을 제거하거나 필요한 모드로 한정한다.
- `canDragToken(mode, token)`과 `canDragVictim(mode, victim)`처럼 판정 규칙을 한 곳에 둔다.
- 메뉴 표시 상태와 실제 이동 금지 상태를 분리한다.

#### P0-DRAG-04 공통 좌표 보정 안전화

- `grabOffsetX/Y`, 토큰 크기, 드롭 좌표에 `Number.isFinite()` 검사를 추가한다.
- 값이 없거나 유효하지 않으면 기존의 카드 중심 기준 계산으로 안전하게 되돌린다.
- 좌표 저장 기준이 카드 중심인지 좌측 상단인지 타입과 함수명으로 명시한다.
- 중첩 드롭 영역은 자식에서 처리한 이벤트가 부모에서 다시 처리되지 않게 한다.

#### P1-DRAG-05 입력 방식 통합 검토

- HTML5 드래그와 사용자 정의 마우스 이동 방식의 장단점을 비교한다.
- 데스크톱·태블릿을 함께 지원하려면 Pointer Events 기반 공통 이동 컨트롤러를 검토한다.
- 입력 방식 교체는 P0 안정화와 회귀 테스트 완료 후 별도 작업으로 진행한다.

### 3.7 회귀 테스트 시나리오

다음 시나리오는 최소 수동 테스트와 브라우저 자동화 테스트에 모두 반영한다.

1. 출동대와 구조대상자를 대기 패널, A~D면, 건물 각 층 사이에서 이동한다.
2. 훈련 타이머가 진행되는 동안 연속으로 이동한다.
3. 방수개시 후 유효한 지점 선택, 잘못된 지점 선택, ESC 취소 각각 이후 `draggable` 복구와 실제 이동을 확인한다.
4. 대기구역·출동대현황처럼 방수할 수 없는 위치에서는 `방수개시` 진입 자체가 차단되는지 확인한다.
5. 송수 연결, 고가차·굴절차 전개, 구조 관련 선택 모드 각각 이후 이동한다.
6. 출동대·구조대상자 우클릭 메뉴를 열고 적용·취소한 뒤 이동한다.
7. 돌발 아이콘 상태 변경과 이동 후 출동대·구조대상자를 이동한다.
8. 직전대기·RIT처럼 부모와 자식 드롭 영역이 겹치는 구역으로 이동한다.
9. 드래그 도중 화면 밖 이동, ESC, 창 포커스 이탈 후 다시 이동한다.
10. 세션 복원과 훈련 설정 다시 불러오기 후 이동한다.
11. Chrome 계열 브라우저의 실제 마우스 입력으로 최종 확인한다.
12. 동일 시나리오를 localhost 개발 모드와 Vercel 배포본에서 비교하고, 장시간 실행·탭 비활성화·HMR 이후에도 native 진단 토큰과 실제 출동대가 모두 드래그되는지 확인한다.

## 4. P0 장애: 구조 처리와 임시의료소 상태 불일치

### 4.1 확인된 오류 — 수동 이동 후 `구조중` 잔류

현재 구조 처리는 출동대에 `구조중` 배지를 추가하고 임시의료소 카운트다운을 시작한다. 지정 시간이 끝나면 배지를 제거하고 직전대기로 자동 이동한다.

그러나 지정 시간 전에 출동대를 임시의료소 밖으로 수동 이동하면 타이머와 카운트다운만 삭제되고 `구조중` 배지는 제거되지 않는다. 타이머까지 취소되므로 자동 완료 경로에서도 배지가 제거되지 않아 영구 잔류한다.

영향 범위:

- 화면에 `구조중` 표시가 계속 남는다.
- `구조중` 배지가 있는 출동대는 이후 구조 출동대 선택 목록에서 제외될 수 있다.
- 일반 이동 카운트다운과 `구조중` 표시가 동시에 나타나 상태 의미가 충돌한다.
- 구조 처리 중 새로고침할 경우 의료소 타이머가 복원되지 않아 동일한 잔류 상태가 발생할 수 있다.
- 배지의 표시 문자열 `line1 === '구조중'`을 업무 상태 판정에 사용해 문구 변경과 중복 배지에 취약하다.

### 4.2 확인된 설계 충돌 — 설치 상태와 출동대 선택 혼합

임시의료소 헤더 버튼은 현재 세 가지 값을 한 자리에 표시한다.

- `미설치`
- `설치`
- 선택된 출동대명

임시의료소 안의 출동대를 클릭하면 `selectedUnit`에 출동대명이 저장되고 `isInstalled=true`가 되며, 헤더 버튼 문구가 출동대명으로 바뀐다. 이는 이벤트 전파로 우연히 발생하는 현상이 아니라 현재 코드에 명시된 동작이다.

문제점:

- 시설 설치 상태와 담당 출동대·소장 지정은 서로 다른 상태인데 한 버튼이 두 의미를 가진다.
- 출동대 토큰의 일반 클릭이 담당자 지정으로도 처리되어 사용자가 의도를 구분하기 어렵다.
- 기존 설정 상태인 `medicalPostChief`와 현재 `selectedUnit` 로컬 상태가 연결되지 않는다.
- 담당 대상을 토큰 ID가 아닌 표시 이름으로 저장해 중복 이름과 이름 변경에 취약하다.
- `isInstalled`와 `selectedUnit`이 컴포넌트 로컬 상태라 구조활동통계 화면으로 전환해 컴포넌트가 재마운트되면 초기화될 수 있다.
- 설치 해제 시 진행 중인 구조 처리의 허용·취소 정책이 정의되어 있지 않다.

### 4.3 권장 사용자 인터페이스

설치 상태와 담당자 지정을 분리한다.

- 헤더 상태 버튼은 항상 `설치` 또는 `미설치`만 표시한다.
- 담당 출동대 또는 임시의료소장은 별도 선택 컨트롤에 `소장 미지정` 또는 출동대명을 표시한다.
- 토큰 단순 클릭은 토큰 기능만 수행하고 담당자 지정은 명시적인 선택 컨트롤에서만 수행한다.
- 담당자는 표시 이름이 아니라 토큰 ID로 저장하고 화면에만 현재 이름을 표시한다.
- 설치 상태와 담당자 지정은 훈련 세션 상태로 관리하고 `runKey` 초기화 정책을 따른다.

제품 결정이 필요한 사항:

1. 임시의료소가 미설치 상태일 때 구조 명령을 허용할지
2. 구조 처리 중 임시의료소를 미설치로 바꿀 수 있는지
3. 지정 시간 전 수동 이동을 허용, 차단, 확인 후 허용 중 어느 방식으로 할지
4. 담당자를 `임시의료소장`으로 부를지 `운영 출동대`로 부를지

현재 사용 흐름을 기준으로 한 기본안은 **수동 이동 허용 + 구조 처리 상태 완전 정리 + 중단 로그 기록**이다.

### 4.4 개선 작업

#### P0-RESCUE-01 구조 처리 종료 경로 통합

- 타이머, 카운트다운, `구조중` 상태를 함께 정리하는 공통 함수를 만든다.
- 자동 완료, 수동 이동, 토큰 삭제, 훈련 초기화가 공통 종료 함수를 사용하게 한다.
- 수동 이동 시 `구조 처리 중단 후 수동 이동`처럼 원인을 구분해 로그를 남긴다.
- 동일 출동대에 `구조중` 상태가 중복 추가되지 않게 한다.

#### P0-RESCUE-02 구조 처리 상태 모델과 세션 복원

- 표시 문자열 기반 배지를 `rescue-in-progress` 같은 타입이 있는 업무 상태로 교체한다.
- 구조 대상, 시작 시각, 종료 예정 시각과 상태를 명시적으로 저장한다.
- 새로고침 시 종료 예정 시각을 기준으로 카운트다운을 복원하거나 만료 처리를 수행한다.
- 현재 위치와 구조 처리 상태가 불일치하면 안전한 정리 규칙을 적용한다.

#### P0-MED-01 설치 상태와 담당자 UI 분리

- 설치 버튼 문구를 `설치/미설치`로 고정한다.
- 임시의료소장 또는 운영 출동대 선택 UI를 별도로 제공한다.
- 토큰 클릭 이벤트에서 담당자 자동 지정 로직을 제거한다.
- 담당 토큰이 의료소를 벗어나거나 삭제되면 담당자만 자동 해제하고 설치 상태는 유지한다.

#### P0-MED-02 임시의료소 세션 상태 중앙화

- `isInstalled`, 담당 토큰 ID를 세션 범위 Context로 이동한다.
- 기존 `medicalPostChief` 설정과 런타임 담당자 상태의 역할을 정리한다.
- 임시의료소/구조활동통계 화면 전환에도 상태가 유지되게 한다.
- 설치·해제, 담당자 지정·해제를 구조화 로그에 기록한다.

### 4.5 회귀 테스트

1. 구조 명령 후 지정 시간이 지나면 `구조중`이 제거되고 직전대기로 자동 이동한다.
2. 지정 시간 전에 수동 이동하면 타이머, 카운트다운, `구조중`이 함께 제거된다.
3. 수동 이동한 출동대를 다른 구조대상자에게 다시 지정할 수 있다.
4. 구조 처리 중 새로고침 후 카운트다운이 복원되거나 정의된 만료 처리가 실행된다.
5. 설치 버튼을 눌러도 담당자 표시가 바뀌지 않고, 담당자를 선택해도 설치 버튼 문구가 출동대명으로 바뀌지 않는다.
6. 임시의료소와 구조활동통계 화면을 전환해도 설치·담당자 상태가 유지된다.
7. 담당 출동대가 의료소를 벗어나면 담당자만 해제되고 설치 상태는 유지된다.

### 4.6 완료 기준

- 구조 처리의 모든 종료 경로에서 타이머, 업무 상태, 화면 배지가 일치한다.
- `구조중` 잔류로 구조 출동대 재선택이 막히지 않는다.
- 설치 상태와 담당자 상태가 화면·코드·저장 구조에서 분리된다.
- 설치·담당자 상태가 화면 전환과 세션 복원 정책에 맞게 유지된다.
- 위 회귀 테스트가 수정 전 실패하고 수정 후 통과한다.
