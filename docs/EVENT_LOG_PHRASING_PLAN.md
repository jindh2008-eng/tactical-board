## 0. 목적

로그를 **실제 무전 멘트와 이동을 그대로 읽는 문장**으로 바꾼다.

지금 로그는 「누가 어디서 어디로」를 화살표로 적는다 — `펌프4 대기(풀) → 자원대기소`.
이건 데이터 구조를 그대로 문장에 옮긴 것이지 현장에서 오가는 말이 아니다.
무전 교신(STT)과 시간축으로 합칠 때([EVENT_LOG_PLAN.md](EVENT_LOG_PLAN.md) §0.3) 두 줄의 어휘가
서로 다르면 정렬은 되어도 대조가 안 된다.

그리고 **동시에 벌어진 일은 한 줄로 적는다.** 다섯 대가 같이 도착하면 다섯 줄이 아니라
`대기1단계 도착: 진압1대, 구급1대, 물탱크1` 한 줄이다. 무전도 그렇게 한 번 나간다.

`payload`(분석용 구조화 데이터)는 손실 없이 유지한다 — 묶음 줄도 `units[]` 로 대별 정보를
그대로 담으므로 분석에서 다시 펼칠 수 있다.

## 1. 착수 전 구조 — 코드로 확인한 값 (2026-09-10)

로그 창구는 [`context/LogContext.tsx`](../src/context/LogContext.tsx) 하나이고
**`addLog` 호출 1건 = 로그 1줄**이었다. 묶는 장치가 없었다.

`payload` 가 분석용 정본, `note` 가 표시용 문장인데 — **`move` 만은 note 가 아니라
`fromZoneId → toZoneId` 를 화면에서 조립했다**(`LogPanel` · `exportLog`). 화살표 표기의 출처가 여기였다.

### 1.1 도착 경로가 4개다 ★

이번 작업의 본체였다. 네 경로 전부 **토큰 단위로** `addLog` 했다.

| # | 경로 | 위치 | 성격 |
|---|---|---|---|
| 1 | 시간모드 타이머 | `TokenContext` 도착 이펙트 | **토큰마다 별도 `setTimeout`** — 서로 다른 태스크다 |
| 2 | 훈련 시작 즉시 배치(`arrivalSec<=0`) | 같은 이펙트 | 루프 안에서 대당 1회 |
| 3 | 착대 라벨 더블클릭 | `UnitStatusPanel` · `UnitAddPanel` | `for (const t of items) moveToken(...)` |
| 4 | 동승 펌프 자동 하차 | `TokenContext.moveToken` | `moveToken` 이 **자기를 재귀 호출**한다 |

4번 때문에 「호출부에서 묶기」가 성립하지 않는다 — 호출부는 펌프가 함께 움직인 것을 모른다.
1번 때문에 「같은 동기 실행 단위로 묶기」만으로도 부족하다.

### 1.2 나머지 세 지점

| 요구 | 착수 전 | 원인 |
|---|---|---|
| RIT = 임무지정 | `직전대기 → RIT` + `임무: RIT` **2줄** | `AFaceBottomZones` 가 `moveToken` 과 `toggleMissionTag` 를 잇달아 불렀다 |
| 송수 무전 문구 | `물탱크1 → 소화전3` | `WaterConnectionContext` 가 이름 둘을 화살표로 잇는 게 전부였다. **`LogPayload` 에 송수 kind 가 없었다** |
| 거점 한 줄 | 2줄 | `PlayPage` · `StandbyColumn` 의 `changeChief` 가 `addLog` 를 연달아 두 번 불렀다 |

## 2. 확정 규칙 (사용자 결정 2026-09-10)

### 2.1 이동 문구

| 목적지 | 출발지 | 문구 | 묶음 |
|---|---|---|---|
| 대기1단계 · 자원대기소 | 출동대현황 · 추가출동대 | `대기1단계 도착: 진압1대, 구급1대, 물탱크1` | ○ |
| 대기1단계 · 자원대기소 | 현장(직전대기·RIT·면·층·임시의료소 …) | `대기1단계 복귀: 진압1대` | ○ (도착과 **별도** 묶음) |
| 대기1단계 ⇄ 자원대기소 | 서로 | `구조1대 대기1단계 → 자원대기소 이동` | ✕ — 자리 옮김이다 |
| RIT | — | `진압1대 RIT 임무지정` | ✕ |
| 그 밖(직전대기·임시의료소·면·층·현장지휘소) | — | `진압1대 대기1단계 → 직전대기 이동` | ✕ |
| 출동대현황 · 추가출동대 | — | **로그 없음 + 직전 도착 철회(§2.2)** | — |

**분류는 목적지(와 출발지) 구역 키에서 파생한다** — `utils/logPhrase.ts` 의 `classifyMove()`.
기존 `move` payload 의 `fromZoneKey`/`toZoneKey` 만으로 다시 계산할 수 있다.

활동대(진압·구조·구급)는 무전 호칭대로 「대」를 붙여 부른다(`진압1` → `진압1대`). 차량은 이름 그대로다.
로그 안의 출동대현황 표기는 `대기(풀)` 에서 **`출동대현황`** 으로 바꿨다.

**RIT 는 공간이 아니라 임무다.** 판 위에서는 RIT 칸에 토큰을 놓는 조작이지만(`standby-rit`),
문장은 임무지정으로 적는다. 뒤따르는 `toggleMissionTag` 는 `{ silent: true }` 로 불러
`임무: RIT` 줄을 남기지 않는다 — 위치는 `move` payload 에 그대로 남으므로 분석 손실이 없다.

### 2.2 도착 철회 — append-only 전제가 깨지는 유일한 지점 ★

출동대현황·추가출동대로 되돌리는 조작은 **도착하지 않은 대를 도착으로 했다가 취소하는 경우**다.
실전에는 없는 일이므로 기록에서 지운다(사용자 확정).

```
대기1단계 도착: 진압1대, 구급1대, 펌프1, 물탱크1
  └ 구급1을 출동대현황으로 되돌림
대기1단계 도착: 진압1대, 펌프1, 물탱크1     ← 줄을 다시 쓴다
  └ 마지막 한 대까지 빠지면 줄 자체를 삭제
```

**안전조건 — 그 대의 가장 최근 흔적이 도착일 때만 거둔다.** 최신 로그부터 거슬러 올라가
그 대가 나오는 첫 줄이 도착 줄이면 철회하고, 다른 줄(이동·임무·송수·역할)이 먼저 나오면 멈춘다.
`도착 → 직전대기 이동 → 되돌리기` 라면 도착은 실제로 있었던 일이라 남긴다.
편성 기록(`dispatch-*`)은 출동대 목록을 통째로 담지만 활동이 아니라서 흔적으로 치지 않는다.

**동승 펌프는 따라 돌아오지 않는다.** 펌프를 함께 옮기는 로직은 출발지가 대기 박스일 때만 돈다
(`TokenContext.moveToken` — 대기 박스를 떠나는 순간이 하차다). 진압1을 대기1단계에서 되돌려도
펌프1은 대기1단계에 그대로 있고, 그러니 도착 줄에도 남는 것이 맞다.
펌프만 따로 되돌리면 펌프도 그 줄에서 빠진다. *(착수 전 초안에는 「함께 빠진다」고 적었으나 틀렸다.)*

> **로그가 사후 수정된다.** 지금까지 로그는 추가만 하는 배열이었다. 이번 변경에서
> 구조적으로 새로운 성질은 이것 하나뿐이다. 소비처(표시·CSV·PDF)는 전부 배열을 다시 읽으므로
> 영향이 없고, 세션 저장은 500ms 디바운스가 따라온다.

### 2.3 송수 문구

| from → to | 연결 | 해제 |
|---|---|---|
| 소화전 → 펌프·물탱크 | `물탱크1 44호 소화전 점령 / 중요물탱크 지정` | `물탱크1 44호 소화전 점령 해제 / 중요물탱크 해제` |
| 순환급수 → 펌프·물탱크 | `펌프1에 순환보수 실시` | `펌프1 순환보수 중단` |
| 펌프·물탱크 → 펌프·물탱크 | `물탱크1 펌프1에 급수 지원 / 1선펌프 지정` | `물탱크1 펌프1 급수 중단 / 1선펌프 해제` |
| 펌프·물탱크 → 고가·굴절 | `펌프1 고가1 급수 펌프 지정` | `펌프1 고가1 급수 중단` |
| 펌프·물탱크 → 연결송수구 | `펌프1 연결송수구 점령` | `펌프1 연결송수구 점령 해제` |
| 펌프·물탱크 → 진압대·구조대 | `진압1대 펌프1에서 수관전개` | **로그 없음** |
| 옥내소화전 → 진압대·구조대 | `진압1대 옥내소화전(3층)에서 수관전개` | **로그 없음** |

**주어가 규칙마다 다르다 — 의도한 것이다(사용자 확정).**
「점령」·「수관전개」는 물을 **받는** 쪽이 주어이고, 「급수 지원」은 **주는** 쪽이 주어다.

`/` 뒤는 **그 연결로 물을 받는 차**에 딸려 바뀐 급수 임무다. 「1선펌프」도 같은 규칙으로 붙는다
(사용자 예시는 소화전의 「중요물탱크」뿐이었으나, 임무 로그를 연결 줄로 옮긴 이상 1선도
같은 자리에 와야 기록이 빠지지 않는다).
연결로 설명되지 않는 임무 변화 — 순환칸 배치, 다른 대에 딸려 풀린 1선 — 는 종전처럼
`급수임무 지정/해제` 줄로 따로 남는다.

이름은 코드에 이미 있는 것을 그대로 쓴다 — 소화전은 `"44호 소화전"`, 순환급수는 `"44호 소화전 순환급수"`,
연결송수구는 `'연결송수구'`, 옥내소화전은 `"옥내소화전(3층)"`.

#### 송수 로그의 주인을 `WaterMissionBridge` 로 옮겼다 ★

「/ 중요물탱크 지정」을 같은 줄에 붙이려면 **연결·순환칸·토큰을 한꺼번에** 봐야 한다.
착수 전 초안은 `addConnection` 에서 `deriveWaterMissions()` 를 미리 돌리려 했으나,
순환칸(`HydrantCirculationProvider`)이 송수 Provider 보다 **안쪽**이라 닿지 않는다.

그래서 셋을 다 보는 [`WaterMissionBridge`](../src/components/shared/WaterMissionBridge.tsx) 가
**연결 목록의 앞뒤를 비교해** 생긴 연결·끊긴 연결마다 한 줄을 만든다.
`WaterConnectionContext` 는 이제 로그를 남기지 않는다. 대기1단계·직전대기로 들어가며 자동으로
풀리는 연결도 같은 경로로 잡힌다. 세션에서 되살아난 연결은 마운트 시점 목록을 기준으로 삼아
「방금 연결」로 다시 적지 않는다.

### 2.4 도착 줄 정렬

```
활동대   진압대 → 구조대 → 구급대
차량     펌프차 → 물탱크차 → 고가차 → 굴절차 → 구조차 → 화학차 → 배연차 → 산불진화차 → 지휘차
기타     general   (설정모드 extraUnits) · 모르는 종류
유관기관 agency
```

같은 종류 안에서는 이름의 숫자 순(`진압1` → `진압2`)이다.
**판 위 표시 순서(`utils/arrivalOrder.ts` typePriority — 진압>물탱크>구조>구급)와 다르므로
재사용하지 않고 별도 비교자를 둔다**(`compareUnitCallOrder`). 그걸 고치면 구역 안 토큰 정렬이 회귀한다.

### 2.5 거점 한 줄

```
자원대기소 지정, 소장: 지휘운전
임시의료소 설치, 소장: 진압1
```

첫 지명(= 설치)일 때만 한 줄로 합친다. payload 는 새 kind **`post-open { post, chiefTokenId, chiefLabel }`** —
`post-install` 에 소장을 끼우면 「설치만 한 경우」와 구분이 흐려진다.
이미 설치된 뒤의 지명·해제는 종전 `post-chief` 줄 그대로다.

## 3. 묶음 방식 — 「같은 태스크 = 한 묶음」 + 타이머 그룹화 ★

`LogContext.addArrivalLog()` 가 도착·복귀를 버퍼에 쌓고 **`queueMicrotask` 로 flush** 한다.
시각은 **첫 대가 들어온 시점**으로 찍는다(flush 시점이 아니라).

- §1.1의 경로 2·3·4는 전부 하나의 동기 태스크라 자동으로 묶인다.
  재귀 펌프 이동도 같은 태스크라 `대기1단계 도착: 진압1대, 펌프1` 로 함께 나온다.
- 경로 1(타이머)은 `scheduleArrivalGroup()` 으로 **도착 시각(`arrivalSec`, 세션 복원은 `targetAt`)별
  한 타이머**로 묶었다. 같은 착대는 같은 초라 한 콜백에서 처리된다. 도착 시각 자체는 종전과 같다.
- 「도착」과 「복귀」는 같은 버퍼를 쓰되 **따로 묶는다**(키에 mode 포함).

**시간창 방식을 쓰지 않은 이유.** `utils/arrivalGroup.ts` 의 표시용 10초 창을 그대로 쓰면
로그가 10초 늦게 찍히고, 짧게 잡으면 경계에서 갈라진다. 마이크로태스크는 지연이 없고 결과가 결정적이다.

**언마운트 때 버퍼를 비우지 않는다.** 착수 초안은 「cleanup 에서 버린다」였으나, StrictMode 의
개발 모드 가짜 언마운트가 flush 전 도착을 통째로 지우는 것을 실측했다(§10.3). 진짜로 내려간 뒤에
flush 가 돌아도 `setState` 는 아무 일도 하지 않으므로 지킬 것이 없다.

## 4. 문장 생성의 단일 출처 — `utils/logPhrase.ts`

`payload → 한 줄 문장` 함수들을 한 파일에 두고 **`addLog` 시점에 `note` 에 박는다.**
화면·CSV·PDF 는 `note` 만 읽는다(`move` 의 화살표 조립을 걷어냈다).
payload 없는 구버전 세션은 기존 경로로 폴백한다.

새 형식 `move` 는 payload 에 **`intent: 'move' | 'mission'`** 을 더 담는다. 분류 자체는 구역 키에서
파생하지만, 이 값이 있어야 「note 가 완성된 문장인가」와 CSV 유형 열(`이동`/`임무`)을 가를 수 있다.
구버전 저장분에는 없으므로 선택 필드다.

순수 헬퍼라 `.ts` 로 뒀다 — `.tsx` 로 만들면 `react-refresh/only-export-components` 기준선이 불어난다.

## 12. 출동대 칩 (2026-09-11)

문장 안의 출동대명을 **칩**으로 떼어, 판 위 토큰과 같은 색 계열로 그린다.
로그를 보고 판에서 그 대를 바로 찾게 하려는 것이다(사용자 결정 — 칩 방식).

```
[진압1대] 대기1단계 → 직전대기 이동
대기1단계 도착: [진압1대], [구조1대], [구급1대], [펌프1], [물탱크1], [한전]
[물탱크1] [펌프2]에 급수 지원 / 1선펌프 지정
```

### 12.1 설계

- **문장을 조각으로 만든다.** `logPhrase` 의 문장 함수가 `LogPart[]`(출동대 / 글자)를 돌려주고,
  `note` 는 조각을 이은 문자열이다 — **CSV·PDF 는 그대로다.** 조각은 로그의 선택 필드 `parts` 에 함께 저장한다.
- **화면에서 이름을 문자열로 찾아 쪼개지 않는다.** `펌프1` 이 `펌프10` 안에서도 걸리기 때문이다(L-5 와 같은 함정).
- **칩 색은 기록 시점의 토큰 색이다.** 차종으로 추정하면 수동 생성·색 변경 토큰이 틀린다 — 도착 묶음의
  `ArrivalUnitRef` 에 `color` 를 더했다.
- **칩 = 출동대.** 소화전·연결송수구·옥내소화전·순환칸은 칩으로 그리지 않는다.
- 칩 모양은 **옅은 배경 + 밝은 글자 + 1px 테두리**. 판 위 원색을 그대로 깔면 수백 줄이 시끄럽다.
  차량·유관기관은 판 위 배경이 로그 바탕과 거의 같아 **테두리가 곧 칩의 모양**이다(`LogPanel.css` `.log-chip`).
- 조각이 있는 이동 줄은 문장 전체를 토큰 색으로 칠하던 것을 걷고 **본문을 중립색**으로 둔다 — 색은 칩이 갖는다(§11 원칙 2의 첫 걸음).

### 12.2 적용 범위

| 줄 | 방식 |
|---|---|
| 도착·복귀 · 이동 · RIT 임무지정 | 조각(`parts`) |
| 송수 — 양쪽 출동대 | 조각. 설비 쪽은 글자 |
| 거점 첫 지명(설치) — 소장 | 조각. 자원대기소장은 이름으로 저장돼 같은 이름표의 토큰이 없으면 글자 |
| 상태(방수·임무·상태메시지) · 구조 · 칩 이전 이동 줄 | 기존 `tokenName` 을 칩으로 |

**아직 칩이 아닌 것** — 이름이 문구 안에 박혀 조각이 없는 줄이다: 단위지휘관 지정·편입·해제,
순환급수 배치·교대, 바스켓 탑승, 급수임무 지정/해제 줄 본문, 인명검색. 넓히려면 그 생산처도 조각을 만들어야 한다.

부수 변화 — 거점 줄의 소장 이름이 호칭으로 적힌다(`소장: 구조1` → `소장: 구조1대`).
자원대기소 `post-open` payload 의 `chiefTokenId` 도 이제 채운다.
