## 0. 이 문서의 위치 — 먼저 읽을 것

**현재 확정된 작업 범위는 훈련모드(무플) 하나다**([MASTER_PLAN.md](MASTER_PLAN.md) D-4). 설정모드 수정은 [DEFERRED_PROPAGATION.md](DEFERRED_PROPAGATION.md) §4의 **반영 순서 2번**에 놓여 있고, 그 문서의 규칙은 "무플 작업 중 설정모드는 고치지 말고 기록한다"이다.

따라서 이 문서는 **지금 실행하는 계획이 아니라, 실행 시점에 펼칠 설계안**이다. 세 가지 중 하나를 선택해야 한다.

| 선택 | 의미 | 영향 |
|---|---|---|
| **A. 무플 완성 후 착수** (문서 기본값) | DEFERRED §4 순서를 지킨다 | D-4 유지. 이 문서는 그때까지 대기 |
| **B. 순서를 앞당겨 지금 착수** | D-4의 "무플 하나만"을 사용자가 명시적으로 뒤집는다 | MASTER_PLAN §1에 D-7로 기록 필요 |
| **C. S-1(토큰)만 선반영** | 토큰 정의는 `/play`와 겹치지 않아 무플 작업을 막지 않는다 | 가장 위험이 낮은 절충안 |

**이 문서는 A를 전제로 쓰였으나, 2026-08-24 사용자 지시로 B가 선택됐다** — [MASTER_PLAN.md](MASTER_PLAN.md) **D-7**에 기록. 작업 브랜치는 `feat/settings-ui-redesign`이다. 단계 구분(S-0~S-2가 독립적으로 완결)은 그대로 유효하다.

설정모드가 `/play`와 **컴포넌트를 하나도 공유하지 않는다**는 실측 사실(DEFERRED §1.1)이 이 계획의 최대 자산이다. 설정모드를 아무리 크게 고쳐도 훈련모드가 깨지지 않는다. 단 하나의 접점은 상단 `app-nav`(P-4)이며, 이 계획은 §10에서 그것을 범위 밖으로 뺀다.

### 0.2 브라우저 실측 — §1에 없던 값

개발 서버에서 직접 쟀다.

```
뷰포트 1600px:  사이드바 200 + 본문 1116  →  본문 사용률 69.8%
훈련장 2560px:  사이드바 200 + 본문 1116  →  본문 사용률 43.6%
```

본문 `max-width: 1180px`가 고정이라 **화면이 커질수록 사용률이 떨어진다.**

**실제 렌더된 글자 크기는 7종뿐이다** — 11.1 / 11.4 / 12.45 / 13.05 / 13.95 / 15 / 18.75px. CSS에 22종의 원시값이 있지만 상당수가 덮여서 죽어 있다는 뜻이고, **토큰 이관의 실작업량이 CSS 숫자보다 작다.** 다만 최소 11.1px는 한글에 확실히 작다.

> ⚠ **정정 (08-24 (3)) — 위 문단의 "7종"은 한 화면만 잰 값이라 결론이 틀렸다.**
> S-0 기준선을 9개 화면 × 3개 폭 × 실 시나리오로 다시 쓸어 보니 **23종**이고
> **최소 9px**이다(11 / 9 · 9.3 · 9.6 · 9.75 · 9.9 · 10.2 · 10.8 · 11.1 · 11.25 · 11.4 · 11.7px가
> 12px 미만). CSS 원시값 28종과 큰 차이가 없다 — **"덮여서 죽어 있다"는 관찰은
> 그 화면에만 해당했고, 토큰 이관 작업량은 CSS 숫자대로 봐야 한다.**
> 화면별 최소값도 6종(건물)에서 14종(체크리스트)까지 벌어진다.
> 실측: [docs/baseline/before/audit.json](baseline/before/audit.json).

### 0.3 §1이 놓친 위험 두 가지 ★

**(1) `--color-border`는 전역이고 훈련모드와 공유한다.** §1.3은 "1.58:1"을 최대 결함으로 지목하지만 이 토큰이 어디 정의됐는지는 적지 않았다 — `src/App.css:16`의 `:root`다.

```
설정모드 CSS의 var(--color-border):  103건
훈련모드 CSS의 var(--color-border):   11건
```

`:root` 값을 고치면 훈련모드가 같이 바뀌어 **D-4를 깬다.** §5.1의 `.settings-page` 스코프 방식은 취향이 아니라 **필수 격리 조건**이며, S-2의 실제 내용은 "hex 128개 치환"이 아니라 **"`var(--color-*)` 사용처 362건을 `--set-*`로 재지정"**이다. 분량을 다시 잡아야 한다(§8).

**(2) 정의되지 않은 토큰 4곳.** `--color-surface-raised`와 `--color-input-bg`는 어디에도 정의돼 있지 않고 폴백만 동작한다 — `UnitStatusPanel.css:44,116` · `TagPresetPanel.css:30,125`. 토큰 체계를 세울 때 실제로 채울 자리다.

## 1. 현상 진단 — 코드 실측

감상이 아니라 숫자로 시작한다. 아래는 2026-08-22 기준 코드에서 직접 센 값이다.

### 1.1 규모

| 항목 | 값 |
|---|---|
| 설정모드 TSX | 11개 파일 · **3,087행** |
| 설정모드 CSS | 11개 파일 · **3,593행** |
| 화면(섹션) 수 | 9개 (4개 그룹) |
| 가장 큰 패널 | `ChecklistSetupPanel.tsx` **1,020행**, 로컬 `useState` **20개** |

> ⚠ **정정 (08-24 (5)) — 위 CSS 집계는 한 파일을 빠뜨렸다.** [`BuildingConfigPanel.css`](../src/components/building/BuildingConfigPanel.css) **448행**이 디렉터리가 `building/`이라 `src/components/settings/*` 글로브에서 빠졌는데, 이 컴포넌트를 import하는 곳은 `SettingsPage.tsx` 하나뿐이라 **설정모드 전용이다.** 실제 규모는 **12개 파일 · 4,041행**이고, §1.2의 값 산포 집계도 그만큼 과소하다.

### 1.2 디자인 시스템 부재 — 값의 산포

| 속성 | 서로 다른 값의 개수 | 비고 |
|---|---|---|
| `font-size` | **20종** (0.60rem ~ 1.25rem) | html 15px 기준 **9.0px ~ 18.8px** |
| `padding` | **51종** | 4/8px 리듬 없음 |
| `border-radius` | **10종** (2·3·4·5·8·10·50%) | 같은 층위의 카드끼리도 다름 |
| 하드코딩 hex | **121개** | 토큰 밖에서 직접 색을 씀 |

3,593행 CSS에 51가지 패딩과 20가지 글자 크기가 있다는 것은 **디자인 시스템이 없다는 뜻**이고, 화면이 "직접 만든 것처럼" 보이는 근본 원인이다. 개별 화면의 미감 문제가 아니다.

`SettingsPage.css` 하단의 "패널 공통 보정" 블록(약 90행)이 이미 이 문제를 후행 처리로 덮고 있다 — `[class*="__group-title"]` 같은 와일드카드 선택자로 다른 파일의 글자 크기를 되돌린다. **증상 치료가 코드에 남아 있다는 것 자체가 진단이다.**

### 1.3 색 — 대비 실측

| 조합 | 대비 | 판정 |
|---|---|---|
| `--color-text` `#c8d8e8` on surface | 12.67:1 | ✅ |
| `--set-text-strong` `#e2ecf6` on surface | 15.41:1 | ✅ |
| `--set-text-dim` `#8aa8c4` on surface | 7.44:1 | ✅ |
| `--color-text-dim` `#6a8aaa` on surface | **5.11:1** | ⚠ AA 통과, 그러나 0.62rem(9.3px)에 쓰임 |

**테두리 1.58:1이 이 화면의 가장 큰 시각적 결함이다.** 입력창·카드·표의 경계가 사실상 보이지 않아, 화면이 "정리되지 않은 텍스트 덩어리"로 읽힌다. 고급스러움은 여백과 폰트보다 **경계의 정확성**에서 나온다.

교정 후보: `#54697f` → surface 대비 **3.25:1**, bg 대비 3.46:1.

### 1.4 정보 구조 — 색이 의미를 배신한다

`SettingsLibraryPanel`의 상단 바에는 버튼 6개가 있고, 각자 다른 색을 **토큰 밖에서** 쓴다.

| 버튼 | 배경 | 뜻하는 바 | 문제 |
|---|---|---|---|
| 저장 | `#4433aa` 보라 | primary | 앱 액센트 `#4488cc`와 무관한 색 |
| 다른 이름으로 | `#252535` | 중립 | |

| 저장 목록 | `#252535` | 중립 | |
| 내보내기 | `#1a3040` 파랑 | 중립 | 색이 위계를 만들지 않고 소음만 만듦 |

**되돌릴 수 없는 파괴적 동작이 초록색이고, 일상적인 저장이 보라색이다.** 이것은 취향 문제가 아니라 사고 유발 설계다. 한 화면에 CTA는 하나여야 하고, 파괴적 동작은 위험색으로 **그리고 공간적으로** 분리돼야 한다.

### 1.5 상호작용 — 저장 모델이 사용자에게 보이지 않는다

`settingsStore.tsx`를 읽으면 저장이 **2단 구조**임이 드러난다.

```
편집 → (모든 변경마다 자동) saveWorkingPresets()  → 작업본, 새로고침해도 살아남음
     → (「저장」버튼을 눌러야)  saveSettings()      → 이름 붙은 설정 세트
     → (「훈련 세팅」을 눌러야)  훈련모드에 반영        → D-6 M-1
```

즉 **세 개의 서로 다른 "저장됨"이 존재하는데, 화면은 이 셋을 구분해 보여주지 않는다.**

| 결함 | 근거 |
|---|---|
| 미저장 변경 표시 없음 | `settingsStore.tsx` 전체에 `dirty`/`isDirty` 상태 **0건** |
| 이탈 경고 없음 | `beforeunload` 핸들러 **0건** |
| 반영 여부 표시 없음 | `훈련 세팅` 버튼은 `PlayPage.tsx:528`에만 있다 — 설정모드에서는 내 변경이 훈련에 갔는지 알 길이 없다 |
| 저장 피드백 | `저장됨 ✓` 1.5초 플래시 하나뿐 |

훈련 직전 시나리오를 고치는 사용자가 **"내가 방금 고친 게 반영됐나?"에 답할 수 없다.** 지휘훈련 도구에서 이것은 미감이 아니라 신뢰성 문제다.

### 1.7 레이아웃 — 화면을 절반만 쓴다

```
사이드바 200px + 본문 max-width 1180px = 1380px
훈련장 PC 기준 화면폭        = 2560 CSS px   (RESPONSIVE 계획 §0)
                              ────────────
남는 공백                    ≈ 1180px (46%)
```

`--ui-scale`은 `/play`에만 적용되고 설정모드는 **반응형 범위 밖**이다(DEFERRED P-5). 결과적으로 큰 화면에서는 오른쪽 절반이 비고, 작은 화면에서는 대응 없이 붕괴한다. 표 형태인 구조대상자·출동대 화면은 넓은 화면에서 특히 손해다.

## 3. 설계 원칙 — "지휘훈련 전문가가 만든 것"의 정의

미감 형용사로는 검증할 수 없다. 네 개의 검증 가능한 원칙으로 번역한다.

### 원칙 1. 설정모드는 **저작 도구**이지 대시보드가 아니다

사용자는 여기서 훈련 시나리오를 **쓴다**. 최적화 대상은 화려함이 아니라 **입력 속도와 오입력 방지**다. 밀도는 높게, 장식은 없게. (design dial: variance 3 / motion 3 / density 7)

### 원칙 2. 훈련모드와 **같은 언어, 다른 문장**

두 모드는 같은 팔레트·같은 폰트를 쓰되, 성격은 갈라야 한다.

| | 훈련모드 | 설정모드 |
|---|---|---|
| 성격 | 실행 · 읽기 중심 · 원거리 판독 | 저작 · 입력 중심 · 근거리 정밀 |
| 밀도 | 낮음 (요소가 크고 명확) | 높음 (한 화면에 많이) |
| 배율 | **스테이지**(고정 캔버스 + `transform: scale()`) | **고정 스케일 + 브레이크포인트** |
| 색 강조 | 상태(화재·구조)를 색으로 | 액센트 1색 + 위험색만 |

원칙 2가 P-5("무플의 배율 규약을 설정모드에 이식")에 대한 이 계획의 답이다 — **이식하지 않는다.**

> ⚠ **2026-08-24 정정.** 이 절이 쓰인 시점의 "무플의 배율 규약"은 `--ui-scale`이었으나 **그것은 이미 제거됐다**(정의 0건, 죽은 참조 94건 — 전부 훈련모드 쪽이고 설정모드에는 0건). 현행은 `StageRoot`의 고정 캔버스 + `transform: scale()`이고, [SCREEN_STAGE_PLAN.md](SCREEN_STAGE_PLAN.md) §5가 이미 "설정모드는 스테이지를 쓰지 않는다"로 같은 답을 냈다.
>
> 결론은 같지만 **근거가 더 강해졌다: 배율은 F-5를 못 고친다.** 스테이지를 이식하면 2560px에서 배율 1.0이 되어 지금과 똑같이 1116px만 쓰고, 1600px에서는 배율 0.625로 글자가 15px→9.4px로 더 작아진다. 균일 확대·축소는 열을 늘릴 수 없다. "본문 사용률 80%"는 `max-width`를 푸는 문제다. 덧붙여 스테이지는 contain-fit 고정 캔버스라 세로로 길게 스크롤되는 체크리스트·출동대 화면과 구조적으로 맞지 않는다.
>
> **Q-1은 브레이크포인트로 확정됐다**(D-7).

### 원칙 3. 상태는 **항상 보인다**

미저장·저장됨·훈련 반영됨. 이 세 상태는 추측이 아니라 화면에 상시 표기한다.

### 원칙 4. 파괴는 **어렵게, 되돌릴 수 있게**

신규 작성·삭제는 위험색 + 공간 분리 + 확인. 가능하면 되돌리기(Undo)를 준다.

## 4. 화면 구성 재설계안

### 4.1 정보 구조 — 9개를 4단계로 다시 묶는다

현재 사이드바는 `현장 / 자원 / 진행 / 검토` 4그룹 9항목이다. 묶음 자체는 합리적이지만 **"무엇을 정의하는가"** 기준이라 **"어떤 순서로 하는가"**를 알려주지 않는다. 처음 쓰는 사람은 어디서 시작할지 모른다.

**시나리오 저작 순서**로 재배열한다.

```
1  현장          건물 · 소방시설  →  현장요소  →  구조대상자
2  자원          출동대  →  임무·상태 프리셋  →  상태 메시지
3  진행          체크리스트  →  지휘절차
4  검토          시나리오 예측
```

순서는 그대로 두되 **세 가지를 더한다.**

- **단계 번호**를 그룹 라벨에 붙인다 — 순서가 있는 작업임을 드러낸다.
- **완료 배지**를 각 항목에 붙인다 — 예: `출동대 · 12` / `구조대상자 · 0` (미입력이면 흐리게 + 경고점).
- **사이드바 하단에 준비도 요약**을 고정한다 — "훈련 실행 가능 / 출동대 미등록" 등.

이것이 이 계획에서 **가장 값이 큰 변경**이다. 시각 정리보다 "지금 무엇이 비어 있는가"를 알려주는 쪽이 전문 도구의 인상을 만든다.

### 4.2 레이아웃 — 3열 고정에서 폭 적응형으로

```
┌───────────────────────────────────────────────────────────────────────┐
│  설정 파일 바   [설정명 ▾] [상태칩: 미저장]     [저장] ⋯ [신규]      │  56px 고정
├──────────────┬────────────────────────────────────────────────────────┤
│              │  ← 화면 제목 + 설명 (sticky)                           │
│  1 현장      │ ┌────────────────────────┬───────────────────────────┐ │
│   건물 ✓     │ │                        │                           │ │
│   현장요소 3 │ │   주 편집 영역          │  보조 영역(넓을 때만)      │ │
│   구조대상자!│ │                        │  · 미리보기 / 요약         │ │
│              │ │                        │  · 도움말                 │ │
│  2 자원      │ └────────────────────────┴───────────────────────────┘ │
│   ⋮          │                                                        │
│              │                                                        │
│ ──────────── │                                                        │
│ 준비도 4/6   │                                                        │
└──────────────┴────────────────────────────────────────────────────────┘
   240px          유동 (max 1680px)          360px (≥1800px에서만 등장)
```

**브레이크포인트 3단**

| 폭 | 사이드바 | 본문 | 보조 열 |
|---|---|---|---|
| < 1280px | 아이콘+라벨 축소 (또는 상단 탭으로 접힘) | 100% | 없음 |
| 1280–1799px | 240px | 유동, max 1180px | 없음 (현재와 동일) |
| **≥ 1800px** | 240px | 유동, **max 1680px** | **360px** |

훈련장 PC(2560px)에서 46% 공백이 사라지고, 표 화면(구조대상자·출동대 목록)이 실제로 넓어진다. 보조 열에는 화면별로 다른 것이 들어간다.

| 화면 | 보조 열 내용 |
|---|---|
| 건물·소방시설 | 건물 단면 축소 미리보기 |
| 출동대 | 도착 순서 타임라인 |
| 구조대상자 | 층별 분포 요약 |
| 체크리스트 | 항목 타입 설명 + 섹션 개요 |
| 그 외 | 도움말 (없으면 열 자체를 숨김) |

### 4.3 화면 헤더 — sticky 제목 + 화면 단위 동작

현재 제목·설명이 스크롤과 함께 사라진다. 긴 화면(체크리스트·출동대)에서 자신이 어디에 있는지 잃는다.

- 제목 줄을 **sticky**로 고정하고, 스크롤 시 높이를 줄인다(설명 숨김).
- 제목 줄 오른쪽에 **화면 단위 동작**을 둔다 — "이 화면 초기화", "전체 펼치기/접기" 등. 지금은 이런 동작이 갈 자리가 없어 패널 안에 흩어져 있다.

## 7. 핵심 상호작용 재설계

### 7.1 저장 모델을 화면에 드러낸다 (F-3)

`settingsStore`에 **파생 상태** 셋을 추가한다. 저장 로직은 건드리지 않는다.

```ts
isDirty:   작업본 ≠ 이름 붙은 설정 세트   // 저장 필요
isApplied: 작업본 === 훈련에 반영된 스냅샷  // 훈련 세팅 필요 (D-6 M-1)
lastSavedAt / lastAppliedAt
```

`isDirty`는 현재 상태와 `settingsList[activeSettingsId]`의 **얕은 비교**로 얻는다(직렬화 비교는 매 입력마다 돌면 비싸다 — 필드 단위 비교 + 디바운스).

상단 바에 **상태 칩** 하나를 둔다.

| 상태 | 표기 | 색 |
|---|---|---|
| 저장 필요 | `● 미저장 변경` | `--set-warn` |
| 저장됨, 훈련 미반영 | `● 저장됨 · 훈련 미반영` | `--set-text-dim` |
| 저장 + 반영 완료 | `✓ 훈련에 반영됨 14:32` | `--set-ok` |

그리고 **`beforeunload` 경고**를 `isDirty`일 때만 건다.

> ⚠ **D-6 M-1/M-2와의 정합**: 설정모드에 `훈련 세팅` 버튼을 놓지 **않는다**. 반영 시점은 오직 `/play`의 버튼 하나여야 한다(M-1). 설정모드는 *반영되지 않았음을 알려주기만* 한다. 훈련 중(`running`)에는 M-2에 따라 설정모드 진입 자체가 막히므로 이 칩은 `idle`/`ended`에서만 의미를 갖는다.

### 7.2 준비도 검사 (§4.1의 배지·요약을 뒷받침)

`utils/scenarioReadiness.ts`를 새로 만든다. 순수 함수 하나면 된다.

```ts
type Check = { id: string; label: string; level: 'block' | 'warn'; ok: boolean; section: SettingsSection };
function checkReadiness(settings): Check[]
```

초기 검사 항목(확정 아님, §11 Q-2):

| 검사 | 수준 |
|---|---|
| 출동대 1개 이상 등록 | block |
| 화재 층이 건물 층수 범위 안 | block |
| 도착 시간이 모두 0보다 큼 | warn |
| 구조대상자 0명 | warn |
| 체크리스트 항목 0개 | warn |
| 지휘절차 선택 레벨이 비어 있음 | warn |

결과는 사이드바 배지 · 하단 준비도 요약 · 「시나리오 예측」 화면 상단에 함께 쓴다. **한 번 계산해 세 곳에서 쓴다.**

### 7.3 체크리스트 화면 — 점진적 공개 (progressive disclosure)

`ChecklistSetupPanel`은 항목 타입이 7종이고, 타입에 따라 추가 폼의 모양이 달라져 `useState`가 20개다. 지금은 **모든 입력이 항상 펼쳐져 있다.**

- 항목 추가를 **한 줄 + 타입 선택**으로 접고, 타입을 고른 뒤에만 그 타입의 옵션을 편다.
- 타입 선택을 세그먼트 7개 나열 대신 **드롭다운 + 최근 사용 3개**로 바꾼다.
- 전환 상태 20개를 **타입별 판별 유니온 1개**(`draftItem: DraftItem | null`)로 합친다. 화면 정리와 상태 정리가 같은 작업이다.

이 화면 하나가 §8 S-5를 통째로 차지한다.

### 7.4 파괴적 동작 정리 (F-4)

| 동작 | 현재 | 변경 |
|---|---|---|
| 신규 작성 | 초록 버튼, 다른 버튼 사이 | `danger` variant + **구분선 뒤 오른쪽 끝**으로 분리 |
| 저장 | 보라 `#4433aa` | `primary` = `--set-accent` |
| 내보내기/가져오기 | 파랑 | `ghost` (중립) + `⋯` 오버플로 메뉴로 이동 |
| 설정 삭제 | 확인창 | 확인창 + **삭제 후 5초 되돌리기 토스트** |

상단 바에 노출되는 버튼을 **저장 / 다른 이름으로 / 저장 목록 / ⋯** 4개로 줄인다. 내보내기·가져오기·신규 작성은 `⋯` 안으로 넣는다 — 훈련 준비 중 오조작 경로를 줄이는 것이 목적이다.

### S-5 완료 (2026-08-24 (9)) — 원시 font-size·border-radius 0건, 클릭 타깃 8개 화면 0건

**토큰 이관 (기계적)** — 12개 파일의 원시 `font-size` 151건·`border-radius` 103건을 `--set-*`로 재지정했다. 매핑 근거는 html 15px 기준 px 환산 후 §5.1의 5단 타입 스케일(title/lg/md/sm/xs) 중 가장 가까운 것을 골랐고, **12px 미만은 전부 xs(12px)로 올렸다** — 원시값의 62%(93/151)가 여기 해당했다. `border-radius`는 3단(sm 4 / md 6 / lg 10)에 배정했고, `50%`·`0`은 이미 허용 목록에 있어 손대지 않았다(`0`은 이번에 추가로 허용).

**결과 — 8개 화면(시나리오 예측 제외) 전부 정확히 5종, 최소 12px.** §9 목표(≤6종, ≥12px)를 정확히 채웠다. stylelint 억제 258건(`declaration-property-value-allowed-list`)이 **0건**이 됐다 — 기준선 280 → 22.

**클릭 타깃 — 446건 → 8개 화면 0건.** 두 갈래로 나눠 처리했다.

- **직접 확대**(체크박스·라디오·아이콘 버튼 대다수): `vsp__stair-cb`(15→24px), `checklist-setup__link-cb`(13→24px), `dsp__radio-label input`(기본→24px) 등 native 컨트롤은 실제 렌더 크기를 24px로 올렸다. WCAG 2.5.8(Target Size Minimum)의 24×24 CSS px를 하한으로 잡았다 — 설정모드는 PC 마우스 전용(D-1)이라 터치용 44px(2.5.5 AAA)는 과하다.
- **히트 영역 확장**(`tag-preset-panel__swatch-btn`, 100건): 색 스와치를 24px 원으로 키우면 팔레트가 점 무더기가 된다. 시각 크기(14px)는 그대로 두고 `::before`로 클릭 판정 영역만 26px로 넓혔다 — `--set-h-btn-sm`(§5.1)이 이미 문서화한 "표 안 인라인 버튼" 패턴과 같다.

이 두 번째 패턴을 쓰면서 **감사 스크립트 자체의 사각지대를 하나 더 잡았다.** `getBoundingClientRect()`만 재는 원래 로직은 `::before` 확장을 전혀 credit하지 않아, 실제로는 접근 가능한 스와치 100개가 전부 "작은 타깃"으로 오탐됐다. `::before`가 `position: absolute`이고 `inset`이 네 변 모두 숫자로 잡히는 단순한 경우에 한해 유효 크기를 계산하도록 `measure()`를 고쳤다([scripts/settings-ui-audit.mjs](../scripts/settings-ui-audit.mjs)). 이 사각지대는 S-3에서 만든 `SetIconButton--sm`도 똑같이 갖고 있었다 — 지금까지의 감사 수치가 그 컴포넌트 몫만큼 실제보다 나쁘게 나오고 있었다는 뜻이다.

**빈 상태** — 8개 화면 중 `CommandProcedurePanel`만 카테고리 0건일 때 안내문이 없던 것을 발견해 다른 패널과 같은 형식으로 추가했다(`cp-panel__empty`).

**키보드 접근성** — 클릭만 되고 포커스가 닿지 않던 `<span onClick>` 두 곳(체크리스트 섹션 제목, 지휘절차 카테고리 제목 — 둘 다 "클릭하여 수정" 인라인 편집 트리거)을 `<button>`으로 바꿨다. `<span>`은 애초에 감사 스크립트의 클릭 타깃 검사 대상도 아니었다 — 대상 선택자(`button, [role="button"], a, input, select, textarea, summary`)에 안 걸리는 요소였기 때문에 지금까지 한 번도 잡힌 적이 없었다.

> ⚠ **남은 한계.** 섹션·카테고리·체크리스트 항목의 드래그 재정렬 손잡이(`*__drag-handle`, 4곳)는 여전히 키보드로 닿지 않는다. 재정렬 자체가 아니라 다른 모든 동작(추가·수정·삭제)은 키보드로 가능하므로 §8.1의 "키보드로 전 항목 도달"을 완전히 충족한 것은 아니다 — 순서 변경만 키보드 대안(위/아래 버튼 등)이 없다. 드래그 재정렬에 키보드 대안을 붙이는 작업은 규모가 있어 별도 항목으로 남긴다.

### 적용한 해법

순서가 뜻을 갖는지로 나눴다. 지휘절차·체크리스트는 드래그로 순서를 바꾸므로 여러 열로 접으면 "다음 항목"이 어디인지 읽히지 않는다. **접지 않고 상한만 둔다.**

- 순서 있는 목록 → `max-width: var(--set-row-max)` (34rem)
- 여러 열 표 → `max-width: var(--set-table-max)` (68rem)
- 순서 없는 목록 → 손대지 않음 (이미 `auto-fill`로 접힌다)

상한은 **패널 루트 한 곳에만** 건다. 안쪽 상자에도 같이 걸면 헤더·목록·추가줄의 세로선이 어긋나고, 같은 숫자가 두 곳에 생겨 결국 갈라진다.

## 12-B. 설정모드 이원화 — 시나리오 / 전체 설정 (2026-08-25)

설정모드는 성격이 다른 두 가지를 한 사이드바에 섞어 놓고 있었다.

| | 시나리오 | 전체 설정 |
|---|---|---|
| 화면 | 건물·소방시설 · 현장요소 · 구조대상자 · 출동대 · 체크리스트 | 지휘절차 · 상태 메시지 · 임무·상태 프리셋 |
| 저장 | `SettingsSet` (이름 붙여 저장, 파일 단위) | 각자 독립 localStorage 키 |
| 시나리오 전환 시 | 덮어쓴다 | **유지된다** |

**분할은 이미 코드에 있었다.** `settingsStore.tsx` 의 `loadSettings`·`newSettings` 가 이 셋만 건드리지 않는다 — 주석도 그렇게 적혀 있었다. UI만 그 사실을 숨기고 있었고, 그래서 세 가지가 어긋나 있었다.

| 어긋난 것 | 증상 | 조치 |
|---|---|---|
| `SettingsSet` 에 전역 3종을 같이 저장 | 저장은 되는데 불러올 때 무시되는 **죽은 데이터**가 모든 파일에 들어감 | 쓰기 중단 + `@deprecated`. `stripGlobalConfigs()` 로 구버전 잔재 정리 |
| `buildSnapshot` 에 전역 3종 포함 | 상태 메시지를 고쳤을 뿐인데 시나리오가 "미저장 변경" | 스냅샷에서 제외 |
| 준비도가 8개 화면 전부 집계 | "8/8 인데 출동대가 비어 있는" 상황이 성립 | `SCENARIO_KEYS` 5개만 집계 |

### 메뉴 구조

한 사이드바를 유지하고 **위치로** 가른다. 탭 전환으로 나누지 않은 이유는 체크리스트의 "지휘절차에서 불러오기" 때문이다 — 두 구역을 오가는 작업이 실제로 자주 일어나서, 탭이면 그 왕복마다 컨텍스트가 끊긴다.

```
파일 바 (현재 시나리오 · 저장 · 저장 목록)
  건물 · 소방시설
  현장요소
  구조대상자
  출동대
  체크리스트
  ─────────────           ← 얇은 선
  시나리오 예측
  시나리오 준비도  5/5
════════════════════════  ← 진한 구분선
  전체 설정 · 모든 시나리오 공통
    지휘절차 / 상태 메시지 / 임무·상태 프리셋
```

- **그룹 라벨(현장 / 자원 / 진행 / 검토)과 단계 번호는 제거했다.** 공통 설정을 아래로 내보내고 나니 여섯 항목이 3 / 1 / 1 / 1 로 남았는데, **한 개짜리 묶음은 묶음이 아니다** — 라벨이 정보를 주지 않고 자리만 먹었다. §4.1 이 번호로 해결하려던 "어디서 시작할지 모른다"는 문제는 위아래 순서가 그대로 맡는다.
- **남은 선은 시나리오 예측 위 한 곳뿐.** 위 다섯은 입력 화면이고 준비도 집계 대상이지만 예측은 읽기 전용 검토 화면이라 집계에서 빠진다(`SCENARIO_KEYS`). 없앤 라벨과 달리 이 선은 사실을 담는다.
- **전체 설정에는 라벨을 남겼다.** 이쪽 라벨은 묶음 이름이 아니라 **규칙**("모든 시나리오 공통")을 말한다 — 없으면 왜 따로 떨어져 있는지 알 방법이 없다.
- **준비도는 진한 구분선 위.** 시나리오 화면만 세는 숫자라, 전체 설정 아래에 두면 어느 쪽 요약인지 안 읽힌다.
- **<1280px 가로 탭**에서는 위치로 못 가르므로 별도 줄 + 앞머리 라벨로 경계를 유지한다. 예측 앞 구분선은 세로선으로 돌린다.

### 파일 입출력 이원화

기존 "내보내기/가져오기"는 실제로는 **저장된 시나리오 전부 + 공통 설정**을 담는 백업이었는데 이름이 그렇게 읽히지 않았다. 시나리오 하나를 주고받으려던 사람이 상대 설정을 통째로 덮을 수 있는 구조였다.

| 메뉴 | 담는 것 | 동작 |
|---|---|---|
| 이 시나리오 내보내기 | 시나리오 1건 (`ScenarioFile`, `kind` 로 식별) | 파일명 = 시나리오 이름 |
| 시나리오 가져오기 | 위 파일 | **덮어쓰지 않고 목록에 추가**. 이름 충돌 시 "(2)" |
| 전체 백업 | 시나리오 전부 + 공통 설정 (`SettingsExport`) | 기기 이전·복구용 |
| 백업에서 복원 | 위 파일 | 현재 내용 대체 — 확인창 |

`<input type="file">` 을 둘로 나눴다. 하나를 돌려 쓰면 백업 파일이 시나리오 경로로 들어가 조용히 엉뚱한 일이 벌어진다.

### 검증

브라우저 실측으로 확인했다 — 공통 설정(상태 메시지)을 수정해도 저장 상태 칩이 `저장됨` 그대로였고, 시나리오 값(대상명)을 고치자 `미저장 변경`으로 바뀌었다. 수정한 공통 값은 `tacticalBoardUnitStatus` 에만 들어갔고 `tacticalBoardSettingsList` 에는 섞이지 않았다.

## 12-C. 시나리오 레일 — 체크리스트를 우측 상주로 (2026-08-25)

### 왜

체크리스트 항목 타입은 **도착 · 화재 · 출동대 · 구조대상자**를 직접 참조한다. 그런데 체크리스트가 별도 화면이라, 항목을 쓰려면 출동대·건물을 확인하러 갔다 와야 했다. 더 나쁜 건 **출동대를 지우면 그걸 참조하는 체크리스트 항목이 깨지는데 다른 화면이라 안 보인다**는 것 — 편의가 아니라 정합성 문제다.

동시에 §12-A·§12-B 이후에도 남아 있던 문제를 구조적으로 해결한다. 화면마다 내용 끝나는 x좌표가 **782 / 1,275 / 2,507** 로 튀었는데(@2560), 우측이 늘 레일로 차 있으면 좌 패널의 오른쪽 경계가 움직이지 않는다. 앞서 검토한 「고정 프레임」을 **빈 공간이 아니라 쓸모 있는 것으로** 채운 셈이다.

16:9 스테이지(훈련모드 방식)는 택하지 않았다. 레터박스는 문제가 아니었지만 — 진짜 16:9 모니터면 0이고 표는 어차피 1,020px 로 묶여 있다 — `transform: scale()` 이 **OS가 그리는 것에는 안 걸린다**. `<select>` 드롭다운 목록과 한글 IME 후보창이 그렇다. 설정모드는 화면마다 한글 입력이 있어서 훈련모드보다 위험이 크다.

### 스크롤 유지 — 이 레일의 존재 조건

체크리스트를 쓰다가 출동대를 확인하고 돌아왔을 때 **보던 자리가 그대로여야** 한다. 두 가지를 지켜야 성립한다.

1. **레일을 조건부 렌더하지 않는다.** `section` 이 무엇이든 트리의 같은 자리에 남는다. 언마운트되는 순간 `scrollTop` 이 사라진다.
2. **접기를 `display:none` 으로 하지 않는다.** `display:none` 은 스크롤 컨테이너의 `scrollTop` 을 날린다. 바깥 폭만 줄이고 `overflow:hidden` 으로 자른다 — 안쪽 `--body` 는 접힌 상태에서도 원래 폭 그대로 살아 있다. 시나리오 예측 화면에서도 언마운트가 아니라 접기만 한다.

실측 — 스크롤 600 에서 시작해 모든 전환 후 600 유지:

| 동작 | scrollTop |
|---|---|
| 600 으로 스크롤 | 600 |
| 출동대 · 구조대상자 · 현장요소 · 건물 클릭 | 600 |
| 전체 설정(지휘절차) 이동 | 600 |
| 레일 접었다 펴기 | 600 |

### 폭

`--set-rail-w: 640px` = 손잡이 40 + 본체 600.

처음엔 520(본체 480)이었다. 480 은 체크리스트 행 상한 `--set-row-max`(34rem ≈ 510)에 맞춘 값이었는데, 실제 행이 `⠿ [메세지] 1착대 도착 (진압1, 구급1, 물탱크1) ✎ ☑ ✕` 처럼 길어서 항목명이 잘렸다.

**레일 안 글자는 한 단계 크다.** 새 값을 만들지 않고 기존 5단계 스케일에서 한 칸씩 밀었다 — 레일은 별도 타입 체계가 아니라 "같은 스케일의 한 단계 위"다. 시나리오를 쓰는 동안 계속 보는 면이라 본문 14px 로는 눈이 빨리 피로해진다.

| 토큰 | 본문 | 레일 |
|---|---|---|
| `--set-fs-xs` | 12px | **14px** |
| `--set-fs-sm` | 14px | **16px** |
| `--set-fs-md` | 16px | **18px** |

행 상한(`--set-row-max`)은 레일 안에서 `none` 으로 푼다. 그 값은 본문 열에서 줄이 화면 끝까지 늘어나는 것을 막으려던 것인데, 레일은 폭 자체가 600 으로 묶여 있어 상한이 이중으로 걸리면 오른쪽에 여백만 남는다.

| 뷰포트 | 레일 | 본문 | 건물 열 |
|---|---|---|---|
| 2560 | 640 | 1,680 | 3열 |
| 1920 | 640 | 1,040 | 2열 |
| 1850 | 640 | 970 | 2열 |
| 1800 | 40 (겹침) | 1,520 | 3열 |
| 1500 | 40 (겹침) | 1,220 | 2열 |

**1850px 미만에서는 레일이 레이아웃에서 빠져 본문 위에 겹친다.** 기본 접힘이고(`railOpen` 초기값을 같은 1850 으로 `matchMedia`), 손잡이만 오른쪽 끝에 남는다.

임계값 1850 은 실측으로 잡았다. 지켜야 할 것은 **레일이 자리를 차지하는 구간에서는 건물 화면이 항상 2열 이상**이라는 것이다. 2열 임계는 컨테이너 900px 이고 컨테이너는 본문의 콘텐츠 박스(좌우 패딩 32씩 제외)라

```
필요 뷰포트 = 900 + 64(패딩) + 240(내비) + 640(레일) = 1844
```

1800 으로 뒀을 때는 컨테이너가 856 뿐이라 건물 화면이 1열로 무너졌다.

### 컨테이너 쿼리로 바꾼 이유

`BuildingConfigPanel` 의 열 수 분기를 뷰포트에서 **컨테이너**로 옮겼다(`@container settings-body`). 사용자가 레일을 접었다 폈다 하면 같은 뷰포트에서도 남는 폭이 520px 달라지는데, 뷰포트 기준 규칙은 그걸 모른다 — 1920px 에서 레일을 편 채로 3열을 그리려 들어 소방시설 열(최소 483px)이 깨진다. 임계값은 실측한 열별 자연 폭(건물 884 / 화재 293 / 소방시설 483)에서 900 / 1,250 으로 잡았다.

### 같이 바뀐 것

- **체크리스트가 좌측 메뉴에서 빠졌다.** 시나리오 메뉴는 4개 + 시나리오 예측. 준비도 집계(`SCENARIO_KEYS`)에는 그대로 포함된다 — 레일 머리줄이 "N개 절 · M개 항목"을 보여준다.
- **보조 열(`.settings-page__aside`)이 없어졌다.** 도착 순서는 출동대 화면 안, 층별 분포는 구조대상자 화면 안, 항목 타입 범례는 레일 안으로 들어갔다. ≥1800px 분기도 함께 사라졌다.
- `ChecklistLegendAside` 에 `summary` 옵션 추가 — 레일 머리줄과 문장이 겹쳐서 기본으로 끈다.

## 12-D. 건물 · 소방시설 재배치 + 미리보기 (2026-08-25)

3열(건물 / 화재 설정 / 소방시설)을 **2열**로 바꿨다.

```
┌─ 좌 480px ─┬─ 우 ────────────────────┐
│ 건물        │ 상황판 구역 비율            │
│ 화재 설정    │ ─────────────────────  │
│ 소방시설     │ 미리보기 (표)             │
└────────────┴────────────────────────┘
```

3열은 카드 높이가 크게 달라(건물이 화재의 3배쯤) 오른쪽 두 열 아래가 늘 비었다. 세로로 쌓으면 그 공백이 사라지고, 비워진 오른쪽을 미리보기가 쓴다. 좌열 상한 480px 은 실측한 열별 자연 폭(건물 884 / 화재 293 / 소방시설 483)에서 잡았다 — 이 폼들은 입력칸이 짧아서 넓혀 봐야 빈칸만 늘어난다.

### 비율 슬라이더를 미리보기 위에 둔 이유

미리보기 표의 열 폭이 `boardColumnRatio` 를 그대로 따른다. 슬라이더를 움직이면 가운데 칸이 같이 넓어져서 `1 : 1.74 : 1` 이 무엇을 뜻하는지 설명 없이 보인다. 예전에는 비율이 건물 카드 안에 있어 그 연결이 없었다.

| 슬라이더 | 표 열 폭 (B / 건물 / D) |
|---|---|
| 1.00 | 33.3% / 33.3% / 33.3% |
| 1.74 (기본) | 26.7% / 46.6% / 26.7% |
| 3.00 | 20% / 60% / 20% |

### 미리보기를 훈련모드 컴포넌트로 만들지 않은 이유

`TacticalArea` 는 BuildingState · Token · Victim · Event · DisplayOptions · FireLine · FireCommand · Training **여덟 Context** 를 요구한다. 설정모드에 올리려면 훈련용 Provider 를 통째로 들여와야 하고, 그러면 D-4 경계가 무너진다. 미리보기는 편집 중인 값이 어떤 모양이 되는지만 보여주면 되므로 **표로 그린다**(`BuildingPreview`, `useSettings()` 만 읽는다).

다만 층 모델은 훈련모드와 **같은 `buildDisplayFloors`** 를 쓴다. 층 압축 규칙(7~6F)을 여기서 다시 구현하면 언젠가 반드시 어긋난다.

표가 보여주는 것 — 층 구성 · 층별 화재 상태(단계별 색 3단) · 옥내소화전 · 연결송수구(1층) · 옥외소화전(면·거리). 읽기 전용이라 클릭·드래그가 없다.

### 첫 판에서 고친 세 가지

| 문제 | 조치 |
|---|---|
| 화재 상태가 층 칸 **왼쪽**에 있어 훈련 상황판과 위치가 달랐다 | `margin-left:auto` 로 오른쪽 끝에 붙였다. 소방시설 표시가 왼쪽, 화재가 오른쪽이다 |
| B/D 면을 `background:none` 으로 뒀더니 보드 바탕이 거의 검정이라 **면 폭이 아예 안 보였다** | 비율 설정이 바꾸는 것이 바로 그 폭이라, 안 보이면 미리보기의 뜻이 없다. 건물 칸과 다른 색으로 채우고 머리글에도 같은 색을 줬다 |
| 위 비율 바와 아래 표의 경계가 **20px 어긋났다** | 원인 둘 — 표에는 「층」 라벨 열이 있고(64px), 표가 `.bpv__board` 의 패딩+경계(21px) 안쪽에 그려진다. 비율 바에 같은 크기의 빈 칸과 안쪽 여백을 줘서 맞췄다 |

라벨 열 폭은 `--bcf-label-w` 하나를 두 곳이 공유한다 — 한쪽만 고치면 다시 어긋난다. 실측으로 확인한 잔여 오차는 비율 1.0 / 1.74 / 2.6 전 구간에서 1~2px(바 테두리 1px)이다.

### 네 면 표현과 옥외소화전 배치

면을 넷 다 그린다. 성격이 갈려서 표현 방법도 다르다.

| 면 | 표현 |
|---|---|
| B · D | 표의 **열**이라 머리글이 곧 라벨이다 |
| C · A | 열이 없는 앞·뒤 면이라 표 **위아래 띠**로 그린다 |

예전에는 B/D 를 보드 가장자리에 절대배치로 한 번 더 적었는데, 열 머리글에 이미 "B면 / D면" 이 있어 같은 말을 두 번 하고 있었다 — 지웠다.

두 띠는 **B 열 시작점부터 D 열 끝까지**다. 처음에는 표 전체 폭으로 그려서 「층」 라벨 열(64px)만큼 A/C 가 B/D 보다 길었다 — 같은 건물의 네 면인데 두 면만 넓어 보였다. `margin-left: var(--bcf-label-w)` 로 맞췄고, 실측 오차 0px 이다.

옥외소화전은 층이 아니라 면에 붙으므로 **자기 면 구역 안**에 놓는다.

| 면 | 자리 |
|---|---|
| B | B 열 하단 (좌측 정렬) |
| D | D 열 하단 (우측 정렬) |
| C | C 띠 우측 |
| A | A 띠 — 첫 번째 좌측, 그 다음부터 우측 |

첫 판은 보드 좌·우 하단 두 자리로만 나눴는데, 그러면 D면 소화전이 B면 소화전 옆에 놓이는 일이 생겨 어느 면 것인지 자리로는 알 수 없었다. A 만 좌·우로 갈리는데 앞면이라 양쪽 어디든 설 수 있기 때문이다.

B·D 는 **1층 행의 그 면 칸** 안에 넣는다. 옥외소화전은 지상에 있으니 1층이 맞는 자리이고, 열 안에 들어가야 어느 면 것인지 자리로 읽힌다. 처음엔 표 맨 아래에 전용 행을 하나 더 뒀는데, 층이 아닌 행이 섞여 표가 한 줄 길어지고 층 목록이 끊겨 보였다.

A·C 띠는 층 행의 **2배 두께**(52px vs 33px)다. 앞·뒤 면도 활동 공간이라 존재감이 있어야 하고, 띠 안에 소화전 칩이 들어가므로 높이도 필요하다.

소방시설 표시(옥내·송수구)는 점선 테두리 + `--set-board-text-dim`(#5a5650) 이라 어두운 칸 위에서 거의 안 읽혔다. 채움을 주고 글자를 밝게(`--set-text-body`), 크기도 12 → 14px 로 올렸다. 화재 배지도 같은 14px 로 맞췄다 — 한쪽만 키우면 줄이 어긋난다. 시설에 의미색을 주지 않은 것은 의도다: 시설은 **상태가 아니라 사실**이라 적·주황·녹을 쓸 이유가 없고, 쓰면 화재 배지와 섞인다.

> **`<td>` 에 `display: flex` 를 걸지 않는다.**
> 걸면 그 칸이 표 레이아웃에서 빠져나가 `colgroup` 의 비율 폭을 잃는다 — 실제로 소화전 행의 D면 칸이 건물 칸 자리로 밀려났다. 배치는 안쪽 `div`(`.bpv__cell-inner`)가 맡는다.

## 12-E. 구조대상자 화면 재배치 (2026-08-25)

건물 · 소방시설과 **같은 2열 골격**으로 맞췄다. 같은 성격의 화면(무언가를 등록하고 그 결과를 확인)이라 골격이 달라 보일 이유가 없다.

```
┌─ 좌 920px ──────────┬─ 우 680px ──────┐
│ 구조대상자 표 (10열)   │ 층별 분포         │
│                     │ ───────────────│
│                     │ 미리보기 (표)      │
└─────────────────────┴────────────────┘
```

우열을 처음 480px 로 뒀더니 미리보기의 B/D 칸이 100px 남짓이라 소화전 칩이 셀 밖으로 넘쳤다. 680px 이면 B/D 칸이 ~170px 이 되어 칩 하나는 들어간다. 좌열은 920px 로 줄지만 구조대상자 표의 실측 자연 폭이 840px 이라 여유가 남는다(가로 스크롤 없음).

### 층별 분포 — 막대에서 사람 아이콘으로

막대는 "가장 많은 층 대비 몇 %" 를 보여줄 뿐이라 3명인지 4명인지 알려면 옆 숫자를 따로 읽어야 했다. 구조대상자는 한 자릿수인 경우가 대부분이라 아이콘을 그 수만큼 늘어놓는 편이 한눈에 세어진다. 8명을 넘으면 아이콘 8개 + `+N` 으로 접는다 — 줄바꿈되면 세는 이득이 사라진다.

아이콘(`ui/PersonIcon.tsx`)은 `ui/icons.tsx` 의 스트로크 아이콘과 달리 **채움**이다. 여러 개를 붙여 늘어놓을 때 선 아이콘은 작게 그리면 서로 뭉개진다.

### 미리보기에 구조대상자 얹기

`BuildingPreview` 에 `victims` 옵션을 더했다(건물 화면에서는 안 넘긴다). 배치 규칙:

| 면 | 자리 |
|---|---|
| B · D | 그 열의 해당 층 칸 |
| A · C · 미지정 | **건물 칸**의 해당 층 |
| 층 미지정 | 표에 자리가 없어 캡션에서 인원만 센다 |

A/C 를 띠로 보내지 않는 이유는 **층을 잃기 때문**이다. 소화전은 지상에 있어 층이 없지만, 구조대상자는 몇 층에 있는지가 가장 중요한 정보라 열이 없는 면이면 면보다 층을 살린다.

### 층 라벨 전용 열을 없앴다

층 이름은 전용 열이 아니라 **건물 칸 왼쪽 안**에 붙는다. 훈련 상황판이 층 이름을 건물 안쪽에 그리기도 하고, 전용 열을 두면 그만큼 표가 밀려 위쪽 비율 바와 경계가 어긋나기 때문이다.

이걸 없애면서 딸린 보정이 전부 사라졌다 — A/C 띠의 `margin-left`, 비율 바의 `.bcf__ratio-gutter`, 그리고 두 곳이 공유하던 `--set-preview-label-w` 토큰까지. 표가 B 열부터 시작하므로 띠도 비율 바도 그냥 100% 면 맞는다. 실측 오차: 띠 0px, 비율 바 1px(바 테두리).

그 전에는 `--bcf-label-w` 를 `.bcf__side`(건물 화면 우열)에만 정의해 두어, 그 클래스가 없는 구조대상자 화면에서 **변수 미정의 → 라벨 열 폭 0** 이 되어 층 이름이 옆 칸 위로 겹쳐 그려지는 버그가 있었다. 열 자체를 없애면서 원인이 함께 사라졌다.

### 소화전은 건물 화면에서만

`hydrants` 를 선택 인자로 바꾸고 구조대상자 화면에서는 넘기지 않는다. 그 화면에서 소방시설은 편집 대상이 아니라 소음이다.

## 12-F. 구조대상자 입력 정비 (2026-08-25)

### 면 · 층은 배타 선택

한쪽을 고르면 다른 쪽을 **비우고 잠근다**. 잠그기만 하면 이미 들어간 반대쪽 값이 남아 모순이 유지된다.

| 고른 것 | 잠기는 것 | 뜻 |
|---|---|---|
| 면 (A~D) | 층 · 계단실 | 건물 **바깥** 그 면에 있다 — 층이 없다 |
| 층 | 면 | 건물 **안**이다 — 면이 없다 |

이전에는 둘 다 고를 수 있어 "3층인데 B면" 같은 값이 만들어졌고, 미리보기에서 어느 칸에 그릴지 규칙으로 때워야 했다. 계단실은 층이 있어야만 성립하므로 면 선택 시 함께 잠긴다.

미리보기 배치도 이 규칙을 따른다 — 층 있음 → 건물 칸의 그 층 / 면 A·C → 그 띠 / 면 B·D → 그 열의 1층 칸(열은 있으나 층이 없어 지상에 세운다).

### 배치 현황 — 좌 건물 / 우 방면

면과 층이 배타 선택이므로 집계도 두 갈래로 갈린다. 한 줄에 섞으면 "3층과 B면이 같은 종류의 자리"라는 인상을 준다.

```
건물                      방면
옥상  👤👤👤👤   4명       A면  👤👤   2명
4층   👤👤       2명       B면  👤👤   2명
3층   👤👤       2명       C면  👤👤   2명
2층   👤👤       2명       D면  👤👤   2명
면·층을 정하지 않은 대상자 1명
```

- **방면은 인원 0 이어도 줄을 남긴다.** 넷이 고정이라 "없는 면"이라는 것이 없어서, 빈 줄이 곧 "그 면에는 아무도 없다"는 정보가 된다. 층은 반대로 사람이 있는 층만 보여준다.
- 둘 다 정하지 않은 사람은 두 열 어디에도 속하지 않으므로 **아래 꼬리말**로 뺐다.

우열 안에서 카드 순서는 **미리보기 → 배치 현황**이다. 미리보기가 배치의 결과이고 현황은 그 요약이라, 그림을 먼저 보고 숫자로 확인하는 순서가 맞다.

### 성별 · 상태 색

훈련모드 [`VictimCard.css`](../src/components/shared/VictimCard.css) 와 **같은 색 체계**를 쓴다. 설정에서 고른 값이 훈련 화면에서 다른 색이면 같은 사람인지 알 수 없다.

| 값 | 훈련 | 설정 | 배경 대비 |
|---|---|---|---|
| 남 | `#1976d2` | `#5aa9f0` | 7.34:1 |
| 여 | `#e53935` | `#ee4b47` | 5.03:1 |
| 경상 | `#5cc87c` | 동일 | 9.34:1 |
| 중상 | `#f07070` | 동일 | 6.37:1 |
| 사망 | `#aaaaaa` | `#9aa4ae` | 7.28:1 |

훈련모드는 밝은 보드 위라 원본이 맞지만 설정모드는 어두운 배경이라 그대로 쓰면 파랑·빨강이 가라앉는다. **색상(hue)은 유지하고 명도만 올렸다.**

한 번 헛디뎠다 — 여성을 `#f2726f` 까지 밝혔더니 중상(`#f07070`)과 거의 같은 색이 되어 나란히 놓인 두 칸이 구분되지 않았다. 훈련모드는 성별이 아이콘 · 상태가 툴팁이라 **붙어 있을 일이 없어 드러나지 않던 충돌**이다. 여성은 채도 높은 빨강, 중상은 연어색으로 갈라 뒀다.

색만으로 뜻을 전하지는 않는다 — 글자('여'·'중상')가 그대로 남아 있고 색은 스캔을 돕는 보조다(WCAG 1.4.1).

### 면 · 층의 빈 값은 "-"

"없음"은 값처럼 읽힌다("없음"이라는 상태를 고른 것처럼). 미입력은 `-` 가 맞고, 글자색도 `--set-text-faint` 로 낮춰 값이 든 칸과 구분한다.

### 손대지 않은 것

연령대를 6종(10~60대)으로 줄였다가 **되돌렸다.** `VictimAgeGroup` 은 설정모드 전용이 아니라 `AGE_GROUP_RANGES` 를 거쳐 훈련모드 구조대상자의 나이 산출에 쓰이고, 줄이면 소아·고령 구조대상자가 훈련에서 아예 나오지 않는다. 9종(`소아` · `10~80대`) 그대로다.

`VictimCondition` 은 이미 `경상 · 중상 · 사망` 이라 처음부터 손댈 것이 없었다.

## 12-G. 현장요소 화면 (2026-08-25)

**반으로 나눈다** — 좌 800px / 우 800px.

```
┌─ 좌 ─────────────┬─ 우 ──────────────┐
│ 현장요소 추가       │ 이미지 (4개 × 3줄)  │
│  [?][이름][종류][추가]│                   │
│ ─────────────    │ ─────────────    │
│ 등록 목록          │ 종류별 세부 상태     │
└──────────────────┴───────────────────┘
```

**2열을 `SettingsPage` 가 아니라 패널이 직접 만든다.** 이미지 격자와 추가 폼이 같은 상태(`newIcon`)를 공유해서, 바깥에서 나누려면 상태를 끌어올려야 한다. 다른 화면(건물·구조대상자)은 좌우가 독립이라 바깥에서 나눴다 — 같은 모양이라고 같은 방법을 쓰지 않는다.

### 폭 상한을 없애고 격자를 4열로

이 화면만 `--set-row-max`(510px)를 걷어냈다. 다른 목록 패널은 한 줄에 짧은 글자만 들어가서 상한이 이득이지만, 이 화면은 **이미지 격자**가 주인공이다.

격자는 `flex-wrap` 에서 **`grid` 4열 고정**으로 바꿨다. wrap 은 칸 폭이 내용에 따라 달라져 줄마다 개수가 들쭉날쭉했다.

이름은 잘라내지 않고 줄바꿈한다. 예전 `max-width: 52px` + `text-overflow: ellipsis` 에서는 `쓰레기더미` 가 `쓰레…`, `페인트,신너` 가 `페인…` 으로 잘렸다 — **파일명이 곧 그 이미지의 유일한 단서**라 잘리면 고를 수가 없다. 실측 결과 11개 전부 잘림 없음.

「아이콘」이라는 말도 「이미지」로 바꿨다(카드 제목 · 목록 머리글 · 툴팁). 실제로 png 파일을 고르는 것이지 아이콘 세트에서 고르는 것이 아니다.

### 종류별 세부 상태 범례

종류(화재 · 가스 · 전기)를 고를 때 이름 셋만 보이고 **그 선택이 무엇을 정하는지는 안 보였다.** 실제로는 훈련 중 우클릭 메뉴가 통째로 달라진다.

| 종류 | 단계 | 상태 |
|---|---|---|
| 화재 | 6 | 연소확대 · 최성기 · 큰불잡음 · 50% · 초진 · 완진 |
| 가스 | 4 | 폭발 · 누출 · 화재 · 제어불가 |
| 전기 | 4 | 폭발 · 불꽃 · 열폭주 · 화재 |

**목록을 문서에도 코드에도 다시 적지 않는다.** `EventTypeLegendAside` 가 `EVENT_TYPE_STATUSES` 를 그대로 읽어 그리므로, 상태를 추가하면 범례가 저절로 따라온다. 색 견본도 같은 출처라 훈련 중 토큰 배경색과 정확히 일치한다 — 옮겨 적었다면 반드시 어긋났을 자리다.

`'-'`(없음)는 상태가 아니라 해제라 범례에서 뺐다.

## 12-H. 출동대 화면 재배치 (2026-08-25)

생성칸을 **가로로 늘어놓고, 만들어진 대를 그 칸 바로 아래**에 둔다. 예전에는 위에서 수량을 정하고 아래 표에서 부대명·착대를 따로 잡아, 방금 만든 대가 표 어디로 갔는지 눈으로 따라가야 했다.

```
활동대                차량                              유관기관   직접입력
진압대 구조대 구급대   고가 굴절 배연 지휘 물탱크 구조차   [칩 2열]  [입력][추가]
[8]   [1]   [6]      [1] [0] [0] [1] [4]  [0]
진압1                 고가1        지휘1  물탱크1        시청      지휘차 운전
1착대▾                6착대▾       4착대▾ 1착대▾         10착대▾   4착대▾
진압2                                     물탱크2
2착대▾                                    5착대▾
```

### 네 그룹의 폭 배분

`--dsp-slot-w: 120px` 를 토큰으로 빼고, 유관기관·직접입력 그룹이 **생성칸 두 개 폭**을 확보하게 했다. 그 전에는 고정 그룹이 내용 크기대로만 잡혀(169 / 198px) 그쪽 토큰만 눈에 띄게 작았다 — 같은 성격의 값인데 그룹에 따라 크기가 달랐다.

| 그룹 | 전 | 후 |
|---|---|---|
| 활동대 | 600 | 501 |
| 차량 | 602 | 503 |
| 유관기관 | 169 | **272** |
| 직접입력 | 198 | **292** |

프리셋 버튼 높이를 활동대 스테퍼 버튼과 맞췄다(26 → 32px, 스테퍼 30px) — 둘 다 「만드는 수단」이라 급이 같다. 프리셋 격자·직접입력 행의 간격도 4 → 8px 로 넓혔다.

글자 크기는 처음부터 네 그룹 모두 14px 로 같았다. 달라 보인 것은 **폭**이었다.

### 차량은 3열 × 2행

여섯을 한 줄로 늘어놓던 것을 접었다. 두 개씩 세로로 짝지어 묶는다.

```
고가차  지휘차  물탱크
굴절차  배연차  구조차
```

**세로로 채운다**(`grid-auto-flow: column`) — TSX 배열을 두 개씩 끊어 읽으면 화면 배치가 그대로 보인다. 가로 채움이면 배열이 고가·지휘·물탱크·굴절… 로 뒤섞여 짝이 읽히지 않는다.

행 높이를 숫자로 박지 않았다. `.dsp__groups` 를 `align-items: stretch` 로 두어 그룹 높이가 서로 맞춰지고, 차량 격자가 `flex: 1` 로 남는 세로를 받아 두 행이 반씩 나눈다 — **활동대 한 칸의 높이에 차량 두 칸이 들어간다.** 활동대는 대수에 따라 자라므로(진압 8대면 그만큼 길어진다) 고정값으로는 맞출 수 없다.

실측 @2560 — 네 그룹 높이 603px 로 동일, 차량 칸 266px(활동대 최소 칸과 같은 값), 한 줄 유지. 가로로 절반이 되면서 남는 폭을 활동대가 가져가 두 그룹이 600 / 602px 로 거의 같아졌다.

### 착대는 토큰 오른쪽에, 숫자만

`N착대` 가 아니라 숫자만 적는다. 옆에 늘어선 값들이 서로 순서라는 것이 열 제목 없이도 읽히고, 글자를 빼는 만큼 토큰이 이름을 더 보여줄 수 있다.

토큰은 **가로만 줄인다** — 드롭다운이 가져간 만큼 좁아지되 높이는 그대로다(둘 다 28px). 세로까지 줄이면 훈련모드 토큰과 덩치가 달라져 같은 것으로 안 읽힌다.

착대 숫자는 **토큰 글자와 같은 크기·굵기**다(14px / 700). 착대순서는 부속 정보가 아니라 토큰과 같은 급의 값이라, 작고 흐리면 눈이 건너뛴다.

| | 폭 | 높이 | 글자 |
|---|---|---|---|
| 토큰 | 66px | 28px | 14px / 700 |
| 착대 | 52px | 28px | 14px / 700 |

52px 은 14px 두 자리("10")가 화살표와 함께 들어가는 폭이다.

### 폭 — 칸 하나가 전체를 정한다

활동대 3칸 + 차량 6칸 = **9칸**이라 칸 폭 1px 이 전체 9px 이 된다. 세로로 쌓았을 때는 92px 이면 됐지만 드롭다운을 옆에 붙이면서 120px 이 됐다.

**생성칸이 있는 그룹은 남는 폭을 나눠 갖는다**(`flex: 1 1 auto`, 칸은 `flex: 1 1 120px`). 고정 폭이면 오른쪽에 수십 px 이 그냥 비는데, 칸이 아홉이라 그 폭을 나누면 칸마다 넓어져 토큰 이름이 그만큼 더 보인다. 프리셋·입력만 있는 그룹(유관기관·직접입력)은 `--fixed` 로 자라지 않게 한다 — 늘리면 버튼 옆이 빈다.

| 뷰포트 | 컨테이너 | 그룹 합 | 남는 폭 | 줄수 |
|---|---|---|---|---|
| 2560 | 1,616 | 1,568 | **0** | **1줄** |
| 1920 | 976 | — | — | 3줄 |

2560 에서 컨테이너를 정확히 채운다. 1920 에서는 3줄로 접힌다 — 가로 배치를 유지하는 값이다.

### 유관기관 프리셋

`지휘차` 를 뺐다. 차량 그룹에 이미 지휘차 칸이 있어 **같은 것을 두 곳에서 만들 수 있었고**, 어느 쪽으로 만들었는지에 따라 토큰 색이 달라졌다(차량이면 vehicle, 유관기관이면 agency).

남은 여섯은 **세로로 채운다**(`grid-auto-flow: column`) — 배열 순서가 곧 「왼쪽 열 위에서 아래로, 그다음 오른쪽 열」이라 TSX 목록을 읽으면 화면 배치가 그대로 보인다. 가로 채움이면 배열이 경찰·시청·한전·보건소… 로 뒤섞여 읽히지 않는다.

```
경찰   시청
한전   보건소
가스   군부대
```

### 높이 정렬 — 생성 부분과 목록

그룹마다 **생성 수단이 다르다.** 활동대·차량은 라벨+스테퍼, 유관기관은 프리셋 3행 격자, 직접입력은 입력 한 줄. 그대로 두면 높이가 74 / 86 / 30 으로 갈리고, 아래 토큰 목록이 그룹마다 다른 y 에서 시작해(576 / 588 / 532) 줄이 어긋난다.

`--dsp-create-h: 86px` 하나로 셋을 묶었다 — 가장 큰 프리셋 격자에 맞춘 값이다. 적용 후 셋 다 86px, 목록 시작 y 는 **588 하나**로 모였다.

### 목록은 5대분을 미리 비운다

출동대 수는 칸마다 다르다(진압 8, 굴절 0). 목록 높이가 내용대로 흐르면 칸마다 바닥이 달라 들쭉날쭉해 보인다.

```
--dsp-list-min: calc(28px * 5 + var(--set-sp-2) * 4)   /* 유닛 5 + 사이 여백 4 = 172px */
```

5대분을 미리 비워 두면 대부분의 칸이 같은 크기가 되고, **넘는 칸만 아래로 자란다.** 실측 — 0~5대 칸은 전부 172px, 6대 칸 208px, 8대 칸 280px.

### 도착 순서 — 착대별 토큰 목록

이름을 `·` 로 잇던 것을 **실제 토큰 색 칩**으로 바꿨다. 훈련 화면에 나올 모습 그대로라 어느 대가 언제 오는지를 글자가 아니라 색 덩어리로 읽는다. 색은 생성 칩과 같은 `--set-token-*` 이다.

```
1착대  [7분후▾]  [진압1][펌프1][구급1][물탱크1]
2착대  [1분후▾]  [진압2][펌프2][구급2]
```

**방식 선택(착대설정 / 시간설정)이 이 카드 머리로 옮겨 왔다.** 방식이 바꾸는 것이 이 카드의 내용이라 여기 있어야 무엇을 바꾸는 스위치인지 보인다 — 예전에는 화면 맨 위에 있어서 한참 아래의 이 목록과 이어지지 않았다.

**착대 드롭다운은 방식과 무관하게 항상 보인다.** 착대는 도착 편성 그 자체이고, 시간설정은 "그 착대가 몇 분 뒤에 오는가" 를 더 정하는 것이라 착대를 먼저 정해야 성립한다. 처음엔 시간모드에서 이걸 숨겼는데, 모드를 바꾸면 편성이 사라진 것처럼 보였다.

**시간은 착대 단위로 정한다.** 같은 착대는 함께 오는 것이 정의라 대마다 따로 시간을 주면 착대가 뜻을 잃는다. 저장은 기존대로 항목별 `arrivalSec` 이고, 한 착대의 항목 전부에 같은 값을 쓴다. 선택 범위는 1~30분.

전 착대를 다 보여준다 — 예전에는 4착대까지만 그리고 나머지를 "6착대 이후 · 11개 대" 로 접었는데, 이 카드가 도착 편성을 정하는 자리가 된 이상 접힌 것을 정할 방법이 없다. 착대마다 구분선을 긋고 번호를 칩으로 만들었다 — 한 착대에 여덟 대가 붙으면 어디까지가 같은 착대인지 세어 봐야 했다.

**연동 펌프는 여기서도 숨긴다** — 생성 칸과 같은 규칙이다. 진압대를 따라 같은 착대로 오므로 적어도 정할 것이 없고, 줄만 두 배로 길어진다.

### 차량 · 유관기관 칩의 대비

높이는 처음부터 다섯 톤 모두 28px 로 같았다. 문제는 **대비**였다 — 훈련모드 원본 색(`#1c1408` · `#140e20`)은 밝은 크림색 보드 위라 또렷하지만, 어두운 설정 배경(`#0e1420`) 위에서는 배경 대비가 **1.01 : 1** 이라 칩이 배경에 묻혀 진압대 칩보다 작아 보였다.

색상(hue)은 그대로 두고 명도만 올렸다. 진압·구조·구급은 원본이 이미 4.4~11 : 1 이라 손대지 않았다.

| 톤 | 테두리 대비 (전 → 후) |
|---|---|
| 차량 | 1.64 → **3.07** |
| 유관기관 | 1.46 → **3.29** |

다섯 톤 전부 테두리 3:1 이상(WCAG 1.4.11), 글자 대비 3.3~12.7 이다.

`unitTone()` 은 별도 파일(`ui/unitTone.ts`)로 뺐다. 쓰는 곳이 생성 패널과 이 목록 둘이고, 한쪽 컴포넌트 파일에 두면 react-refresh 가 "컴포넌트 파일이 컴포넌트 아닌 것을 export 한다"고 잡는다.

### 착대 자동 배정 · 드래그드롭 · 압축

**생성 칸에서 착대 드롭다운을 없앴다.** 착대는 도착순서 카드에서 **드래그드롭으로만** 정한다. 만드는 곳과 배치하는 곳을 갈랐다.

#### 자동 배정 — 같은 종류 중 최대 + 1

`buildRoster` 의 `nextOrderFor()`. 새로 만든 대만 대상이고, 이미 있던 대는 값을 지킨다(`prevByName`) — 사용자가 옮겨 둔 것을 되돌리면 안 되기 때문이다.

| | 결과 |
|---|---|
| 진압 3대 생성 | 1 · 2 · 3착대 |
| 진압3을 2착대로 옮긴 뒤 6대로 늘림 | 진압4→3, 진압5→4, 진압6→5착대 |

유관기관(`agency`)·직접입력(`general`)은 `unitType` 이 달라 **각자 별도 계수기**가 된다. 연동 펌프는 세지 않고 부모를 따른다.

#### 압축 — 빈 착대를 없애고 위를 당긴다

`compactArrivalOrders()`. 4착대가 비면 5착대가 4착대가 된다.

> **체크리스트를 자동으로 고치지 않는다.**
> `ChecklistItem.arrivalOrder` 가 착대 **번호**를 저장하므로, 압축으로 번호가 밀리면 그 항목이 다른 편성을 가리킨다. 설정모드가 다른 화면의 데이터를 조용히 바꾸기 시작하면 되돌릴 방법이 없어서, **몇 개가 영향을 받는지 알리고 판단은 사람이 한다**(사용자 결정: 안 「다」).

실측 — 진압 5대(1~5착대), 체크리스트에 3·4·5착대 도착 항목을 둔 상태에서 진압2를 1착대로 옮기면:

```
착대: 1(진압1,진압2) · 2(진압3) · 3(진압4) · 4(진압5) · 5(추가칸)
알림: 빈 착대를 정리했습니다 (3→2 · 4→3 · 5→4).
      체크리스트 도착 항목 3개가 이전과 다른 편성을 가리킵니다 — 확인이 필요합니다.
```

압축이 아무것도 밀지 않으면(비운 착대가 최대였을 때) 알림도 뜨지 않는다.

#### 착대 추가 칸

마지막 착대 다음 자리에 점선 칸을 하나 더 그린다. 거기로 끌어다 놓으면 그 번호가 생긴다. 착대 상한(예전 1~10)은 없앴다 — 훈련모드 도착 시각이 계산식(`1착대 180초 · 2착대 300초 · 이후 +120초`)이라 상한이 필요 없다.

### 잡은 버그 — 특이도 높은 옛 규칙

`SettingsPage.css` 에 `.settings-page .dsp { display: grid; grid-template-columns: repeat(auto-fit, minmax(440px, 1fr)) }` 가 남아 있었다. 패널 쪽 `.dsp { flex-direction: column }` 보다 특이도가 높아 **새 레이아웃을 통째로 덮었다** — `.dsp__groups` 가 800px 짜리 오른쪽 칸에 갇혀 그룹이 3줄로 접혔다.

패널 CSS를 갈아엎을 때 **페이지 쪽에 그 패널을 겨냥한 규칙이 있는지** 함께 확인해야 한다. 이 파일에는 `.settings-page .<패널>` 형태의 덮어쓰기가 여러 개 있다.
