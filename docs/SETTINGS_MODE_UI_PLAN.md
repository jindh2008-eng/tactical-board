## 0. 이 문서의 위치 — 먼저 읽을 것

**현재 확정된 작업 범위는 훈련모드(무플) 하나다**([MASTER_PLAN.md](MASTER_PLAN.md) D-4). 설정모드 수정은 [DEFERRED_PROPAGATION.md](DEFERRED_PROPAGATION.md) §4의 **반영 순서 2번**에 놓여 있고, 그 문서의 규칙은 "무플 작업 중 설정모드는 고치지 말고 기록한다"이다.

따라서 이 문서는 **지금 실행하는 계획이 아니라, 실행 시점에 펼칠 설계안**이다. 세 가지 중 하나를 선택해야 한다.

| 선택 | 의미 | 영향 |
|---|---|---|
| **A. 무플 완성 후 착수** (문서 기본값) | DEFERRED §4 순서를 지킨다 | D-4 유지. 이 문서는 그때까지 대기 |
| **B. 순서를 앞당겨 지금 착수** | D-4의 "무플 하나만"을 사용자가 명시적으로 뒤집는다 | MASTER_PLAN §1에 D-7로 기록 필요 |
| **C. S-1(토큰)만 선반영** | 토큰 정의는 `/play`와 겹치지 않아 무플 작업을 막지 않는다 | 가장 위험이 낮은 절충안 |

**이 문서는 A를 전제로 쓰였으나, 2026-08-24 사용자 지시로 B가 선택됐다** — [MASTER_PLAN.md](MASTER_PLAN.md) **D-7**에 기록. 작업 브랜치는 `feat/settings-ui-redesign`이다. 단계 구분(S-0~S-2가 독립적으로 완결)은 그대로 유효하다.

설정모드가 `/play`와 **컴포넌트를 하나도 공유하지 않는다**는 실측 사실(DEFERRED §1.1)이 이 계획의 최대 자산이다. 설정모드를 아무리 크게 고쳐도 훈련모드가 깨지지 않는다. 단 하나의 접점은 상단 `app-nav`(P-4)이며, 이 계획은 §10에서 그것을 범위 밖으로 뺀다.

### 0.2 브라우저 실측 — §1에 없던 값

개발 서버에서 직접 쟀다.

```
뷰포트 1600px:  사이드바 200 + 본문 1116  →  본문 사용률 69.8%
훈련장 2560px:  사이드바 200 + 본문 1116  →  본문 사용률 43.6%
```

본문 `max-width: 1180px`가 고정이라 **화면이 커질수록 사용률이 떨어진다.**

**실제 렌더된 글자 크기는 7종뿐이다** — 11.1 / 11.4 / 12.45 / 13.05 / 13.95 / 15 / 18.75px. CSS에 22종의 원시값이 있지만 상당수가 덮여서 죽어 있다는 뜻이고, **토큰 이관의 실작업량이 CSS 숫자보다 작다.** 다만 최소 11.1px는 한글에 확실히 작다.

### 0.3 §1이 놓친 위험 두 가지 ★

**(1) `--color-border`는 전역이고 훈련모드와 공유한다.** §1.3은 "1.58:1"을 최대 결함으로 지목하지만 이 토큰이 어디 정의됐는지는 적지 않았다 — `src/App.css:16`의 `:root`다.

```
설정모드 CSS의 var(--color-border):  103건
훈련모드 CSS의 var(--color-border):   11건
```

`:root` 값을 고치면 훈련모드가 같이 바뀌어 **D-4를 깬다.** §5.1의 `.settings-page` 스코프 방식은 취향이 아니라 **필수 격리 조건**이며, S-2의 실제 내용은 "hex 128개 치환"이 아니라 **"`var(--color-*)` 사용처 362건을 `--set-*`로 재지정"**이다. 분량을 다시 잡아야 한다(§8).

**(2) 정의되지 않은 토큰 4곳.** `--color-surface-raised`와 `--color-input-bg`는 어디에도 정의돼 있지 않고 폴백만 동작한다 — `UnitStatusPanel.css:44,116` · `TagPresetPanel.css:30,125`. 토큰 체계를 세울 때 실제로 채울 자리다.

## 1. 현상 진단 — 코드 실측

감상이 아니라 숫자로 시작한다. 아래는 2026-08-22 기준 코드에서 직접 센 값이다.

### 1.1 규모

| 항목 | 값 |
|---|---|
| 설정모드 TSX | 11개 파일 · **3,087행** |
| 설정모드 CSS | 11개 파일 · **3,593행** |
| 화면(섹션) 수 | 9개 (4개 그룹) |
| 가장 큰 패널 | `ChecklistSetupPanel.tsx` **1,020행**, 로컬 `useState` **20개** |

### 1.2 디자인 시스템 부재 — 값의 산포

| 속성 | 서로 다른 값의 개수 | 비고 |
|---|---|---|
| `font-size` | **20종** (0.60rem ~ 1.25rem) | html 15px 기준 **9.0px ~ 18.8px** |
| `padding` | **51종** | 4/8px 리듬 없음 |
| `border-radius` | **10종** (2·3·4·5·8·10·50%) | 같은 층위의 카드끼리도 다름 |
| 하드코딩 hex | **121개** | 토큰 밖에서 직접 색을 씀 |

3,593행 CSS에 51가지 패딩과 20가지 글자 크기가 있다는 것은 **디자인 시스템이 없다는 뜻**이고, 화면이 "직접 만든 것처럼" 보이는 근본 원인이다. 개별 화면의 미감 문제가 아니다.

`SettingsPage.css` 하단의 "패널 공통 보정" 블록(약 90행)이 이미 이 문제를 후행 처리로 덮고 있다 — `[class*="__group-title"]` 같은 와일드카드 선택자로 다른 파일의 글자 크기를 되돌린다. **증상 치료가 코드에 남아 있다는 것 자체가 진단이다.**

### 1.3 색 — 대비 실측

| 조합 | 대비 | 판정 |
|---|---|---|
| `--color-text` `#c8d8e8` on surface | 12.67:1 | ✅ |
| `--set-text-strong` `#e2ecf6` on surface | 15.41:1 | ✅ |
| `--set-text-dim` `#8aa8c4` on surface | 7.44:1 | ✅ |
| `--color-text-dim` `#6a8aaa` on surface | **5.11:1** | ⚠ AA 통과, 그러나 0.62rem(9.3px)에 쓰임 |
| `--color-accent` `#4488cc` on surface | 4.95:1 | ✅ |
| **`--color-border` `#2a3a4a` on surface** | **1.58:1** | ❌ **WCAG 1.4.11 (3:1) 미달** |

**테두리 1.58:1이 이 화면의 가장 큰 시각적 결함이다.** 입력창·카드·표의 경계가 사실상 보이지 않아, 화면이 "정리되지 않은 텍스트 덩어리"로 읽힌다. 고급스러움은 여백과 폰트보다 **경계의 정확성**에서 나온다.

교정 후보: `#54697f` → surface 대비 **3.25:1**, bg 대비 3.46:1.

### 1.4 정보 구조 — 색이 의미를 배신한다

`SettingsLibraryPanel`의 상단 바에는 버튼 6개가 있고, 각자 다른 색을 **토큰 밖에서** 쓴다.

| 버튼 | 배경 | 뜻하는 바 | 문제 |
|---|---|---|---|
| 저장 | `#4433aa` 보라 | primary | 앱 액센트 `#4488cc`와 무관한 색 |
| 다른 이름으로 | `#252535` | 중립 | |
| **신규 작성** | **`#1a3a1a` 초록** | **전체 초기화(파괴적)** | ❌ **초록은 "진행/성공"의 색이다** |
| 저장 목록 | `#252535` | 중립 | |
| 내보내기 | `#1a3040` 파랑 | 중립 | 색이 위계를 만들지 않고 소음만 만듦 |
| 가져오기 | `#1a3040` 파랑 | 중립 | |

**되돌릴 수 없는 파괴적 동작이 초록색이고, 일상적인 저장이 보라색이다.** 이것은 취향 문제가 아니라 사고 유발 설계다. 한 화면에 CTA는 하나여야 하고, 파괴적 동작은 위험색으로 **그리고 공간적으로** 분리돼야 한다.

### 1.5 상호작용 — 저장 모델이 사용자에게 보이지 않는다

`settingsStore.tsx`를 읽으면 저장이 **2단 구조**임이 드러난다.

```
편집 → (모든 변경마다 자동) saveWorkingPresets()  → 작업본, 새로고침해도 살아남음
     → (「저장」버튼을 눌러야)  saveSettings()      → 이름 붙은 설정 세트
     → (「훈련 세팅」을 눌러야)  훈련모드에 반영        → D-6 M-1
```

즉 **세 개의 서로 다른 "저장됨"이 존재하는데, 화면은 이 셋을 구분해 보여주지 않는다.**

| 결함 | 근거 |
|---|---|
| 미저장 변경 표시 없음 | `settingsStore.tsx` 전체에 `dirty`/`isDirty` 상태 **0건** |
| 이탈 경고 없음 | `beforeunload` 핸들러 **0건** |
| 반영 여부 표시 없음 | `훈련 세팅` 버튼은 `PlayPage.tsx:528`에만 있다 — 설정모드에서는 내 변경이 훈련에 갔는지 알 길이 없다 |
| 저장 피드백 | `저장됨 ✓` 1.5초 플래시 하나뿐 |

훈련 직전 시나리오를 고치는 사용자가 **"내가 방금 고친 게 반영됐나?"에 답할 수 없다.** 지휘훈련 도구에서 이것은 미감이 아니라 신뢰성 문제다.

### 1.6 접근성·조작성

| 항목 | 실측 | 기준 |
|---|---|---|
| `:focus-visible` 사용 | **0건** (`:focus` 24건) | 키보드 포커스 링 필요 |
| `aria-*` / `role` | 11개 파일 중 6개가 **0건** | 아이콘 전용 버튼(`×`, `+`)에 이름 없음 |
| 22px 이하 클릭 타깃 | **12곳** (최소 13px) | 마우스 전용이어도 24px 권장 |
| `@media` 쿼리 | **0건** (설정 CSS 전체) | |
| `prefers-reduced-motion` | **0건** (앱 전체) | |
| 전환 시간 | 대부분 **0.1s** | 즉각적이라 상태 변화가 안 읽힘 (권장 150–250ms) |

### 1.7 레이아웃 — 화면을 절반만 쓴다

```
사이드바 200px + 본문 max-width 1180px = 1380px
훈련장 PC 기준 화면폭        = 2560 CSS px   (RESPONSIVE 계획 §0)
                              ────────────
남는 공백                    ≈ 1180px (46%)
```

`--ui-scale`은 `/play`에만 적용되고 설정모드는 **반응형 범위 밖**이다(DEFERRED P-5). 결과적으로 큰 화면에서는 오른쪽 절반이 비고, 작은 화면에서는 대응 없이 붕괴한다. 표 형태인 구조대상자·출동대 화면은 넓은 화면에서 특히 손해다.

## 3. 설계 원칙 — "지휘훈련 전문가가 만든 것"의 정의

미감 형용사로는 검증할 수 없다. 네 개의 검증 가능한 원칙으로 번역한다.

### 원칙 1. 설정모드는 **저작 도구**이지 대시보드가 아니다

사용자는 여기서 훈련 시나리오를 **쓴다**. 최적화 대상은 화려함이 아니라 **입력 속도와 오입력 방지**다. 밀도는 높게, 장식은 없게. (design dial: variance 3 / motion 3 / density 7)

### 원칙 2. 훈련모드와 **같은 언어, 다른 문장**

두 모드는 같은 팔레트·같은 폰트를 쓰되, 성격은 갈라야 한다.

| | 훈련모드 | 설정모드 |
|---|---|---|
| 성격 | 실행 · 읽기 중심 · 원거리 판독 | 저작 · 입력 중심 · 근거리 정밀 |
| 밀도 | 낮음 (요소가 크고 명확) | 높음 (한 화면에 많이) |
| 배율 | **스테이지**(고정 캔버스 + `transform: scale()`) | **고정 스케일 + 브레이크포인트** |
| 색 강조 | 상태(화재·구조)를 색으로 | 액센트 1색 + 위험색만 |

원칙 2가 P-5("무플의 배율 규약을 설정모드에 이식")에 대한 이 계획의 답이다 — **이식하지 않는다.**

> ⚠ **2026-08-24 정정.** 이 절이 쓰인 시점의 "무플의 배율 규약"은 `--ui-scale`이었으나 **그것은 이미 제거됐다**(정의 0건, 죽은 참조 94건 — 전부 훈련모드 쪽이고 설정모드에는 0건). 현행은 `StageRoot`의 고정 캔버스 + `transform: scale()`이고, [SCREEN_STAGE_PLAN.md](SCREEN_STAGE_PLAN.md) §5가 이미 "설정모드는 스테이지를 쓰지 않는다"로 같은 답을 냈다.
>
> 결론은 같지만 **근거가 더 강해졌다: 배율은 F-5를 못 고친다.** 스테이지를 이식하면 2560px에서 배율 1.0이 되어 지금과 똑같이 1116px만 쓰고, 1600px에서는 배율 0.625로 글자가 15px→9.4px로 더 작아진다. 균일 확대·축소는 열을 늘릴 수 없다. "본문 사용률 80%"는 `max-width`를 푸는 문제다. 덧붙여 스테이지는 contain-fit 고정 캔버스라 세로로 길게 스크롤되는 체크리스트·출동대 화면과 구조적으로 맞지 않는다.
>
> **Q-1은 브레이크포인트로 확정됐다**(D-7).

### 원칙 3. 상태는 **항상 보인다**

미저장·저장됨·훈련 반영됨. 이 세 상태는 추측이 아니라 화면에 상시 표기한다.

### 원칙 4. 파괴는 **어렵게, 되돌릴 수 있게**

신규 작성·삭제는 위험색 + 공간 분리 + 확인. 가능하면 되돌리기(Undo)를 준다.

## 4. 화면 구성 재설계안

### 4.1 정보 구조 — 9개를 4단계로 다시 묶는다

현재 사이드바는 `현장 / 자원 / 진행 / 검토` 4그룹 9항목이다. 묶음 자체는 합리적이지만 **"무엇을 정의하는가"** 기준이라 **"어떤 순서로 하는가"**를 알려주지 않는다. 처음 쓰는 사람은 어디서 시작할지 모른다.

**시나리오 저작 순서**로 재배열한다.

```
1  현장          건물 · 소방시설  →  현장요소  →  구조대상자
2  자원          출동대  →  임무·상태 프리셋  →  상태 메시지
3  진행          체크리스트  →  지휘절차
4  검토          시나리오 예측
```

순서는 그대로 두되 **세 가지를 더한다.**

- **단계 번호**를 그룹 라벨에 붙인다 — 순서가 있는 작업임을 드러낸다.
- **완료 배지**를 각 항목에 붙인다 — 예: `출동대 · 12` / `구조대상자 · 0` (미입력이면 흐리게 + 경고점).
- **사이드바 하단에 준비도 요약**을 고정한다 — "훈련 실행 가능 / 출동대 미등록" 등.

이것이 이 계획에서 **가장 값이 큰 변경**이다. 시각 정리보다 "지금 무엇이 비어 있는가"를 알려주는 쪽이 전문 도구의 인상을 만든다.

### 4.2 레이아웃 — 3열 고정에서 폭 적응형으로

```
┌───────────────────────────────────────────────────────────────────────┐
│  설정 파일 바   [설정명 ▾] [상태칩: 미저장]     [저장] ⋯ [신규]      │  56px 고정
├──────────────┬────────────────────────────────────────────────────────┤
│              │  ← 화면 제목 + 설명 (sticky)                           │
│  1 현장      │ ┌────────────────────────┬───────────────────────────┐ │
│   건물 ✓     │ │                        │                           │ │
│   현장요소 3 │ │   주 편집 영역          │  보조 영역(넓을 때만)      │ │
│   구조대상자!│ │                        │  · 미리보기 / 요약         │ │
│              │ │                        │  · 도움말                 │ │
│  2 자원      │ └────────────────────────┴───────────────────────────┘ │
│   ⋮          │                                                        │
│              │                                                        │
│ ──────────── │                                                        │
│ 준비도 4/6   │                                                        │
└──────────────┴────────────────────────────────────────────────────────┘
   240px          유동 (max 1680px)          360px (≥1800px에서만 등장)
```

**브레이크포인트 3단**

| 폭 | 사이드바 | 본문 | 보조 열 |
|---|---|---|---|
| < 1280px | 아이콘+라벨 축소 (또는 상단 탭으로 접힘) | 100% | 없음 |
| 1280–1799px | 240px | 유동, max 1180px | 없음 (현재와 동일) |
| **≥ 1800px** | 240px | 유동, **max 1680px** | **360px** |

훈련장 PC(2560px)에서 46% 공백이 사라지고, 표 화면(구조대상자·출동대 목록)이 실제로 넓어진다. 보조 열에는 화면별로 다른 것이 들어간다.

| 화면 | 보조 열 내용 |
|---|---|
| 건물·소방시설 | 건물 단면 축소 미리보기 |
| 출동대 | 도착 순서 타임라인 |
| 구조대상자 | 층별 분포 요약 |
| 체크리스트 | 항목 타입 설명 + 섹션 개요 |
| 그 외 | 도움말 (없으면 열 자체를 숨김) |

### 4.3 화면 헤더 — sticky 제목 + 화면 단위 동작

현재 제목·설명이 스크롤과 함께 사라진다. 긴 화면(체크리스트·출동대)에서 자신이 어디에 있는지 잃는다.

- 제목 줄을 **sticky**로 고정하고, 스크롤 시 높이를 줄인다(설명 숨김).
- 제목 줄 오른쪽에 **화면 단위 동작**을 둔다 — "이 화면 초기화", "전체 펼치기/접기" 등. 지금은 이런 동작이 갈 자리가 없어 패널 안에 흩어져 있다.

### 5.2 강제 방법

토큰만 정의하면 다시 흩어진다. **린트로 막는다.**

- `stylelint` + `declaration-property-value-allowed-list`로 `src/components/settings/**`에서 `font-size`·`border-radius`의 원시값을 금지하고 `var(--set-*)`만 허용.
- 도입 시점의 기존 위반은 baseline으로 무시하고 **새 위반만 오류**로 본다 — CLAUDE.md의 기존 린트 기준선 운영 방식과 같다.

이 항목이 없으면 이 계획은 6개월 뒤 원상복귀한다.

## 6. 컴포넌트 표준

패널마다 `__add-btn`·`__del-btn`·`__input`을 새로 정의하는 지금 구조가 F-1의 직접 원인이다. **설정모드 전용 공용 컴포넌트 6종**을 만들고 패널을 옮긴다.

| 컴포넌트 | 대체 대상 | 규격 |
|---|---|---|
| `SetButton` | 각 패널의 `__btn` 계열 (11종) | variant: `primary`(화면당 1개) / `default` / `ghost` / `danger`, size: `md`(32px) / `sm`(26px) |
| `SetField` | 각 패널의 `label + input` 조합 | 라벨 상시 표시 · 도움말 슬롯 · 오류 슬롯(필드 아래) · `id`↔`htmlFor` 자동 |
| `SetCard` | `settings-page__card` + 패널별 `__group` | 제목 / 보조표기 / 본문. elevation 1단 |
| `SetTable` | `vsp__table`, `dsp__roster`, `esp__list` | 머리글 `--set-fs-xs` · 얼룩 없음 · 행 hover · 숫자열 `tabular-nums` |
| `SetEmpty` | 각 패널의 `__empty` (7종) | 설명 1줄 + 즉시 실행 버튼 1개 |
| `SetIconButton` | `×`·`+` 등 아이콘 전용 | **`aria-label` 필수** · 클릭영역 32×32 보장 |

**아이콘**: 현재 `×`, `▲▼`, `+`, `✓` 등 문자 글리프를 쓴다. 폰트에 따라 모양·정렬이 흔들린다. **인라인 SVG 세트**(stroke 1.5px, 16px 그리드)로 통일한다. 외부 패키지 없이 `src/components/settings/icons.tsx` 한 파일이면 충분하다(필요 아이콘 약 12종).

## 7. 핵심 상호작용 재설계

### 7.1 저장 모델을 화면에 드러낸다 (F-3)

`settingsStore`에 **파생 상태** 셋을 추가한다. 저장 로직은 건드리지 않는다.

```ts
isDirty:   작업본 ≠ 이름 붙은 설정 세트   // 저장 필요
isApplied: 작업본 === 훈련에 반영된 스냅샷  // 훈련 세팅 필요 (D-6 M-1)
lastSavedAt / lastAppliedAt
```

`isDirty`는 현재 상태와 `settingsList[activeSettingsId]`의 **얕은 비교**로 얻는다(직렬화 비교는 매 입력마다 돌면 비싸다 — 필드 단위 비교 + 디바운스).

상단 바에 **상태 칩** 하나를 둔다.

| 상태 | 표기 | 색 |
|---|---|---|
| 저장 필요 | `● 미저장 변경` | `--set-warn` |
| 저장됨, 훈련 미반영 | `● 저장됨 · 훈련 미반영` | `--set-text-dim` |
| 저장 + 반영 완료 | `✓ 훈련에 반영됨 14:32` | `--set-ok` |

그리고 **`beforeunload` 경고**를 `isDirty`일 때만 건다.

> ⚠ **D-6 M-1/M-2와의 정합**: 설정모드에 `훈련 세팅` 버튼을 놓지 **않는다**. 반영 시점은 오직 `/play`의 버튼 하나여야 한다(M-1). 설정모드는 *반영되지 않았음을 알려주기만* 한다. 훈련 중(`running`)에는 M-2에 따라 설정모드 진입 자체가 막히므로 이 칩은 `idle`/`ended`에서만 의미를 갖는다.

### 7.2 준비도 검사 (§4.1의 배지·요약을 뒷받침)

`utils/scenarioReadiness.ts`를 새로 만든다. 순수 함수 하나면 된다.

```ts
type Check = { id: string; label: string; level: 'block' | 'warn'; ok: boolean; section: SettingsSection };
function checkReadiness(settings): Check[]
```

초기 검사 항목(확정 아님, §11 Q-2):

| 검사 | 수준 |
|---|---|
| 출동대 1개 이상 등록 | block |
| 화재 층이 건물 층수 범위 안 | block |
| 도착 시간이 모두 0보다 큼 | warn |
| 구조대상자 0명 | warn |
| 체크리스트 항목 0개 | warn |
| 지휘절차 선택 레벨이 비어 있음 | warn |

결과는 사이드바 배지 · 하단 준비도 요약 · 「시나리오 예측」 화면 상단에 함께 쓴다. **한 번 계산해 세 곳에서 쓴다.**

### 7.3 체크리스트 화면 — 점진적 공개 (progressive disclosure)

`ChecklistSetupPanel`은 항목 타입이 7종이고, 타입에 따라 추가 폼의 모양이 달라져 `useState`가 20개다. 지금은 **모든 입력이 항상 펼쳐져 있다.**

- 항목 추가를 **한 줄 + 타입 선택**으로 접고, 타입을 고른 뒤에만 그 타입의 옵션을 편다.
- 타입 선택을 세그먼트 7개 나열 대신 **드롭다운 + 최근 사용 3개**로 바꾼다.
- 전환 상태 20개를 **타입별 판별 유니온 1개**(`draftItem: DraftItem | null`)로 합친다. 화면 정리와 상태 정리가 같은 작업이다.

이 화면 하나가 §8 S-5를 통째로 차지한다.

### 7.4 파괴적 동작 정리 (F-4)

| 동작 | 현재 | 변경 |
|---|---|---|
| 신규 작성 | 초록 버튼, 다른 버튼 사이 | `danger` variant + **구분선 뒤 오른쪽 끝**으로 분리 |
| 저장 | 보라 `#4433aa` | `primary` = `--set-accent` |
| 내보내기/가져오기 | 파랑 | `ghost` (중립) + `⋯` 오버플로 메뉴로 이동 |
| 설정 삭제 | 확인창 | 확인창 + **삭제 후 5초 되돌리기 토스트** |

상단 바에 노출되는 버튼을 **저장 / 다른 이름으로 / 저장 목록 / ⋯** 4개로 줄인다. 내보내기·가져오기·신규 작성은 `⋯` 안으로 넣는다 — 훈련 준비 중 오조작 경로를 줄이는 것이 목적이다.

## 8. 작업 순서

각 단계는 **독립적으로 완결**되고, 중단해도 화면이 깨지지 않는다. 파일 소유권이 겹치지 않아 순서 조정이 가능하다.

| 단계 | 내용 | 주요 파일 | 규모 | 선반영 가능(C안) |
|---|---|---|---|---|
| **S-0** | 기준선 기록 — 현재 화면 스크린샷 9장, 린트/타입 기준선 | `docs/` | XS | ✅ |
| **S-1** | **토큰 정의** — §5.1 전체 + stylelint 규칙 | `SettingsPage.css` | S | ✅ |
| **S-2** | **경계·대비 교정** — 하드코딩 hex 121개를 토큰으로 치환 (F-2) | 설정 CSS 11개 | M | ✅ |
| **S-3** | **공용 컴포넌트 6종 + 아이콘** — 만들고 상단 바부터 적용 (F-4) | `components/settings/ui/*`, `SettingsLibraryPanel` | M | — |
| **S-4** | **레이아웃·내비** — 3단 브레이크포인트, sticky 헤더, 사이드바 배지, 준비도 (F-5, §7.2) | `SettingsPage.tsx/css`, `utils/scenarioReadiness.ts` | L | — |
| **S-5** | **패널 이관** — 9개 화면을 공용 컴포넌트로. 체크리스트(§7.3)가 절반 | `components/settings/*` 전부 | **XL** | — |
| **S-6** | **저장 상태 모델** — dirty/applied, 상태 칩, beforeunload, 되돌리기 (F-3) | `settingsStore.tsx`, `SettingsLibraryPanel` | M | — |

**권장 실행 묶음**

- **1차** S-0 → S-1 → S-2 — 코드 구조를 안 건드리고 화면 인상의 절반이 바뀐다. C안(선반영)으로 지금 해도 무플 작업을 막지 않는다.
- **2차** S-3 → S-4 → S-6 — 뼈대와 상태.
- **3차** S-5 — 가장 크고, 앞의 셋이 끝나야 기준이 생긴다. 화면 단위로 잘라 9회에 나눠 진행.

### 8.1 각 단계 완료 조건

| 단계 | 완료 조건 |
|---|---|

### 끝나지 않은 것 — 여기부터 잇는다

**S-0 기준선이 미완성이다.** `docs/baseline/before/audit.json`이 저장소에 있지만 **빈 설정 상태로 측정한 것**이다. 이게 왜 문제냐면:

- 저장소 루트의 `tactical-board-settings-2026-08-06.json`이 실제 시나리오 11건을 담은 샘플이고(예: 출동대 37건, 구조대상자 11명), 이걸 불러오면 `DispatchSetupPanel.tsx:59,72`의 `−`/`+` 글리프 버튼, `VictimSetupPanel.tsx:161`의 `×` 글리프 버튼처럼 **롤 목록이 있어야 렌더되는 요소**가 비로소 나타난다.
- 빈 설정으로 잰 1차 결과는 `이름없는_아이콘버튼: 0`인데, 이건 버그가 없어서가 아니라 **그 버튼들이 화면에 아예 없어서**다. 이 숫자를 §9의 실제 기준선으로 쓰면 안 된다.
- `importSettings()`(`src/utils/settingsStorage.ts:305`)는 파일을 읽어 `localStorage`의 `tacticalBoardSettingsList`·`tacticalBoardWorkingPresets` 등 개별 키에 그대로 쓰는 구조라, 감사 스크립트가 브라우저를 열기 전에 **`context.addInitScript()`로 같은 키에 샘플 JSON을 미리 심으면** UI에서 파일 선택 없이 실 데이터 상태를 재현할 수 있다. 이 작업을 하다가 중단됐다.

**다음 컴퓨터에서 할 일 (순서대로)**:

1. `scripts/settings-ui-audit.mjs`에 실 시나리오 주입을 추가한다 — `chromium.newContext()` 직후 `page.addInitScript()`로 `tactical-board-settings-2026-08-06.json`의 `settingsList[0]`(또는 가장 큰 것)을 `workingPresets` 형태로 변환해 `localStorage`에 심는다. `SettingsExport`의 필드명은 `src/utils/settingsStorage.ts`의 `importSettings` 본문 참고.
2. `docs/baseline/before`를 **실 데이터 기준으로 재실행**한다. 이번 결과가 진짜 기준선이다 — §9 표를 이걸로 채운다.
3. 기준선이 확정되면 S-1(토큰 정의 + `.stylelintrc` 작성) → S-2(`var(--color-*)` 362건을 `--set-*`로 재지정, §0.3에서 지적한 대로 "hex 치환"이 아니라 이것이 진짜 작업량)로 진행한다.
4. S-1·S-2가 끝나면 같은 감사 스크립트를 `docs/baseline/after`로 재실행해 §9 표와 대조한다.

### 참고 — 사용자 질문 (미답변, 무플 작업과 무관)

이 세션 도중 사용자가 "API Error 529 Overloaded가 무슨 뜻인지, 서비스 혼잡으로 중단돼도 사용 한도가 차감되는지"를 물었으나 컨텍스트 전환으로 답하지 못했다. **다음 세션에서 먼저 짚어줄 것**: 529는 Anthropic 서버 과부하로 인한 일시적 오류로 요청이 처리되지 않은 것이며 이 저장소 코드와 무관하다. 사용 한도 차감 여부는 클라이언트(Claude Code 자체)의 과금 정책 질문이라 이 저장소의 지식 범위 밖이다 — 확답이 필요하면 사용자가 status.claude.com 또는 자신의 Claude 요금제 대시보드를 확인해야 한다.
